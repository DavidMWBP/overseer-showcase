# packages/daemon

All state and side effects: Fastify, node:sqlite, the harness adapters and the MCP server. Loaded when working under this directory. The root `CLAUDE.md` keeps shared commands, configuration, conventions and the documentation-surface rule; `packages/web/CLAUDE.md` covers the views. This file is the code map and the gotchas; the full behaviour of each area is in the batches spec (`docs/superpowers/specs/2026-09-13-batches-speed-ui-design.md`, "spec §" below).

## Daemon restart and port takeover

`docs/daemon-restart-failure-modes.md` records every failure mode below with its symptom, the fix commit and the test that covers it (`src/daemon-restart.integration.test.ts`, slow).

- `GET /api/daemon` reports the daemon's commit, whether a restart is needed and the last restart failure. It is never held by the ready gate and carries no session row, since the takeover handshake reads it.
- Setup → Restart (`POST /api/daemon/restart`) compares the startup hash of the root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `packages/*/package.json`. Changed inputs, or an unavailable startup hash when current inputs can be read, run `pnpm install --frozen-lockfile` in that checkout through the shell (bounded to five minutes) before one detached successor starts.
- A startup hash read failure does not prevent startup. If restart inputs cannot be read during relaunch, Setup reports the reason and the current daemon stays online.
- An install or startup failure keeps the current daemon serving, shows in status with the reason and up to 20 output lines, and sends one wake notice. Setup hides an older failure while a restart is in progress. A second request while shutdown is pending returns 409.
- The parent waits for its detached successor to load and reach the restart-parent gate before it closes; a successor that does not reach it within 30 seconds is stopped and the parent keeps serving. Setup polls for `RESTART_POLL_TIMEOUT_MS` (`packages/web/src/views/Setup.tsx`), which must cover the install bound (`RESTART_INSTALL_TIMEOUT_MS`), this gate, the 10-second parent-close bound and the successor's bind.
- On success the old daemon closes board websockets and any open MCP stream, drops keep-alive connections and shuts down with a bounded wait; the successor binds with no retry deadline and adopts detached workers through `recover()`. A parent that cannot close cleanly still exits 0, since a non-zero code makes `pnpm -r --parallel start` stop Vite and the root process. The root pnpm process and its Vite sibling keep running, so the page and API proxy reconnect without a manual full-stack start.
- Ready gate (`registerReadyGate` in `src/app.ts`): the port can bind before recovery has run, so every request, websocket upgrade and MCP call is held until `lifecycle.recover()` and `servers.recover()` return, and `GET /api/health` answers 503 meanwhile (the web stays on its offline poll and refetches once ready). MCP is held because `worker_status` reads a session row recovery is about to end and `list_servers` a server row it is about to stop. Recovery may start the orchestrator against this daemon's own MCP server, but starting it only spawns the CLI, so no held tool call can stall `recover()`.
- A tagged restart successor waits for its parent and retries a busy port. A plain `pnpm start` retries a busy port for 15 seconds, then takes it only when `GET /api/daemon` on it reports the same `data_dir` and `source_root`: it stops that daemon process alone (`stopProcess`, no tree kill, so workers survive and are adopted), logs the stopped pid and retries the bind (`takeOverPort` in `src/util/daemon.ts`). A daemon of another data dir or checkout, including one reporting neither field, is never stopped; the start exits 1 naming that pid and process.
- `pnpm dev` (sets `OVERSEER_WATCH=1`) never takes an occupied port, so a watcher in another worktree cannot replace the long-running daemon. When a managed repo is the daemon's own source root (`src/util/watch.ts`, `WATCH_WARNING`) it warns once at startup, in the log and as a Chat notice, because a merge into the base branch restarts it mid-merge.

## Database

- The schema is created with `CREATE TABLE IF NOT EXISTS`. Migrations are `ADDED_COLUMNS` in `src/db/schema.ts` (a missing column is added with `ALTER TABLE ... ADD COLUMN` after a `PRAGMA table_info` check) and `ADDED_INDEXES` in the same file (`CREATE INDEX IF NOT EXISTS`, run after that loop, because an index on `worktrees.batch_id` needs the column first). Extend those lists instead of adding another mechanism. The connection sets `PRAGMA cache_size=-32768` (`db.ts`).
- `accounts` holds named harness credentials, optional labels and OpenCode providers that distinguish otherwise similar accounts.
- `preflight_runs` records every setup+verify probe of a repo (result `pass|fail|timeout|error`, exit code, last 600 chars of output); `repos.verify_suspect` holds the run id of the probe that made dispatch refuse, cleared on a passing probe.
- `repos.review_command` is nullable; `batches.review_check` stores the latest JSON result for a batch head (command, exit code, duration, output tail, parsed counts).
- `worktrees.verify_command` stores the optional command supplied only for a verify-only worker (a re-dispatch that keeps `verify_only` and omits `verify_command` retains it); `worktrees.verify_only_result` stores its latest head, exit code, duration, output tail and parsed counts.
- `batches.origin_chat_id` (nullable) and `chat_batch_links`: see [Orchestrator and chat](#orchestrator-and-chat).
- `programs` groups the batches of one multi-story request and records its repo, title, `open|done` status, creation time and nullable origin chat id. `program_batches` assigns each batch one lane and a zero-based position unique within that lane; `batch_waits` records prerequisite relations, their durable release time and one-time notice state; `program_entries` stores verbatim decisions, ownership and notes with a nullable source chat id; `merge_order` stores the program's batch ids at zero-based positions. A wait releases only after its prerequisite batch is merged.
- Batch ids carry four random base32 characters, so a reset install cannot adopt the previous one's labelled beads.

## REST API and socket

- `src/api/rest.ts` holds every route. Fastify's own logger is off, so unhandled 500s are logged by the REST error handler.
- Action endpoints (eleven): `POST /api/tasks/:id/{merge,reject,interrupt,verify,close,close-landed,redispatch,accept-review}` and `POST /api/batches/:id/{merge,reject,abandon}`. They check only what needs no git or bd work — the target, from the daemon's rows and the filesystem, and the state it requires (e.g. a batch in review) — and answer `202 { job_id, action, target }` at once, running the lifecycle call as a background job (`src/api/jobs.ts`: in memory, one job per target, gone on a restart).
  - A second request while its job runs answers 409 `{ error, job_id, action }` naming the running action, checked before the state checks (which a running job may already have changed).
  - A refusal those checks can make stays a 4xx; a refusal only git or bd can see is the job's `ok: false` result. The `/verify` job follows the run through the `done` promise `Lifecycle.reverify` returns, so a failed verification is its `ok: false` result.
  - The target's board row carries `pending_action { job_id, action, started_at }` while it runs; the `action_result` socket message reports the outcome.
  - The three terminal batch actions also exclude each other per batch inside the lifecycle: a Merge, Reject or Abandon started while another runs is refused with `batch <id> is being merged|rejected|abandoned`, whether it came from a REST job or the MCP `merge_batch`/`reject_batch`/`abandon_batch`.
- `GET /api/chat?limit=&before=&since=` returns a chronological `ChatPage` (default 100, maximum 500; `before` pages backwards, `since` returns a delta). Every page also carries the `reply_to` rows it references, every open question and every `queued_at` row however old, while `has_more`/`oldest_id` describe the window only. Every row carries `seen_at` (set when handed to an orchestrator session) and `replied_at` (set on a user row the orchestrator answered after seeing it).
- Programs: `GET /api/programs?repo=<id>` lists programs newest first for a repo; omitting `repo` lists all. `GET /api/programs/:id` returns lane-ordered batch mappings with current batch status and bead counts, waits with their persisted `released` state, chronological entries and the ordered merge list. Counts read beads from the program's repo only. A program with no batches returns empty collections without building the board.
- `POST /api/chat` accepts `open_question_ids`, the IDs open when drafting started: absent keeps the older close-all behaviour, `[]` closes none. Only named questions still pending are closed and listed in the delivery prefix; the turn-end cutoff targets only those IDs. The route responds after storing the message and attachments and emitting chat; user-message deliveries continue serially after the response. A thrown delivery is logged and adds one system chat row with the error. That row and the account refusals of a user send store the user row id in `chat.failed_for`; `POST /api/chat/:id/retry` sets `retried_at` on every failure row of that message and re-delivers its stored text and attachment lines on the same queue, answering 404 for a row without `failed_for` and 409 for one already retried; startup requeues an accepted retry left pending by a daemon restart before new chat sends.
- `GET /api/usage?from=&to=&group=` (`src/api/usage.ts`; the request and response shape is in spec § API): reported and estimated dollars are never added together, each a floor carrying the count of sessions with no such figure (`reported_unknown`, `estimated_unknown`); each bucket is one grouped SQL query so thousands of sessions stay fast; every bucket carries `codex_sessions`, since a breakdown row names no harness and the Usage view marks a codex estimate from that count.
- Evidence (read-only, from `<dataDir>/evidence`): `GET /api/evidence` returns folder summaries (name, recursive count and size, newest file time) newest first. A cold folder scan uses async filesystem operations; a cached summary returns immediately while one coalesced async refresh runs for that folder, so in-place file changes appear on a subsequent load after refresh. Direct root files use the reserved label `<evidence-root>` (it cannot name a real Windows folder). `GET /api/evidence/:folder` returns recursive file metadata; adding `offset` or `limit` returns `{ files, total, next_offset }` pages (100 by default, maximum 500), while a request without either query parameter keeps the full-array response. `GET /api/evidence/:folder/*` serves file contents. Symlinks are refused, paths stay within the evidence root, and file opens use `O_NOFOLLOW`; HTML and SVG are sandboxed, other files download, byte ranges return 206 or 416, and HTML, plain, Markdown and CSV responses declare UTF-8.
- Accounts: `GET|POST|PATCH /api/accounts`, `/api/accounts/:id/login`, `/login/code`, `/usage` and `/verify` serve Setup ([Accounts and auth](#accounts-and-auth)).
- Repos: `POST /api/repos` runs `bd init --prefix <id> --non-interactive` itself when `.beads` is missing, adding `--stealth` unless the body sets `beads: 'commit'`; `worker_limit` (default 2, 1 to 16) caps a repo's running workers (`worker limit N reached`); `POST /api/repos/:id/probe` (202) triggers a preflight probe; `GET /api/repos/:id/preflight` returns `{ runs (20, newest first), crashes (per harness and class) }`.
- `src/api/commands.ts` reads repo and global `.claude/commands` and `.claude/skills` metadata without following symlinks (malformed frontmatter leaves an empty description); `rest.ts` serves the combined, name-sorted list with a 30-second per-repo cache.
- `src/doctor/doctor.ts` backs `GET /api/doctor` (prerequisite checks, `TOOLS`); `src/fs/` backs folder browse and repo inspect for Setup.
- `src/api/board.ts`: `buildBoard`, `coalesced` (concurrent builds share one promise) and `BoardCard.state`, the one word the web drives a card's actions from. Board batch rows expose `linked_chat_ids`.
- `src/api/ws.ts`, the `/api/events` socket. Messages: `board`, `chat`, `status`, `repos`, `event`, `session_ended`, `plans`, `discussion`, `action_result` (`{ job_id, action, target, ok, message, data }` when a background action ends), `orchestrator_activity` (latest value resent to every new socket), `office`, `office_snapshot` and `office_milestone`.
  - Office feed (`src/office/office.ts`; states, fields and milestone kinds in spec § API): `office` is one message per session state change plus one when a harness resolves the model; `office_snapshot` is the whole set on every connect (empty included) and the web replaces its set with it; `office_milestone` is one-shot and never in the snapshot. Recovery's ended-write publishes `session:reaped`, so a connected socket sees the leave, and a snapshot built during recovery is reconciled against the running rows.
  - A stall is `stalled_since` on the session (set by the sweep's `onStalled`, cleared by the next event or a sweep that no longer finds it). A usage-limit pause publishes nothing, since the daemon has only an account hold for it.

## Child processes and hooks

- `src/util/procs.ts`: every child process goes through `spawnLines`/`runCapture`. On Windows they resolve `.exe` and npm `.cmd` shims and spawn with `shell: false` (cmd.exe truncates args at newlines). Verify, review and setup commands (`src/lifecycle/verify.ts`) and the restart install run through a shell.
- Harness processes are spawned with `logFile`: detached, unref'd, stdout/stderr in `<dataDir>/sessions/<session id>.log[.err]`, which the daemon tails, so they outlive a daemon restart; `adoptLines` follows such a process by pid from a saved offset.
- On Windows the detached process is `src/util/launcher.cjs`, which starts the harness non-detached with a hidden console (a detached process has none, so every console program under it, such as `codex.exe` or a Bash tool's `cmd.exe`, opened a visible window), writes the harness pid to `<log>.pid` (`LineProcess.pidReady`; that pid is the one recorded, adopted and killed) and exits with its code; the harness dies with the launcher (libuv's kill-on-close job object).
- The per-repo `setup_command` runs in every new bead and batch worktree, and before a batch's first merge if it has not passed there yet (`batches.setup_at`), so commit hooks and the verify and review commands find their dependencies. A failed setup reopens the bead with a `setup_failed` signal: in a bead worktree no worker starts and the worktree is removed; in the batch worktree the bead is not merged and Retry verification runs the setup and the merge again.
- `hooks/deny-background.cjs` is the PreToolUse hook every Claude session gets through `--settings` (`denyBackgroundSettings` in `src/harness/claude.ts`, matcher `Bash`). It denies (exit 2, reason on stderr):
  - a Bash call with `run_in_background`, since a headless session exits when the model yields;
  - on Windows only (`process.platform === 'win32'`), a Bash call whose command, split on `&&`, `||`, `;` and `|`, has a segment starting with `pnpm`, `npm`, `npx`, `vitest`, `playwright` or `playwright-cli`, because Git Bash rewrites `C:\program files\nodejs` and the corepack shim is not found (overseer-hpe1: 398 of 407 affected sessions were Claude). The reason reads `On Windows run this in the PowerShell tool instead: <command>`, with a leading `cd <dir> &&` turned into `Set-Location <dir> &&`; a name that is only an argument (`grep -r pnpm .`, `echo npm`) passes, but the split ignores quotes, so `grep -E "a|npm|b"` is denied too (use the Grep tool, PowerShell, or a script file). A headless `claude -p` has the PowerShell tool (probe 2026-09-24).
  - Tests: `src/harness/deny-background.test.ts`, which preloads a `process.platform` override to run both platforms.
- `hooks/deny-eval-side-effects.cjs` sandboxes prompt-eval sessions: [Prompts and evals](#prompts-and-evals).

## Beads

- `src/beads/store.ts`: `phaseOf` (the eight phase labels only), `batchOf` (`overseer:batch:<id>`, written at `bd create` time so a batch counts a bead before its first dispatch), `columnFor`, `blocked`/`dependentsOf`/`blockersOf` (one `bd blocked` read carries both directions).
- `src/beads/beads.ts`: `BD_READS` is the single list of which bd commands are reads; it decides both what may run alongside what in the per-repo queue and what schedules a Board refresh.
- One bd write per lifecycle transition (`store.update` takes status, phase and note together). A bd call costs about half a second and the board's `bd list` queues behind that repo's writes; its last result is reused for up to two seconds while nothing in the repo's `.beads` moved (the files bd rewrites on a mutation), and any write clears it.
- bd 1.2.2: `bd create --deps` takes `blocked-by:<id>` / `depends-on:<id>` for the depends-on direction; `blocks:<id>` is the reverse. `bd close` refuses a bead with open blockers unless `--force`, which also overrides the pinned and gate guards.

## Orchestrator and chat

- `src/orchestrator/orchestrator.ts`: the idle rule (`OVERSEER_ORCHESTRATOR_IDLE_MIN`), the fresh-session preamble, wake vs. queued notices, superseded questions, and `activitySummary` (one line per tool call, exposed only through the rail mascot's accessible label, never the full command or output).
- Notices: `wake` starts a session; everything else waits for the next turn and carries `chat.hint`, never shown to the user. A no-action kind (`isQuietNotice`, `quietNotices.ts`) starts no turn even while a session is live: it is written to the chat as queued, to its bead's notes when the caller passes `beadId` (`noteBead` in `index.ts`), and prepended once to the next turn under `[Overseer] Since your last turn:`.
- Chat replies stay focused on questions, decisions, actionable failures and completed requests; the orchestrator searches and reads for itself before using a helper, caps helper reports at about 100 words because the full report reaches Chat, and skips progress recaps between tool calls. The one-line note before a call expected to take over a minute remains.
- Chat attachments use the `attachments` column and `<orchestratorDir>/attachments/`; delivery appends one `[attached image: <absolute path>]` line per file, including on rejections.
- The orchestrator pushes every assistant reply (skipped in a turn that called `ask_user`) while the `push_on_reply` setting is on ([Push](#push)).
- `batches.origin_chat_id` is set from the latest user message the orchestrator's session has been handed (`seen_at`) when it calls `create_batch`, so a follow-up sent mid-turn wins over the message that started the turn; notice turns, plan approval and web creation leave it null.
- `chat_batch_links (chat_id, batch_id, created_at, PRIMARY KEY (chat_id, batch_id))` records every batch an MCP call acts on for a message: `create_batch`; a `batch_id` on `bd`/`spawn_worker`/`request_batch_review`/`reject_batch`/`merge_batch`/`retarget_batch`/`abandon_batch`; and `message_worker`/`interrupt_worker`/`close_bead`/`retry_verification`/`accept_review` plus a `bd note`/`update`/`dep add` write, taking the batch from the bead's `overseer:batch:<id>` label. A bead with no batch records nothing; the same pair twice is one link. Board batch rows expose them as `linked_chat_ids` (`BatchSummary`, sorted, `origin_chat_id` included).
- Token refresh on a live session: when its recorded `token_expires_at` no longer matches its account's, or is inside `CLAUDE_OAUTH_REFRESH_MARGIN_MS` (two hours), it is ended before the turn and the same native session resumed on the account's current environment, so context and open questions stay and no "New orchestrator session" row is written. While a turn is running the delivery joins it instead (ending the process would kill that turn); the rail reads idle, not ended, while either resume path replaces the process.
- A turn rejected on its token (`auth_failed`, or a `turn_end` with `authFailed`) writes no chat row: the process ends, `freshAccountEnv` runs, the same native session resumes, and every failed delivery — a user message, an answer or a notice — is re-sent once each in order. The not-logged-in line appears only when the refresh is rejected or the resumed session is rejected again; there is no second retry.
- Orchestrator account fallback: before a new session starts, its Claude OAuth account uses the same running-session-adjusted usage gate as workers and critics. A usage refusal or an unexpired `accounts.exhausted_until` selects the first other usable logged-in Claude OAuth account in Accounts-list order, and Chat records that fallback once. A proactive token rollover of a live orchestrator session resumes on the refreshed token without the usage gate. An auth-failure resume is gated on its pinned account and stays there if the gate refuses it.

## Accounts and auth

- `src/accounts/env.ts` refreshes expiring Claude OAuth credentials and injects `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, a provider-specific OpenCode API-key variable, or `CODEX_HOME`. A Claude OAuth access token expiring within two hours is refreshed before a session starts, and the session records the expiry it started on.
- Logins: Claude is OAuth with PKCE driven from the page, with a `claude setup-token` paste fallback; Codex uses device login; OpenCode uses a known provider and a pasted API key, whose provider and secret can be replaced through PATCH and are never returned by the API.
- Rejected login on a worker or critic: treated as a token rollover first. From the structured signal (`auth_failed`, or a `turn_end` with `authFailed`) the account's environment is refreshed and the same native session resumed with a short continue prompt (a claude worker's or critic's native id is recorded at spawn, so a first turn rejected before any result can still resume); a review session re-runs its round through `startReview` without spending one, on whichever usable critic candidate the tier picks again. When the stored token is the very one rejected (the session's recorded expiry equals the account's), `freshEnvForResume` forces the refresh even with hours left.
- Only a rejected refresh, or a resumed session rejected again (one resume per ended session, marked `sessions.auth_resumed` so it holds across a restart), parks the account at a far-future `AUTH_HOLD_UNTIL` that only a successful login or verify clears (`clearAuthHold`), records `crash_class='auth'` and sends one notice naming the account and asking for the re-login.
- A worker or critic auth resume that passes token refresh but fails the usage gate is not started; it reopens the task with the usage reason and does not park the refreshed account.
- A stop from the user or the orchestrator wins over the resume: that worker settles as stopped. A 401 merely quoted in a session's own output parks, resumes or classifies nothing; the exit text is read only for a session on the CLI's own login, which has no account to park.
- Holds: before a new worker, critic, discussion participant or synthesis, or orchestrator session starts on a Claude OAuth account, the usage gate checks session, weekly and matching-model usage against `max(OVERSEER_USAGE_THRESHOLD / 2, OVERSEER_USAGE_THRESHOLD - running sessions on the account * OVERSEER_USAGE_RESERVE_PER_SESSION)`. For a new start it counts all other running rows for that account, including workers, critics, discussion sessions and orchestrator sessions; for a resume it excludes the session being resumed. The reserve defaults to 2 percentage points. A refusal names the configured and effective thresholds and running-session count. The gate never stops a running session, and an account's cached usage is dropped when its session ends. An unreachable first usage fetch and non-Claude accounts remain usable; `accounts.exhausted_until` and auth holds keep their existing behavior. A candidate whose account has no authorization yet, or whose stored token can no longer be refreshed (a revoked or expired Claude OAuth grant, invisible to `accountLoggedIn` because its stale access token is still stored), is skipped, not failed on.
- Claude `rate_limit_event` messages from worker and critic sessions are lifecycle stops: the account is held until its reset, then the same bead re-dispatches through the usable-account picker without step-up or model avoidance; with no account left it stays Ready with an entry in the Office Needs strip.
- Codex usage limit: a codex session that ends after a `usage_limit` event (`CodexParser`) holds its account's `exhausted_until`, or with no account its harness in the `harness_limits` setting (`src/accounts/harnessLimits.ts`), until the reset (one hour when unreadable). `spawnWorker`, the forced-harness path and `startReview` skip it via `unusableCandidates`; one notice names the harness, the UTC reset and the session. The session is then re-dispatched through `redispatchExhausted`, the account-exhaustion path:
  - a worker starts afresh on the next usable candidate of its tier; a forced, tierless worker on the next usable candidate of its own CLI, keeping that harness and the account it needs (its replacement row stays `tier: null`, so it never moves to another harness);
  - a critic resumes its current review round on the next critic candidate without reopening the bead or spending a round;
  - with no candidate left the bead stays Ready with a notice naming the held harness and its reset — except a forced, tierless worker whose own accounts are exhausted while its CLI is not held, which, only without a repository model filter, takes the forced route's degraded fallback (the CLI's own login, harness kept, tier and account null, with a warning); a forced worker whose whole CLI is held still waits;
  - a session stopped on purpose, or whose batch was abandoned or merged meanwhile, keeps the normal settle.

## Routing and tiers

A repository model filter restricts the global worker tier candidates by harness, model and account before routing and price sorting; it is not a separate tier table. Each non-empty list is an allow-list, empty lists leave that field unrestricted, and an account allow-list excludes machine login. All worker retries use the current filter, including review-findings and exhausted-account retries. A forced harness outside the filter is refused. If no allowed candidate is usable, dispatch is refused with the reason and the task waits; a filtered repository never uses the degraded CLI-default or machine-login fallback. Critics and their retries keep the global review tiers and are not filtered. `repos.model_filter` is exposed by `list_repos` and edited in Setup → Repositories; `filterRepoTiers` in `src/routing/tiers.ts` preserves global candidate order.

- Tier candidate lists (chore/standard/hard/critic, the optional critic-chore, plus the deny list) and the orchestrator model/effort/prompt override are key/value rows in the `settings` table, edited in Setup → Models; there is no env var for them.
- `resolveTier(settings, tier, opts)` (`src/routing/tiers.ts`) picks a harness+model for a tier from those lists, skipping denied models and (with `opts.stepUp`) moving one tier up; used by `spawn_worker` and the review round's critic dispatch. `critic` and `critic-chore` fall through `critic → hard → standard → chore` when their own candidates do not survive (`critic-chore` tries its own tier first), so a held harness anywhere in that chain is gated on the review path too.
- `standardCandidate(settings, harness)` returns the standard tier's candidate for one harness (denied models excluded) or undefined; a discussion participant runs on it and is refused by name when there is none.
- A first dispatch (`previousModels` empty) of a `chore` or `standard` bead takes the usable candidate with the lowest catalog input price (`ResolveOpts.prices`, the daemon's `PriceCatalog`; unpriced models after priced ones, ties in configured order; configured order when no catalog is passed or `PriceCatalog.loaded()` is false because no cached copy was read and no fetch has finished) and logs the pick with its price, or that no catalog is loaded. `hard`, `critic`, `critic-chore`, re-dispatches and a forced harness keep configured order.
- Resolution skips a candidate whose CLI is missing (`ResolveOpts.available`, fed by `commandExists` in `src/util/procs.ts`, one-minute cache; tests omit it, so every harness counts as installed), so the codex-first defaults fall through to claude on a machine without codex.
- Defaults (`DEFAULT_TIERS` in `src/db/db.ts`): worker tiers use Codex `gpt-5.6-luna`/`terra`/`sol` (chore/standard/hard) with Claude as the fallback candidate in each; `critic` defaults to `fable` on Claude; `critic-chore` ships unset, so a chore bead's review falls back to `critic` until configured.
- Forced harness (`harness` without `tier`): runs on the first usable candidate of that CLI in the standard, chore, then hard tier (`FORCED_TIERS` in `lifecycle.ts`), with the same usage and exhaustion rules and fallback to the next usable account.
  - Without a repository model filter, with no usable candidate it keeps what it has — a retry's pinned model (else the CLI's default) and the account a retry recorded while that account is still usable — and otherwise falls back to the CLI's own login with a warning: a degraded session, not a failed one.
  - Why it matters: it gives a forced `claude` worker a configured Claude OAuth account and with it the `CLAUDE_CODE_OAUTH_TOKEN` that makes Claude Code load the plugin's MCP servers (Figma) instead of suppressing them for the machine login's claude.ai connectors, so a design-parity worker can measure a design itself. The session records the model and account it chose.
- Prompt selection: for an adapter failure or a long, silent check, the orchestrator chooses a CLI with usage headroom that fits the work and avoids the failing harness. OpenCode ends a silent turn after 20 minutes; Codex waits for `turn.completed` or process exit. Claude is used only when it is the sole fit or the user or a Claude-only MCP tool such as Figma requires it, since automatic retries keep a forced harness pinned.
- `harness` with `tier`: resolves only among that tier's candidates of that harness (`resolveTier`'s `harness` option: configured order, the same usage, exhaustion, `previousModels`, `needs_server` and held-harness rules, no step-up) and is refused as `no usable <harness> candidate in tier <tier>` instead of moving harness or tier. The session records the tier plus `sessions.harness_forced = 1`, so transient-crash, rate-limit, evidence-gate, review-round, deferred-work and Board retries keep both, across a restart too.
- `needs_server`: OpenCode cannot keep a server, daemon or browser alive (its shell tool reaps a backgrounded process and blocks for good on a detached one; measured in `docs/server-start-in-a-worker-shell.md`). A `spawn_worker(needs_server: true)` passes `NO_SERVER_HARNESSES` (`src/routing/tiers.ts`, the one place that list lives) as `unusableHarnesses`, so every OpenCode candidate is skipped, and an OpenCode harness forced with or without a tier is refused with that reason. The flag is recorded on `sessions.needs_server`, so an evidence-gate re-dispatch, a review round, a rate-limit pickup, a crash retry and the Board's Re-dispatch carry it.

## Lifecycle

`src/lifecycle/lifecycle.ts` drives dispatch, settling, verification, review, landing and merges.

### Settling a session

- A session end is settled once: the `session:ended` handler claims a session id in an in-memory set and writes `sessions.settled_at` as the settle starts (`claimSettlement`), so a second delivery for the same id — `finish` and a re-adopted process both reporting one end, or a replay after a restart — is ignored with one `log.debug` line. Recovery marks a lost session `ended` before settling it, and the guard reads `settled_at`, never `status`, so it still settles a session that never was.
- A stop marks the live session `stopped` before the process is signalled, so `SessionManager.finish` records `ended` on every end path even when the kill's own error event is consumed first. The stop travels on the `session:ended` event itself (`SessionEnded.stop`), so `settleWorker` reads it with or without an in-memory record and before the `interrupt` event (appended only after the signal) is written, instead of falling through to the crash rule and overwriting the row with `failed`.
- Uncommitted work: `settleWorker` reopens a bead whose branch has real work but whose worktree still holds a staged or unstaged edit or an untracked file, naming the paths as modified and untracked, since verification runs in that worktree and would pass on the uncommitted edit while the merge takes only the branch ref (`uncommittedWork` in `src/git/git.ts`, from `git status --porcelain`, which omits gitignored paths). The worktree's dirt at creation, after setup and before the worker started, is subtracted (`worktrees.created_dirty`, written at creation so it survives a restart), so the repo's generated files are not mistaken for the worker's while a re-dispatch's leftovers still count. It marks that session `failed` and records an `uncommitted_changes` reopen signal; a stop keeps its own outcome.
- Deferred work: a worker that ends with no commits and whose final message hands the work to a background agent or promises a later result is its own outcome. `deferredWorkSentence` matches a deliberately narrow set of phrasings from the final text alone (never from timing) and excludes a message that reports finished work plus a check still running. `redispatchDeferred` records the triggering sentence on the bead and as the note of a `no_commits` reopen signal, then re-dispatches at once on a harness the bead has not just run on (`SpawnOpts.avoidHarness`, added to `resolveTier`'s unusable harnesses) with an instruction to do and commit the work in that session. A refused re-dispatch leaves the bead Ready with the sentence and wakes the orchestrator.
- Crash classes (`src/lifecycle/crash.ts`): `classifyExit(reason, stderr)` labels a worker that ended without commits: `transient` when the exit reason starts with `event stream failed`; `harness_bug` when it ends `exited with code 2` and the startup-only stderr carries CLI usage text (read only when the session produced no events); `auth` when the exit reason or stderr reports a rejected authentication (a 401 with an OAuth or authentication word; read only for a session on the CLI's own login); else `task`. `settleWorker` stores it on `sessions.crash_class` and a `crash` batch signal.
- A first transient crash (the bead's previous session was not transient) re-dispatches once, fresh, pinned to the same harness and model, with notice `<bead> re-dispatched after a transient stream failure on <who> (<reason>).` and no wake; any other outcome (a refusal, a second transient, a harness bug) falls through to the normal reopen, a harness bug's hint naming the harness so the orchestrator does not retry it there.
- Every notice that reports a session's error text names the session's account (`sessionWho` in `lifecycle.ts`, `accountDisplayName` on `session.account`, the bare harness on the CLI's own login): `<bead> reopened: worker ended without commits<why> on <who>: <reason>` and `<bead> reopened: its review round on <who> could not be completed: <reason>`, so an auth error names the account to log in again.
- An automatic re-dispatch (`SpawnOpts.automatic`: an evidence-gate re-dispatch, a review round, a rate-limit pickup, a crash retry) passes as unusable to `resolveTier` a harness whose latest worker session here was stopped for inactivity (its `interrupt` event carries `stalled`, set by `interruptBead` when the stop followed the stall threshold) or reopened as a `harness_bug`, and refuses with `no usable harness for tier …` naming it when that leaves no candidate. A user's Re-dispatch from the Board does not set it.
- Before a finished lifecycle path removes a bead or batch worktree, and on every ended session, the scoped orphan-cleanup pass (`reapEndedSession`, overridable via `LifecycleDeps.reapEnded`) runs so a leaked process does not survive the landing.

### Verification and verify-only beads

- `spawn_worker` may pass `verify_command` only with `verify_only: true`, when one command decides a verification-only bead's pass or fail; a re-dispatch with `verify_only: true` keeps the stored command when no new one is supplied. The daemon runs it in the bead worktree at session end and records its command, head, exit code and parsed counts.
- The verify-only close applies when the branch has no commits, only merge commits or an empty diff (`nothingToLand`; a re-dispatched bead's branch carries earlier refresh merges) and the worker did not crash; a branch with real commits goes on to verification and landing.
- Unless a stop wins, an opted-in evidence report is checked against the bead description, final message and worktree HEAD before either close; a failure reopens as `verify_incomplete` with its problems in the note and notice. If `verify_command` and the gate both fail, one reopen includes both reasons.
- With `verify_command`: a passing run with no failing Check line closes as verified; a failing run reopens as `verify_incomplete` with its output tail, including a same-command worker PASS line when present. Any worker Check failure still reopens.
- Without it: an all-PASS Check result closes as worker-reported with the `overseer:worker-reported` label, close reason, notice and card state text; a missing, failed, blocked, not-run or malformed check keeps its `verify_incomplete` reason and reopens with the missing or offending lines in its note and notice. `Check:` and `PASS` match case-insensitively.
- For opted-in code beads, the gate runs before verification and critic planning. Its first failure automatically re-dispatches the same worker; a second consecutive failure awaits a decision. A passing gate and a non-automatic dispatch reset the count; an automatic retry keeps it.

### Review rounds

- Before verification or critic planning, `settleWorker` runs `evaluateEvidence` for a non-`verify_only` worker whose branch has code to land and no new uncommitted changes. It uses the bead description, final message and branch HEAD; no opt-in with no `Parity:` or `Evidence:` lines keeps the existing path.
- The first gate failure automatically re-dispatches the same worker on the first review-retry route without spending a round; a second consecutive failure parks the bead with the problems and totals. `worktrees.evidence_gate_failures` carries the count through automatic re-dispatch upserts and daemon restarts; a passing gate or non-automatic dispatch resets it.
- Each repo has `review_rounds` (default 2), a cap rather than a count; 0 disables the post-verification critic round (repo Setup form). After verification passes on a batch bead's branch, `startReview` dispatches a critic on a different model than the worker.
- `src/lifecycle/reviewPlan.ts` plans rounds from the bead's dispatch tier: chore gets one round, on `critic-chore` when configured, else `critic`; standard (a forced harness without a tier counts as one) gets round 1 on `critic-chore` (else `critic`) and round 2 on `critic` only after a round-1 `[must]` or a diff over 400 changed lines (`BIG_DIFF_LINES`); hard gets every round, all on `critic`. Round 2 and later pass the previous critic's model as `previousModels`.
- Diff size: `diffLines` in `src/git/git.ts` (`git diff --shortstat` insertions plus deletions over the review range), measured once when round 1 starts, kept on `worktrees.review_diff_lines` through the review's re-dispatches and in the bead notes, cleared by Retry verification and a fresh dispatch. A large diff's clean or should-only round 1 starts round 2 directly (`reviewsAgain`).
- Review range (`reviewDiff`, `src/git/git.ts`): the newest merge commit since the base decides, its second parent standing in for the base branch when the branch merged that base in, because `<base>...HEAD` would otherwise carry everything the merge brought (measured sizes in spec § Review rounds); with no merge commit since its base, `<base>...HEAD` unchanged.
- Prompt size: above `inputLimit(harness)` (`src/lifecycle/prompt.ts`; codex's measured 1,048,576 characters, carried by every harness, never raised by configuration) `boundedCriticPrompt` reduces the prompt in fixed steps until it fits, the diff first (replaced by `diffStat`) and the task description last (steps in spec § Review rounds). The `submit_review` instructions are never cut, and a critic whose criteria were cut is told to report them missing rather than read the task with `bd`, which a critic may not run. The steps come back as `omitted` (a bead note and one notice with size, limit and refs), so an oversized prompt is reported rather than refused by the CLI as a crashed critic.
- Verdict (`onCriticEnded`/`applyReview`, severity parsing in `src/lifecycle/reviewSeverity.ts`):
  - a pass, or findings with no `[must]` item, lands the bead (`landVerified`) with the findings in its notes (`Review findings landed with (round N)`) and the landing notice;
  - a `[must]`, or a severity that cannot be parsed, re-dispatches the worker with the findings;
  - at the round limit the bead parks `awaiting_decision`, whose notice ends with the bead's totals so far (worker and critic sessions, re-dispatches and the cost — reported, else the estimate, else `cost unknown`), and the user calls `acceptReview` (land anyway) or dispatches again;
  - a critic session that ends without a verdict becomes a no-verdict `must` finding.
- Review re-dispatch:
  - a harness forced with a tier (`sessions.harness_forced`) stays on that harness among that tier's candidates, no step-up, refusing rather than moving when none is usable;
  - a forced harness (`sessions.tier IS NULL`) keeps its pinned model and recorded account, revalidating that account's authorization and falling back to the next usable candidate of the harness (else the CLI login) when its token can no longer be refreshed; one that hung or failed to start loses its pin and retries through the standard tier;
  - tiered sessions use `resolveTier`, continuing on the first failed round (`SpawnOpts.continuation`) and, from the second failed round on, stepping up (`stepUp`) with previously tried models excluded.
- Resume needs the same harness and model and a non-empty `native_session_id` (codex and opencode report `''` when they have no thread); otherwise the dispatch starts afresh.

### Batches, merges and review commands

- `Lifecycle.requestBatchReview` runs the repo's review command in the batch worktree after pending setup and before a GitLab push or MR. It reuses a recorded pass for the same head and command (a failure or timeout runs again), gates failures with one wake notice, and stores results for `list_batches` and Review. Calls for one batch serialize from the open-state check through the status update, so concurrent requests cannot run the command twice.
- `mergeBatch(batchId, actor: MergeActor = 'user')` records who merged: the user's Merge / Mark merged, the orchestrator through `merge_batch` for local merges, or the GitLab MR watcher recording an external merge. The REST Merge button and MCP `merge_batch` use this same path. After a `local-merge` writes status `merged`, it queues plain `git push <remote> <base>` to the base's configured upstream or `origin`; it does not await the push, and no configured remote skips it silently. A failed push leaves the batch merged and queues one Chat notice with the repo, remote, first error line, retry command and repo path; the next successful merge pushes the current base, including earlier commits. Shutdown cancels a queued push before it starts. The completion notice names the approving actor (`by the user` / `by the orchestrator`), so an autonomous merge is not recorded as the user's.
- `batch_approver` per repo (default `user`, the migration gives existing rows that default; repo Setup form): `orchestrator` tells the orchestrator in the ready-for-review notice that it may merge a finished batch without asking. The merge gates (verify command, overlap hold, refusal to merge a batch not in review) are unchanged. `orchestrator` is valid only for `local-merge`: a `gitlab-mr` repo always approves with the user, the API refuses that combination, and `merge_batch` never merges an MR on its own.
- Program waits: `spawnWorker` refuses a batch with any unreleased wait and names the prerequisite and its current status. Both local merges and GitLab MR watcher merges persist release for every wait on the merged batch; `recover()` releases waits left behind by a crash after the merged status write. One wake notice per waiting batch uses a stable `chat.notice_key`, so startup retry can recover a missing notice without adding a duplicate Chat row. Abandoning a prerequisite leaves waits unreleased and wakes the orchestrator to ask the user what should happen next. A wait added after its prerequisite is already merged starts released and does not send a stale release notice.
- Stacking: review batches based on a batch branch refresh when that branch gains commits; open stacked batches pick them up when their next bead worktree is cut. When a parent batch is marked merged, every open or review batch based on its branch moves to the parent's base and its MR is retargeted when present; a squash merge leaves the parent's commits on the stacked branch, so refreshing relies on Git's merge and a conflict follows normal refresh handling. When a parent is abandoned, stacked batches stay on their base and the orchestrator asks whether to `retarget_batch` each to the parent's base or abandon it.

### Sweeps and the reaper

Behaviour in full: spec § Stall detection, § Idle end after a turn end, § Orphan reaper (and its § Leftover worktree folders). All three start in `index.ts` after `recover()` and stop in `onClose`.

- Stall sweep (`src/lifecycle/stall.ts`, every `SWEEP_MS` = 60 s): one queued notice per silent stretch of a running worker or critic once its latest event (`events.lastTs`, else `started_at`) is older than `OVERSEER_STALL_MIN` and its worktree is quiet too (changed files' newest mtime from `git status --porcelain`, read at most every `WORKTREE_CHECK_MS` = 5 min per session, because an opencode sub-agent edits files long before its `task` call reaches the log). The daemon only reports: it never interrupts a stalled worker, and never sweeps the orchestrator (idle between messages by design). Each pass hands `office.setStalled` the ids it finds (empty set included). `startStallSweep` returns null when the threshold is 0; its timer is unref'd.
- Idle-end sweep (`src/lifecycle/idle-end.ts`, same interval): ends a worker idling past `OVERSEER_IDLE_END_MIN` after a `turn_end` with a non-empty final message, through `SessionManager.end` (the clean-end path). It re-reads the latest event every pass (`db.events.last`, which skips a sub-agent event carrying a `parentId`), and `SessionManager.send` (`message_worker`) records a `message` event, so a message queued for an idling worker is its latest event and the worker is not ended out from under the reply. 0 disables it in both `startIdleEndSweep` and `sweepIdleEnds`; anything other than a non-empty `turn_end` is left to the stall sweep.
- Orphan reaper (`src/lifecycle/reap.ts`): `reapOrphans` at startup and every `OVERSEER_REAP_MIN` kills processes (`processRows`, `killProcess`) whose command line, or Linux cwd, names a `<worktreesDir>/<repo>/<name>` worktree no running session uses. It never touches a running session's worktree, a `base` worktree, a primary checkout, the source root, or the daemon or its ancestors, and a periodic pass also spares the daemon's descendants; a periodic pass kills a candidate only when all its live ancestors are candidates too, so a shell or editor the user opened on a worktree is safe.
- `reapEndedSession` runs on every `session:ended`, scoped to that session's worktree, without the live-ancestor guard. It also considers the daemon's descendants, but reaps one only when its cwd or executable path is inside the ended worktree; a worktree path in its other arguments no longer counts. It reads their cwd from `/proc` on Linux or one batched PowerShell query on Windows. This keeps a stopped worker's server eligible when it hangs off the exited CLI through the daemon; it stops each process with its tree and posts one notice naming what it stopped.
- `reapLeftoverFolders` (each periodic pass) removes a worktree folder git no longer lists once the daemon's record says the work is done, or after a day with no row, never outside the worktrees directory, through `removeWorktreeRetry`.

### MR watcher

Behaviour in full (poll cadence, merge detection, pipeline notices): spec § Lifecycle, "GitLab MR watcher" row.

- `src/lifecycle/mrWatcher.ts` polls `gitlab-mr` review batches every 120 seconds, one MR `glab api` call per batch per tick plus one pipeline-jobs call when needed. A merged MR goes through `Lifecycle.mergeBatch` with its GitLab actor, so the stacking and retarget paths are the same as a local merge.
- It never abandons a batch on its own: a closed MR only wakes the orchestrator to ask. The last valid state per MR URL and the last terminal pipeline id/outcome per batch survive a restart, so no notice repeats.
- Run `glab auth login` before using the `gitlab-mr` merge mode; `glab auth status` shows the login state. The provider's tests use a fake `glab`.

### Preflight probe

- `src/lifecycle/probe.ts`: `Prober.probe(repoId)` runs the repo's setup then verify command, serialised per repo, in a throwaway detached worktree `<worktreesDir>/<repo id>/probe` at the base head, removed after every run. It records a `preflight_runs` row and sets `repos.verify_suspect` to that run's id on `fail`/`timeout`, clears it on `pass`, and leaves it on `error` (could not start) or with no verify command configured.
- On the transition to suspect it sends one Chat notice ("Dispatch to <repo> is paused: <refusal>.") with a hint, plus a web push. Triggered by `POST /api/repos` (with a verify command), `PATCH /api/repos/:id` (verify or setup command changed) and `POST /api/repos/:id/probe`.

## Harnesses

- Sessions retain cumulative input, output, cache-read, cache-write and reasoning token counts when a harness reports them at turn end.
- MCP reaches every harness through its own mechanism. Claude gets `--mcp-config`. OpenCode has no such flag, so `OpencodeAdapter.start` writes a per-session config (`writeOpencodeMcpConfig`, `mcp: { overseer: { type: 'remote', url, enabled: true } }`) to the temp dir and points `OPENCODE_CONFIG` at it, loaded in addition to the user's own config; tools arrive prefixed (`overseer_submit_review`). Codex has none either and its `CODEX_HOME` already carries the account, so `codexMcpArgs` passes one `-c mcp_servers.<name>.url="<url>"` per turn (a dotted `-c` path sets that leaf only, leaving the user's servers in `$CODEX_HOME/config.toml` configured and no file of theirs written); a resumed turn is a fresh process, so it is passed again. Before this, both adapters dropped `mcpServers` and three opencode critics lost a verdict on 2026-09-17, one a clean pass recorded as findings.
- Claude orchestrator and critic sessions pass the daemon's `--mcp-config` without `--strict-mcp-config`, so they get the `overseer` server plus the user's configured MCP servers for that scope; any server in that config, now or later, is visible to every such session together with any credentials in its environment. Workers receive the `overseer` server too (for `start_server` and its siblings), on top of the repository's `.mcp.json` they inherit.
- Each session reaches MCP on its own URL, `/mcp/<session id>` (`registerMcp`), since `start_server` must know whose session it starts a process for and no harness lets the daemon set a header. `SessionManager.start` appends the row id to every configured MCP server URL. Bare `/mcp` still serves the identity-less tools; a server tool called there answers "this tool is available to a worker session only".
- Interrupt: `interruptBead` goes through `SessionManager.interrupt`, which ends the harness; each adapter's `interrupt()` calls the shared `sweepProcessTree` (`src/util/procs.ts`) after `killProcess` has taken down the CLI, so a Stop from the Board or `interrupt_worker` kills what the worker started — descendants and any process holding both session logs — each survivor dropped when it started before the session (an interrupted worker's dev server and two test daemons outlived it for hours on 2026-09-17, overseer-0zv and overseer-1xw).

### Claude Code

- Adapter fixture recorded from a real run; exercised live as orchestrator and worker (`docs/guide/limits.md` → Status and known gaps).
- Worker and critic sessions run without the user's context-mode plugin: `sessionSettings` (`src/harness/claude.ts`, from `StartOpts.role`, which `SessionManager.start` passes) adds `"enabledPlugins": { "context-mode@context-mode": false }` to their `--settings`, next to the worker's Bash hook. Each context-mode MCP server rescans every database under `~/.claude/context-mode/sessions` once a minute, and one per headless session kept the SSD at 100% active time on 2026-09-28. Orchestrator and discussion sessions keep the plugin. A `--settings` `enabledPlugins` entry overrides the user's `~/.claude/settings.json` (probe on Claude Code 2.1.283: no `context-mode/.../start.mjs` child with it, one without).
- No turn grace: one `claude -p` process idles between turns by design and its `result` line ends the turn. The orphan sweep (descendants plus holders of both session logs, each only when started after the CLI) runs at `end()` instead, once the CLI has exited at stdin EOF, because with `logFile` its stdout is a file handle a lingering dev server keeps open.
- Known gap (overseer-xnj, 2026-09-16): a detached Bash child with its own stdio survives `end()` when its intermediate parent exits before `result`; snapshots at `result` and just before stdin EOF are both too late, and the child holds neither session log. The regression in `claude.test.ts` is an expected failure pending a decision on earlier capture; no alternative cleanup mechanism was added.

### Codex

- `codex --version` gives the installed CLI; `src/harness/codex.ts` comments name the version each flag change came with. Its usage-limit refusal ("You've hit your usage limit ... try again at Sep 20th, 2026 12:18 PM.") names the reset in the machine's local zone (codex-rs `format_retry_timestamp`, time only when the reset is today); the adapter parses it into a `usage_limit` event ([Accounts and auth](#accounts-and-auth)).
- Reports no cost, so its card and totals read "cost unknown"; the session still records the catalog estimate with `cost_source: estimated`.
- Turn grace: the adapter ends a turn even when the CLI lingers after `turn.completed` (`TurnGrace` in `src/util/procs.ts`, `TURN_END_GRACE_MS`; `spawnLines` tails the session log from its current size, so an earlier turn's `turn.completed` never arms it), because a worker's dev server holding the CLI's stdio can keep a session open (incident: the spec's "Daemon-owned servers" bullet). After the grace the tree is killed and the turn ends normally. Once the CLI is gone, whether it exited after `turn.completed` or was killed, `TurnGrace.exitCode` sweeps any process that inherited both session-log handles, including an orphan whose intermediate parents exited, while excluding a human tailing only stdout.

### OpenCode

- Adapter fixture recorded from a real run; not exercised live in the UI loop.
- Permissions go through `OPENCODE_PERMISSION` instead of `--auto` (`opencode run --auto` fails with an UnknownError on 1.18.19); the value also allows `external_directory` (a DeepSeek run on 2026-09-17 was auto-rejected reading the session log) and the read and search tools claude and codex have. A tier effort becomes `--variant` only for a value the DeepSeek model accepts on models.dev (flash: low/high/max, v4-pro: high/max), so `medium`, `xhigh` and `ultra` pass none; `ultra` is Codex-only.
- The prompt goes over stdin, never argv (`opencode run` takes stdin as the message when no argument is given), since a diff-sized prompt exceeds the Windows command-line limit (`spawn ENAMETOOLONG`).
- An OpenCode account holds a provider key, and a tier candidate can point at that account; Setup decides which tier uses DeepSeek. A candidate with no account runs on the CLI's own login and is unusable to tier resolution (`Lifecycle.unusableCandidates`, through `LifecycleDeps.opencodeLoginReaches`, which `index.ts` sets to `opencodeOwnLoginReaches` in `src/accounts/env.ts`; omitted in tests) when that login holds no key for the model's provider: no provider key variable in the daemon's environment and no provider entry in opencode's `auth.json` (`opencodeLoginHasKey`). 1.18.19 without a key exits 1 at the first request with only `{"type":"error","error":{"name":"UnknownError","data":{"message":"Unexpected server error. ..."}}}` and an empty stderr (four account-less chore critics on 2026-09-28); a key the provider rejects is a 401 `APIError`. `OpencodeParser` reads that nested `error.data.message` with the `error.name`.
- Turn grace: the same `TurnGrace` as codex, armed by a `step_finish` line whose `part.reason` is `stop` (1.18.19 marks a turn's last step that way and every intermediate step `tool-calls`); after the grace the tree is killed and the orphan sweep runs.
- Silence limit (spec § Traces, cost, log): a turn that prints nothing for `TURN_SILENCE_MS` (20 minutes; every parent line and sub-agent event resets it; the adapter's fourth constructor argument overrides it) is ended through a zero-length `TurnGrace` with an `error` event and a warning naming the session, the silence and the last event type, because opencode can hang on a `step_start` forever. opencode prints a shell call only when it completes and a call may ask for any timeout, so the limit runs from the later of the last event and the latest deadline of the still-`running` tool calls in opencode's store (`runningToolDeadlines`, default call timeout `OPENCODE_DEFAULT_TOOL_TIMEOUT_MS`). An unreadable store keeps the plain silence, with one warning per session.
- Sub-agents: `SubagentWatcher` reads a `task` sub-agent's tool calls, texts and file edits from opencode's store (`~/.local/share/opencode/opencode.db`, every 2 s) with the task's call id as `parentId`, since `opencode run --format json` prints the task call only once finished. A resumed or adopted session primes it from the parts already stored, so earlier history is never replayed; an adoption reads the session id from the log's lines, since the native id is written only at turn end.

## Long-lived servers

- No harness can hold a long-lived process: opencode's shell tool is synchronous (upstream closed "no background process support" as not planned), codex's command policy refuses `Start-Process ... -PassThru` on Windows, and a claude worker is denied `run_in_background` by `hooks/deny-background.cjs` ([Child processes and hooks](#child-processes-and-hooks)).
- `src/servers/servers.ts` owns them instead: `start_server`, `server_logs`, `stop_server` and `list_servers` are MCP tools every worker gets. The process is a child of the daemon with its output on a file, so it holds none of the session's stdio and cannot keep a turn open; `stop` runs the same `sweepProcessTree` the adapters use, so a dev server's children and a chromium a Playwright run left behind go with it.
- A session's servers stop when it ends (`bus.on('session:ended')` in `index.ts`); `servers.recover()` kills any that outlived a restart. Rows live in the `servers` table.

## MCP tools

- `src/mcp/tools.ts`: besides `spawn_worker`, `request_merge` and the rest, the chat-parity tools `merge_batch`, `reject_batch`, `abandon_batch`, `close_bead` and `retry_verification` mirror the Review/Board buttons of the same name; they call the lifecycle directly and stay synchronous, unlike the REST background jobs. Also `retarget_batch(repo, batch_id, base)` when the user asks to move a stacked batch, `submit_review`/`accept_review` for the critic round, and `propose_plan(repo, title, steps)`, answering `{ plan_id, url, steps }`, for the plan gate.
- Program tools: `create_program(repo, title)`, `add_to_program(program_id, batch_id, lane, after_batch_id?)` (the optional batch creates a wait), `log_program_entry(program_id, kind, text)`, `set_merge_order(program_id, batch_ids)` and `list_programs(repo, program_id?)`. They refuse unknown or cross-repo batches, wait cycles and merge orders with batches outside the program; a program detail includes its current bead counts, waits, entries and merge order. The orchestrator prompt's Batches and beads → Programs rules say when it opens a program and what it records (spec § Data).
- `batch_retrospective` is compact by default (rejections and corrections cut to 400 characters with `truncated` flagged, other signal text to 300, re-dispatches grouped per bead); `full: true` or `bead_id` returns the uncut record, while the notice, the REST route and `dayReport` read the full one.
- The `bd` tool returns a read command's full output but trims a write (`create`, `note`, `update`, `close`, `dep add`/`remove`, `label add`/`remove`) to the bead id(s), status and title — its labels on `create`, the two ids and type on `dep add`/`remove` — and `dep list` to id, title and status per dependency, so a long description or notes is never handed back to be re-read.

## Discussions

Behaviour in full: spec § Discussions. `src/discussions/discussions.ts` runs the rounds, the stop rule, the closing synthesis and the cost cap for the `role: 'discussion'` session role (`SessionRole` in `packages/shared`); prompts are `prompts/discussion.md` (read and search only: never edit, commit, switch branches or push) and `prompts/discussion-synthesis.md`.

- The role stays out of the idle-end and stall sweeps, the worker and critic paths, and the board and office.
- `POST /api/discussions` takes one to three distinct participants, each on its harness's `standardCandidate` and account with `keepAlive: true`, in a throwaway detached worktree `worktrees/<repo>/disc-<id>/<harness>` on one base SHA shared with the synthesis (no repo: a temp dir under `<dataDir>/discussions/<id>/<harness>`), asserted never to be the repo's primary checkout.
- A round-1 turn that ended after an `error` or with no text, and a later-round turn with no text after its round prompt, fail that participant. A session that ends on its own without a `turn_end` is noticed one macrotask after `session:ended`, so a buffered turn end is recorded first.
- The cost cap is checked after every turn end, the synthesis's own included (`discussionCost` counts its live session cost or stored `synthesis_cost`): at or above it everything ends as `stopped` with no synthesis, on purpose. A Stop that lands while a synthesis settles stays final rather than being overwritten with `done`; `POST /api/discussions/:id/stop` waits for every start to settle.
- `DELETE /api/repos/:id` snapshots each discussion into `discussion_participants` before deleting session rows; every session end emits the `discussion` ping; `recover()` fails a still-running discussion (`daemon restarted`).
- Images (up to four, 8 MB decoded each) reuse the chat validator and storage helper and are copied into each cwd as `.discussion-attachments/<index>-<name>`; responses never return file paths.

## Plans

- `src/plans/plans.ts`: `Plans` (`propose`, `save`, `approve`, `discard`, `drafts`, `all`), `PlanError` (the REST error handler answers 400) and `PlanConflictError` (409, a stale revision or a plan no longer a draft). A plan (`plans` table; `Plan`/`PlanStep`/`PlanStatus`, `planProblem`, `planOrder` in `packages/shared/src/plan.ts`) touches no git or bd state until approved.
- REST: `GET /api/plans` (drafts only, for the Needs strip and its Plans-row count), `GET /api/plans/all` (every status, newest first), `GET|PUT /api/plans/:id`, `POST /api/plans/:id/approve`, `POST /api/plans/:id/discard`; a `plans` socket message (bus event `plans`) tells the web to refetch both.
- `approve` calls `createBatch` without an alternate base (the repository's configured base), then creates one bead per step in `planOrder` (dependencies first) via `TaskStore.create` with `--deps blocked-by:<id>`. A bd failure mid-loop calls `Lifecycle.rollbackBatch`, which closes the beads made so far and removes the worktree, branch and row with no notice or retrospective signal; the plan stays a draft.

## Pricing

Behaviour in full: spec § Traces, cost, log. `src/pricing/catalog.ts`: `PriceCatalog` (models.dev, cached at `<dataDir>/models.dev.json`, refreshed daily) and `priceFor`, which matches a model id exactly (opencode ids carry the provider, `deepseek/deepseek-flash`; claude prefers `sessions.resolved_model`, so `fable` prices as `claude-fable-5-1`) and returns null rather than a close match. `SessionManager` writes `estimated_cost` beside the CLI's `cost` and sets `cost_source`.

- Claude and codex are priced once from cumulative counters. `addUsage` adds Claude's per-turn usage but replaces codex's, whose `turn.completed.usage` is the thread's running total (measured sample in `src/sessions/manager.test.ts`). Only codex's non-cached `input_tokens` slice is billed at the input rate.
- A resumed codex session stores the thread's counters at resume in `sessions.usage_baseline`, and `addUsage` subtracts them, so the row's tokens and estimate carry only its own turns and summing a bead's sessions counts the thread once.
- Codex caveat: `gpt-5.6-*` carries a higher per-request tier (`context_over_200k`, `tiers`) the estimate deliberately does not apply, since codex's stream reports no request's own context; a session whose requests crossed ~272k tokens is estimated low by up to 2x.
- opencode is priced response by response (`step_finish`), each at the tier `selectContextPrice` picks from that response's raw input as opencode does: the matching `tiers` entry with the largest `size`, else `context_over_200k` only when `inputTokens > 200000` and no entry matched, else base prices. Its `reasoning_tokens` bill at the `output` price; Claude's and codex's reasoning is inside `output_tokens` and is not billed twice.
- Claude cache writes split into a 1-hour slice (`message.usage.cache_creation.ephemeral_1h_input_tokens`, `TokenUsage.cacheWrite1h`) and the rest of `cacheWrite`; `estimateCost` bills the 1h slice at 2x the input rate (Anthropic's documented multiplier) and the rest at the catalog's 5-minute rate.

## Reports and retention

Behaviour in full: spec § Nightly report. Both run on the nightly clock started in `index.ts` after `recover()`.

- `src/report/dayReport.ts`: `buildDayReport` derives one UTC day's counters per repo from the stored record (reusing the retrospective's signal extraction and the usage reader's sum); `renderDayReport` renders plain text.
- `src/report/nightly.ts`: `startNightlyReport` at `NIGHTLY_HOUR` (03:00 local; `msUntilNextLocalHour` only moves forward, so it never runs at startup and a missed night is skipped) writes `<dataDir>/reports/<UTC date>.txt` per repo and notifies through `orchestrator.systemMessage` only past a threshold: `NO_COMMIT_THRESHOLD` (3), `REDISPATCH_THRESHOLD` (3, `dayReport.ts`) or the review-round limit, `ORPHAN_BYTES_THRESHOLD` (1 GiB). A failed run is logged and rescheduled.
- `src/report/retention.ts`: a session ended more than `OVERSEER_RETENTION_DAYS` ago loses its events and stdio log (row, cost and tokens stay); a running session is never touched, a stored `log_path` is used only inside the sessions dir, and pages return through an incremental vacuum (one full `VACUUM` the first time).

## Prompts and evals

- `prompts/orchestrator.md`, `prompts/worker.md`, `prompts/critic.md` (the critic reviews a branch's diff and calls `submit_review`), covered by `src/lifecycle/prompt.test.ts` and `src/orchestrator/orchestrator.test.ts`.

### `pnpm --filter @overseer/daemon eval:prompt` (spends tokens)

Flags: `[--prompt <file>] [--cases <dir>] [--k <n>] [--max-run-usd <n>] [--judge-model <model>] [--out <dir>]`. Runner `scripts/prompt-eval.ts`; case format, checks, judge grading and scoring in `src/evals/promptEval.ts`.

- Scores a prompt file (default `prompts/orchestrator.md`) against the JSON cases directly in a split directory (default `evals/orchestrator/cases/train/`, 20 cases; `holdout/` holds 10 more, scored with `--cases evals/orchestrator/cases/holdout` and never shown to anything that rewrites a prompt), K runs each (default 3). Reports the mean case pass rate, the prompt's character count and each run's cost and duration in `<live data dir>/evidence/prompt-evals/<run id>/` (or `--out`), never in the repo.
- Mock MCP (`src/evals/mockMcp.ts`) serves the names and schemas `registerTools` registers, runs no handler, and records raw arguments for every `tools/call`. Schema-parsed arguments, defaults included, select fixtures only; repeated matching calls consume duplicate fixtures in listed order, then reuse the first match; a `bd create` reply carries the submitted title, as does every later reply naming that bead; refused calls are recorded with `rejected` (`not_called` counts them, other checks do not).
- A run starts the orchestrator through `SessionManager.start` as the daemon does (preamble from `sessionPreamble`), on the live orchestrator's model, effort and account from a read-only database handle, with a temp database guarded by `assertNotLiveDb`, a temp cwd, `strictMcpConfig`, a `maxBudgetUsd` cap and `noSessionPersistence` (the three start options only the eval sets). The empty `~/.claude/projects` folder the CLI still makes for the temp cwd (`claudeProjectDir`) is removed afterwards unless it holds a file.
- Sandbox (tests: `src/evals/denyEvalSideEffects.test.ts`, `src/evals/promptEval.test.ts`, `src/harness/claude.test.ts`):
  - `evalSessionEnv` (`src/evals/gitEnv.ts`: `GIT_CONFIG_NOSYSTEM`, empty `GIT_CONFIG_SYSTEM`/`GIT_CONFIG_GLOBAL`, inherited `GIT_*` dropped) switches off system and global Git config, so a stock install's system `diff.astextplain.textconv` runs for no read and only the repository's own config is left to refuse.
  - `hooks/deny-eval-side-effects.cjs` (Bash, Read, Grep, Glob) blocks network and local-port commands, shell redirection and anything outside a read-only allowlist (Git reads: branch, blame, diff, grep, log, ls-files, rev-parse, show, status). It also refuses the allowlisted forms that run a program or write or read a file (sed `e`/`w`/`W`/`r`/`R` and the `e`/`w` flags of `s`; sed script files, parsed, an unreadable one refused; `find -exec`/`-delete`/`-fprint`; `rg --pre`; `sort -o`/`--compress-program`; `git grep -O`; `file -C`; `uniq` with an output file), and any Git command in a repository whose config sets a helper (the keys in `GIT_HELPER_CONFIG`) or under `GIT_EXTERNAL_DIFF`, `GIT_PAGER` or `PAGER`.
  - It rejects UNC paths for read tools and confines native file writes to the eval cwd; `--tools` limits built-in tools to `Bash,Read,Grep,Glob`, and the strict MCP config exposes only the fixture-backed server.
- A one-line probe on that account must answer before any run. A run counts only when `turnProblem` finds a clean, completed turn (`runPassed`). `parseJudge` fails any rubric grade whose quote is not in the transcript or that lacks the evidence the judge contract asks for; a judge reply with no readable grades gets one more judge session (`JUDGE_ATTEMPTS`).
- A new case quotes its `docs/lessons.md` entry verbatim and uses an entry no other case in either split uses; `src/evals/promptEval.test.ts` checks that plus the split sizes and the silence (`no_message`) and `ask_user` counts.

### `pnpm --filter @overseer/daemon eval:loop` (spends tokens)

Flags: `[--prompt <file>] [--train <dir>] [--holdout <dir>] [--k <n>] [--rounds <n>] [--budget-usd <n>] [--target-chars <n>] [--target-holdout <n>] [--max-rewrite-usd <n>] [--train-report <json>] [--holdout-report <json>] [--max-run-usd <n>] [--judge-model <model>]` (the last two pass through to each eval). Runner `scripts/prompt-loop.ts`, decisions in `src/evals/promptLoop.ts`, live-install helpers shared with `eval:prompt` in `scripts/evalLive.ts`.

- Defaults: K=3, 5 rounds, $300, 30,000 characters, 0.9 holdout, $10 per rewriter call.
- Round 0 scores the prompt with `eval:prompt` (a child with `--out` into the loop folder) or reads two reports, refused by `checkRound0Report` when `prompt_chars` differs from the file or `k` from K.
- Each round one fresh rewriter `claude -p` (like the probe and each judge, a `claudeCall` whose process tree is killed after `CLAUDE_CALL_TIMEOUT_MS`, 30 minutes) on the live orchestrator's model, effort and account (no tools, no MCP server, temp cwd, `evalSessionEnv`) gets `buildRewriterInput`: the best prompt and its length, the target, the train cases and the failed train runs' transcripts and checks, never a holdout case, transcript or per-case result.
- `keepDecision` keeps a candidate only when it is shorter and its holdout and train scores are both at least the best's (within `SCORE_TOLERANCE`, 1e-9, counts as equal); every candidate is scored on train and holdout at K. `stopReason` stops on the target, the round count, the budget, or a next-round estimate (mean round cost, or before round 1 the round-0 cost plus the rewriter cap) that would pass the budget.
- Output only to `<live data dir>/evidence/prompt-evals/loop-<run id>/`, never `prompts/`.

## Testing

- Tests use real git repos (`src/test/tmpgit.ts`), real SQLite (`:memory:`), the fake adapter (`src/harness/fake.ts`) and a real in-process MCP client; test output must stay free of warnings.
- Run child processes asynchronously, never `spawnSync` or `execSync` in a loop: a file that holds a Vitest worker's event loop for about a minute fails the full `pnpm --filter @overseer/daemon test` run with `Timeout calling "onTaskUpdate"` while every test passes, and still passes alone (it happened in `src/evals/denyEvalSideEffects.test.ts`).
- Three files are in `slowTestFiles`. `src/beads/beads.live.test.ts` makes about 25 real bd calls sharing one repo, and `src/daemon-restart.integration.test.ts` starts a second daemon and waits out a hardcoded busy-port retry window. `src/api/evidence.performance.test.ts` creates 11,000- and 5,000-file temporary trees. The process tests can be flaky under load: a `Hook timed out in 60000ms` in `beads.live.test.ts` means bd was slow, not that the wrapper is wrong.
