# Setup and configuration

## Setup

Setup has sub-navigation with one section visible at a time: General contains Prerequisites, a link to the Usage view and Daemon, followed by Models, Accounts, Notifications and Repositories. General is the default, and Setup remembers the selected section for the browser session. Prerequisites, the daemon line and the repository table shimmer in the shape of what arrives while their first fetch is in flight, so nothing under them moves when it lands; an unanswered repository list is not reported as an empty one, and a fetch that failed shows its plain state instead of a shimmer. An account is a separate Claude or Codex login: add it in Setup → Accounts, then use **Log in** from any device. An optional account label distinguishes accounts with the same name, for example by organisation. Codex shows a device link and code. Claude opens its OAuth approval page with PKCE; paste the returned authorization code into Setup. The token printed by `claude setup-token` remains a fallback in the same field. OpenCode API-key accounts carry their provider (for example, `deepseek`), are created from a pasted key without a login flow, and can replace their provider or key from the account row. An OpenCode tier candidate with no account runs on OpenCode's own login, and is skipped when that login has no key for the model's provider (no `DEEPSEEK_API_KEY` in the daemon's environment and no `opencode auth login` entry), because opencode then fails its first request with a bare "Unexpected server error"; give the candidate an OpenCode account to use it. A tier candidate offers only accounts for its selected harness; the Claude-only orchestrator remains separate. **Machine login** remains the default. An orchestrator configured with a Claude OAuth account starts on the first other logged-in Claude OAuth account when its configured account is exhausted or its usage reaches the effective threshold after the per-session reserve for sessions already running on that account. When a Codex session ends on Codex's "You've hit your usage limit" message, its account is marked exhausted, or Codex itself when it runs on its own login, until the reset time the message names (one hour when it names none), dispatches skip it until then, and Chat says so once. A session that ends on a rejected login is treated as a token rollover first: the daemon reads the structured auth signal, refreshes the account and resumes the same native session with a short continue prompt, so a refresh mid-run does not cost the work; when the stored token is the one that was just rejected, the refresh is forced even with hours left on it. A review session re-runs its round instead, without spending one, on whichever usable critic candidate the tier picks again, which may be another account. A stop you or the orchestrator ask for wins over the resume. A 401 merely quoted in a session's own output no longer parks anything. Only a rejected refresh, or a resumed session rejected again (one resume per session, remembered across a daemon restart), parks the account: it sends one notice naming it and asking for a re-login, and the hold does not lift on its own, only a successful login or verify of that account clears it. That task is then re-dispatched on the next usable candidate for its work (a forced, tierless task stays on its own CLI and takes that CLI's next usable account; a critic continues the same review round rather than starting a new one), and Chat says so; only when nothing is left usable does the task wait, with a notice naming the harness and its reset — unless it is a forced, tierless task whose own accounts are exhausted while the CLI itself is still usable, which starts on that CLI's own login only without a repository model filter; a forced task whose whole CLI is held still waits. A session stopped on purpose, or one whose batch was abandoned or merged meanwhile, is left to its normal settle instead of being re-dispatched. Expiring Claude OAuth access tokens are refreshed before a worker or orchestrator starts as soon as less than two hours remain, so a session begins with at least that much of its token left. A running orchestrator session picks a rollover up without losing the thread: when its account was refreshed or logged in again since the session started, or its token is inside that window, the daemon ends the process and resumes the same native session on the account's current token, keeping the conversation and any open question; this same-session continuation bypasses the usage gate. Only a refresh that is rejected, or a resumed session rejected again, shows the "not logged in" line and asks you to log the account in from Setup. Each Claude OAuth account also shows a usage line with its session, weekly and per-model percentages and their reset times; it refreshes on its own while Setup is open.

**Add repository** is shown at once when no repository is registered yet; once one exists it sits behind an **Add repository** button at the top right of the Repositories section (Cancel or a successful add hides the form again, and the button is disabled while a row is being edited). The form takes a path (typed or through Browse), an id, a base branch, a merge mode, a batch approver, a worker limit (1–16, checked as you type), review rounds (0–5, default 2), an optional verify command, an optional review command and an optional setup command.

- **Base branch** is where batches are cut from and merged into. It defaults to the branch checked out when you add the repository.
- **Merge mode** is `local-merge` (the daemon merges the batch branch into the base branch in its persistent base worktree, falling back to your checkout only when it is already on that branch) or `gitlab-mr` (it pushes the branch and opens a merge request with `glab`; after you merge it on GitLab, the watcher records it within about two minutes, or you can press Mark merged to record it manually). A push or `glab` failure fails the review request with the error, and the batch stays open.
- **Batch approver** is `user` (default: a finished batch waits for your Merge or Mark merged in Review) or `orchestrator` (the ready-for-review notice tells the orchestrator it may merge the batch on its own, without asking). The orchestrator value is offered only for `local-merge`; a `gitlab-mr` repository always approves with you, and the form says so. Either way the completion notice names who merged it, and the verify, overlap and in-review gates still guard every merge.
- **Verify command** runs in the bead's worktree after each worker ends, through the shell, with a 20-minute timeout; a non-zero exit or a timeout reopens the bead (see [When verification fails](batch-flow.md#when-verification-fails)).
- **Setup command** (for example `npm ci`) runs once in every new bead and batch worktree, and before a batch's first merge if it has not passed there, so commit hooks and the verify and review commands find their dependencies; with none, worktrees are created bare. A failure reopens the bead it was for (see [When the setup command fails](batch-flow.md#when-the-setup-command-fails)).

Adding a repository with a verify command, or changing its verify or setup command, probes it at once: the setup and verify commands run in a throwaway worktree at the base branch's head, and the result shows in the repository row as `probe: pass`, `fails (exit N)`, `timed out`, `could not run`, or `running`, alongside a `crashes: N` count and a **Re-probe** button. While a probe fails, dispatch to that repository is refused — the orchestrator is told the command and exit code instead of retrying — and the repository appears in the Office strip until you fix the command in Setup and press Re-probe.

Setup shows daemon start time, pid and commit. **Restart daemon** asks for confirmation, hashes the root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `packages/*/package.json`, and runs `pnpm install --frozen-lockfile` before relaunch when those inputs changed or when the startup hash was unavailable and current inputs can be read. A startup hash read failure does not stop the daemon; if the inputs still cannot be read at restart, the current daemon stays online and Setup shows the reason. The install has a five-minute bound. An install failure or a successor that exits or misses its startup deadline leaves the current daemon serving; Setup shows the reason and up to 20 output lines, and Chat gets one wake notice. Setup hides an older restart failure while a new restart is in progress, and a later successful restart clears it. On success, detached workers continue and are adopted, and this page reconnects. Daemon crashes are recorded in `~/.overseer/daemon.log`. A **Restart needed** badge in the header appears when the source `main` commit differs from the daemon commit and opens Setup.

Add stays busy until the repository list has been refetched, then confirms with "Added <id>…".

**Edit** replaces the row's cells with the form, headed with the repository it is editing. You can change the base branch, review rounds, verify command, review command, setup command, merge mode, batch approver, worker limit and model filter; the path and the id are fixed. The save notice says running workers keep their settings. A verify command change applies to the next verification (including one that runs when a worker already running ends); clearing it means no verification runs. A review command change is used before the next batch review request; clearing it disables the suite. The model filter offers harness, account and model checkboxes, previews the remaining chore, standard and hard candidates, and applies to future dispatches; clearing all selections restores global routing. Missing models and deleted accounts remain visible until removed, and failed option loads or saves keep the selection. The orchestrator is told about verify, review or setup changes too; a change to the batch approver is read from `list_repos`.

**Remove** asks first and lists what goes and what stays. It deletes Overseer's worktrees for the repository (batch and bead), its batch and task rows, and its worker sessions with their recorded cost. It does **not** delete the repository, its `.beads/` data, or any branch: every `feature/*` and `bead/*` branch stays where it is, because a batch in review or an open bead may hold commits that landed nowhere else. The confirmation names the unfinished batches by their real status, and the status line afterwards lists the branches that were kept. A repository with running sessions is refused — stop its workers first.

## Models and review

A repository model filter restricts the global worker tier candidates by harness, model and account before routing and price sorting; it is not a separate tier table. Each non-empty list is an allow-list, empty lists leave that field unrestricted, and an account allow-list excludes machine login. All worker retries use the current filter, including review-findings and exhausted-account retries. A forced harness outside the filter is refused. If no allowed candidate is usable, dispatch is refused with the reason and the task waits; a filtered repository never uses the degraded CLI-default or machine-login fallback. Critics and their retries keep the global review tiers and are not filtered.

Setup → **Models** sets the orchestrator's model, effort and an optional prompt override, plus four tiers of worker models — `chore`, `standard`, `hard` and `critic` — each a list of harness+model candidates (for `hard`, the critic tiers and every re-dispatch a preference order; for the first dispatch of a `chore` or `standard` task a pool from which the usable candidate with the lowest models.dev input price is taken, unpriced models last and ties in list order, falling back to list order, and logging so, while no catalog copy has been read or fetched yet), an optional fifth tier `critic-chore` for a cheaper review of chore beads, and a deny list (models refused everywhere, `gpt-6-astra` by default). Codex tier candidates can choose `ultra` for `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6-sol`, `gpt-5.6-sol`, `gpt-5.6-terra` and custom model ids; `gpt-6-luna`, `gpt-5.6-luna`, `gpt-5.5`, Claude, OpenCode and the Claude-only orchestrator do not offer it. Out of the box: `chore` → Luna, `standard` → Terra, `hard` → Sol (Codex models, Claude as fallback), `critic` → Fable (Claude), and `critic-chore` unset. `spawn_worker` resolves a tier to a harness and model with `resolveTier`, skipping denied models, candidates whose CLI is not installed, and Claude OAuth accounts whose effective threshold is reached after reserving for other running sessions on the account, or that have an unexpired exhaustion handoff, then moving up a tier after a failed attempt. Models are picked from a list per harness, with a custom entry for anything else; an empty model keeps that CLI's default. To force a harness, pass `harness` without `tier` to `spawn_worker`: it runs on the first usable candidate of that CLI in the standard, chore or hard tier (a forced OpenCode harness runs on OpenCode's own default only when there is none), so it records a model and, when one is configured, an account — a forced `claude` worker needs an account to reach the plugin MCP servers (Figma) that Claude Code loads only for an account; without a repository model filter, with no usable candidate — including one whose account has no authorization yet, or one whose stored Claude token can no longer be refreshed — it keeps a retry's pinned model (else the CLI's default) and any account it can still use, otherwise falling back to that CLI's own login, a degraded session rather than a failed one. To force a harness at a tier's strength, pass both `harness` and `tier`: it runs on that tier's candidate for that CLI, with its model, effort and account, and when the tier has no usable candidate for that CLI the dispatch is refused with the reason (for example `no usable claude candidate in tier hard`), never moved to another harness or tier. Every automatic retry of such a task, and a Re-dispatch from the Board, keeps both the harness and the tier, across a daemon restart too. A review retry from a harness-only dispatch keeps that harness and its recorded model, and reuses its recorded account while the account remains usable; without a repository model filter, a Claude grant that can no longer be refreshed falls back to the harness's next usable candidate, then to the CLI's own login. A retry forced with both a harness and a tier resolves among that tier's candidates for the same harness, with no step-up, and is refused if none is usable. A tier-only retry uses normal tier routing. An exhausted-account retry stays on the recorded forced route: a harness-only dispatch takes that CLI's next usable candidate and account, a harness-plus-tier dispatch stays within that tier on the same harness, and a tier-only dispatch uses normal tier routing. An automatic retry also treats the harness whose latest session for that task hung (stopped for inactivity) or failed to start as unusable, moving to the next candidate and, when none is left, refusing and waiting for you instead of reusing it. A task that runs a server, a daemon or a browser (a dev server, a preview, Playwright, evidence capture) is dispatched with `needs_server: true`, because OpenCode cannot keep such a process alive — its shell tool reaps a backgrounded start and blocks for good on a detached one. With that flag every OpenCode candidate is skipped, and an OpenCode harness forced with or without a tier is refused with that reason rather than started, which otherwise costs a silent round and leaves a listening server behind. The flag stays with the task, so later automatic retries of it skip OpenCode too.

When a repository's **review rounds** (Setup, per repository, default 2) is above 0, a bead that passes verification does not land straight away: a critic session, always on a different model than the worker that wrote the change, reviews the branch's diff and either passes it — the bead lands — or sends it back to a worker with its findings for another round. Only a `[must]` finding sends it back: a round whose findings are all `[should]` lands the bead like a pass, with the findings in the bead's notes under `Review findings landed with (round N)` and in the landing notice (also when bd failed to record the close and Retry close or a restart records it later), so the orchestrator can carry them into the batch's review note. The diff is the change under review: when the branch merged its base in, it is diffed against what it merged in rather than against the base branch, so the review is about the resolution and not about everything the merge carried along. When even that diff is larger than the critic's CLI accepts, Overseer shortens the prompt in steps instead of sending an input the CLI refuses: the diff becomes the list of changed files, then the earlier rounds' context goes, then that file list itself is cut, and only in the last resort the task description, which carries what the review is judged against — its place is then taken by a notice that those criteria are unavailable, asking the critic to report that rather than judge against criteria it cannot read. The instructions to report a verdict through `submit_review` are never cut, so the critic still reports one, it is told which of those parts are missing and how to read the change in its worktree, and the measured size, the limit, the refs and everything left out are recorded in the bead's notes and in Chat. The card reads **Reviewing** while this runs, and the orchestrator is not involved unless the last round still has a `[must]` finding, in which case the bead goes **Awaiting decision**, Chat gets a notice with the findings, and the card's pane offers Land anyway alongside Re-dispatch. Review rounds is a cap, not a count: the tier the bead was dispatched with decides how many rounds it gets and which critic tier runs each one. A chore bead gets one round, on the optional `critic-chore` tier when it is configured, otherwise on `critic`. A standard bead (and a forced harness without a tier) gets round 1 on `critic-chore` (else `critic`), and round 2 on `critic` only when round 1 had a `[must]` finding or its diff is over 400 changed lines, measured once when the review starts and recorded in the bead's notes; a diff that large gets its second round even when round 1 passed or found only `[should]` items. A hard bead gets every round up to the cap, all on `critic`. A second or later round prefers a different critic model than the round before. Setting review rounds to 0 disables the round for that repository. A critic reports its verdict through the `overseer` MCP server, which reaches Claude, OpenCode and Codex critics alike.

## When the daemon is unreachable

If the event socket closes or a request cannot reach the daemon, a banner reads "Daemon unreachable, retrying…". Elapsed times stop, the rail mascot shows its idle pose in grayscale, and `/api/health` is polled with backoff (1, 2, 4, then every 5 s). Whatever was loaded stays on screen and is labelled as the last known state; nothing is blanked.

Actions that write are disabled while the banner is up, in Review (Merge / Mark merged, Reject, Abandon) and in the Board's card pane (Stop worker, Retry verification, Re-dispatch, Close bead, Retry close), under "The daemon is unreachable: nothing is sent and nothing is queued." Nothing is queued for later: a click during an outage is not sent. Review's rejection note and Chat's draft are kept, and Chat's Send is disabled rather than failing.

When the daemon answers again, or the socket reconnects, repositories, status, doctor, costs, the board and the chat thread are all refetched — a daemon restart needs no page reload, and neither does a page opened while the daemon is still booting.

An error the daemon itself answered — a 400, or a 500 from one endpoint — is not an outage: the shell stays online and shows "Could not load /api/<path>: <reason>" until that endpoint loads again.

## Configuration

Most settings are environment variables read by `packages/daemon/src/config.ts` (and the web settings plus `OVERSEER_PORT` for its API proxy by `packages/web/vite.config.ts`). The orchestrator's model, effort and prompt override, the four tier candidate lists and the deny list are not: they live in the database's `settings` table and are edited in Setup → Models. Each repository's `verify_command`, `review_command`, `setup_command` `review_rounds` and `model_filter` (stored on the database repo row) are repository settings edited in Setup → Repositories.

All of these can go in a `.env` file at the repository root (copy `.env.example`; the file is git-ignored). Both the daemon and the web server read it at start, and a variable already set in the shell takes precedence.

| Variable | Default | Purpose |
|---|---|---|
| `OVERSEER_PORT` | `4400` | daemon port |
| `OVERSEER_WEB_PORT` | `5173` | web server port |
| `OVERSEER_DATA_DIR` | `~/.overseer` | database, worktrees, orchestrator working dir, `sessions/` logs, `reports/` nightly counts, `daemon.log` |
| `OVERSEER_PROMPTS_DIR` | `packages/daemon/prompts` | orchestrator and worker prompts |
| `OVERSEER_BD` | `bd` | beads binary |
| `OVERSEER_CLAUDE` | `claude` | Claude Code binary |
| `OVERSEER_CODEX` | `codex` | Codex binary |
| `OVERSEER_OPENCODE` | `opencode` | OpenCode binary |
| `OVERSEER_GLAB` | `glab` | glab binary |
| `OVERSEER_PUSH_SUBJECT` | `mailto:overseer@example.com` | VAPID subject sent with push notifications; Apple's service refuses a `localhost` address |
| `OVERSEER_WEB_HOSTS` | (none) | comma-separated hostnames the web server accepts besides localhost, e.g. your Tailscale `*.ts.net` name for the phone (read by `packages/web/vite.config.ts`, not the daemon) |
| `OVERSEER_ORCHESTRATOR_IDLE_MIN` | `30` | minutes of inactivity after which the next message starts a fresh orchestrator session |
| `OVERSEER_STALL_MIN` | `15` | minutes of silence after which a running worker or critic is reported as stalled; `0` starts no sweep |
| `OVERSEER_IDLE_END_MIN` | `3` | minutes a worker is left idling after a turn end with a non-empty final message before the session is ended cleanly; `0` starts no sweep |
| `OVERSEER_REAP_MIN` | `5` | minutes between orphan-reaper passes; `0` starts no reaper |
| `OVERSEER_RETENTION_DAYS` | `14` | days after a session ends before its events and session log are deleted; the session row, cost and token counts stay |
| `OVERSEER_USAGE_THRESHOLD` | `95` | Claude OAuth usage threshold, reduced by the per-session reserve for each other running session on the account (the session being resumed is excluded) and floored at half this value |
| `OVERSEER_USAGE_RESERVE_PER_SESSION` | `2` | Percentage points to reserve per other running Claude OAuth session; blank, negative or non-finite values fall back to 2, and 0 is valid |
