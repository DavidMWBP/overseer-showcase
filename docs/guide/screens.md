# Screen guide

## The Board

- **Activity strip**, sticky at the top: at most three workers, longest running first, with an "and N more running" line below. Each row shows its elapsed time and its cost once the session has reported one. A card whose worker has exited but whose bead has not settled reads "settling…". "No workers running." when there are none. A small "refreshing…" note appears once a board fetch has been in flight for 400 ms.
- **Per repository**: a header with the base branch, then the live batch rows (title, branch → base, beads done/total, cost, status chip), then a collapsed "n finished batches" group (the newest 20; a row opens that batch in Review).
- **Six columns**: Ready, Blocked, Running, Verifying, Review, Done, each with its own hue on the header rule and on the cards' left rule. Below 1400 px they wrap to two rows of three. Batches in review appear as a dashed card in the Review column — there is no seventh column for them.
- **Cards** are two lines: the title, cut short with an ellipsis, and the bead id on the title line; then one row with a coloured state pill (Ready, Blocked, Running with a pulsing dot, settling…, Verifying, Reviewing, Review, Needs you, Failed, Done, Verified, Closed, Abandoned), the `<harness> · <model>` pill with the tier and selected account in its hover text, and the elapsed time (or "last run" on a waiting card). A card with a background action running carries another chip that reads the action in progress (Merging…, Retrying…, and so on). On a narrow card, a waiting card hides its whole "last run" text before the agent pill gives way; running and verifying elapsed text stay until the existing narrowest-card rule. The state pill and the id always show whole. Branch, batch, cost, tier, the verified, from bd, closed and abandoned flags and, while the bead runs or verifies, the account are in the card pane.
- **Done** shows the newest six cards with a "Show n more" toggle, and hides closed beads Overseer never handled.
- **Cards from bd.** A bead that was already in the repository's bd database when you registered it lists "from bd" under Flags in its pane; Overseer has no batch, branch or session for it, so the only action on it is Close bead, and only while it sits in Ready or Blocked. Its pane says so and, there, points you at Chat if you do want it worked on.
- **Card pane.** Clicking a card (or pressing Enter on it) opens a pane with a sticky header: the bead id and close button on desktop, or Back and the id on phones. It contains the title, description, History (the bead's notes, oldest first), the worker's last message and the verification output, plus the actions above, Trace, Open batch and Open in Review for a bead awaiting review. It opens at once from the card's own data and fills in when the detail arrives. The open card lives in the URL hash as `#board/<bead id>`, so a reload reopens it. Escape closes it.

The board is fetched once and refreshed on socket events — the UI never polls. Socket changes during an in-flight request coalesce into one fresh follow-up after the current response lands, so a slow first response can still update the screen. While a refresh is in flight the previous board stays complete and every button stays enabled; only before the first response does the board shimmer in the shape of its arrived activity line, repository header, two live batch rows, finished-batches disclosure, column tabs and two cards per column. The Office needs-you strip and the Plans list, a plan's own page, Review's list and detail panes, and a review batch's detail in the Office drawer shimmer while their first fetch is in flight; the strip's placeholder mirrors the Plans row (icon, title, one sub line) and then as many item rows, each in the same card box as the row it stands in for, as the strip showed the last time it loaded in this browser (one on a first visit, none when it last had none), and the Office room objects and the phone count row show no number until the data they count has arrived (no note, no folders and a bare whiteboard; the row shimmers), never a 0 they do not know yet; once the data lands, an empty strip shows no item rows and the Plans row stays available. If a first detail fetch fails, the shimmer stops and an error line stands on its own; a failed refetch keeps the detail under its warning line. Setup does the same while its own data is in flight: the Models forms, the account rows and each row’s usage line, and the Browse dialog’s folder list, shimmer in the shape of what arrives, so nothing jumps when it lands. The rail’s repo chips do the same for their cost: the chip and its repo name are there with the repo list, and the cost beside the name reserves the width of the longest value it can show, so the phone header that holds those chips does not grow when the totals land.

The Board placeholder uses the same worst-case title, branch, cost, progress and status boxes as the arrived rows, so a first response does not move the fixed board blocks. A batch title and a branch name both wrap, so the placeholder text is as long as the longest title and branch a batch carries; a row with the longest title arrives at exactly the reserved height, and a shorter one leaves a little of it unused.

## The Office

Office is the default view and first phone tab. Its needs-you strip sits above the room, with a Plans row that opens every plan; the item rows are hidden when the list is empty. It shows at most 3 item rows on a phone and 6 otherwise, then a "+N more" row naming how many are hidden; that row expands the list in place and becomes "Show fewer" at its end, which collapses it again. The expanded list is not kept: a reload or a return to Office shows the capped list. The counts live in the room as objects, with no pills over it: a yellow sticky note on the edge of the orchestrator's monitor with the open-question count in marker ("3?"), which flutters in when the first question arrives and peels off when the last is answered; one manila folder per batch in review on the meeting table, counting every repository's, including a batch held behind another and one the orchestrator may merge, which the Review tab badge leaves out (exact to four, then a stack with a numbered note), each batch keeping its seat while it stays and folders sliding on and off, so one batch leaving as another enters swaps that seat's folder, and each stack folder the count adds or takes away past four slides on or off the same way while the numbered note pops its new number; and a six-column kanban whiteboard on the right wall in the Board's order and colours, hung low just left of the door so the whole board, every header and count included, is in the first view at 1280 × 800, with each column's count in its header in 15 px marker digits, sheared onto the wall like the column labels so they read at 1280 × 800 without hovering, and one note per task up to ten. The whiteboard's Done column counts only tasks closed since local midnight and is labelled Done today, while the Board keeps every done task. A new task's note pops in and a task that changes column sends its note across. A count past 99 reads 99+. The note opens Chat, the table opens Review and the whole whiteboard is one button that opens Board; each is reachable by Tab in that order, shows a focus ring and a chip naming it (the chip sits next to the part of its object the room shows and stays inside the room after a pan or resize), shows the pointer cursor and a hover highlight under the mouse (a character standing in front of an object takes the hover, as it takes the click), and its accessible name carries the count ("Open Chat, 3 questions", "Open Review, 2 batches in review", "Open Board, Ready: 4, Blocked: 1, …" with each Office column and its current label, including Done today). On a phone the objects are too small to tap, so a slim row of 44 px tall buttons under the room (each at least 44 px wide on a touch screen, whether it reads 0 or three digits) shows an icon and the number for the note, the folders and each Board column, dims a zero, and opens the same places. A question row in the Needs strip selects and focuses its answer in the docked Chat, or opens Chat with the question selected and focused when the dock is absent. The Office room draws running sessions as pixel-art characters on an isometric floor plan instead of listing them. One character appears per running session — an orchestrator, a worker or a critic — and takes the first free of the 12 pod desks, then the two QA desks, then the coffee machine, the fridge and the sofa, then 20 standing spots in rows along the two back walls, kept clear of the corner itself so a 1440 x 900 screen shows every head (a character past the last row spot shares it). A desk is assigned the first time a session appears, so a character does not move when another one arrives or leaves; the orchestrator has its own desk, a review session sits at the first free seat of the meeting table (once all four seats are taken it follows the same path from the first free pod desk) and is drawn differently from a worker, and every character carries a `harness · model · bead id` label, where the model is the one the session is actually running — the id its CLI resolved once it reports one, otherwise the configured model, and no model segment at all when neither is known. Labels are drawn above the room and moved apart when they would collide, each keeping a line back to its character; a label only moves to a spot where that line crosses no other label, so all three fields stay readable at every window width outside the phone layout and it is always clear which character a label belongs to. On a phone the labels give way to one small badge above each character's head and speech bubble, laid out by the same rules so no two overlap: its colour is the repository (in the order the repositories are listed, the first blue, the second green, then purple, red, teal, orange and pink), its two letters are the harness (`CL` Claude, `CX` Codex, `OC` OpenCode), a review session's badge wears a white ring, the orchestrator's is a gold pill, and an unknown harness or repository reads `?` on grey; every mark is at least 4.5:1 on its fill. For stills, open the page with `?capture=1` (for example `/?capture=1#office`): the room then draws no labels and no phone badges, while the characters, bubbles and animations stay and each character's button keeps its name. Tapping a character or its badge, or Enter or Space on its button, opens one card from the bottom of the screen with the harness, model, task id, batch title, repository, role and state, and a link that does what a desktop click on the character does (the task pane, or Chat for the orchestrator). On a touch screen each character and each badge answers a tap anywhere in a 44 x 44 px square about its centre, though neither looks any bigger; at the edge of the room the square moves inward instead of being cut off, so it stays whole; where two of those squares overlap, the character or badge whose centre is nearest the tap wins, a character still wins over a room object it stands in front of, and a tap on empty floor opens nothing. A tap outside the card, its close button or Escape closes it and returns focus to the matching character button; tapping another character switches the card and its focus return target. When the session ends, the card closes and focus moves to the room stage. The card follows session updates while open. A key under the room names the orchestrator's gold pill while the orchestrator is in the room, each repository colour and harness mark present, plus the grey `?` when one is shown (an orchestrator with an unknown harness is covered by that entry), wraps onto more lines instead of scrolling sideways so every entry stays visible at 360 px, and is absent with nobody in the room; on a phone each character button's accessible name reads harness, model, `task <id>` and `repository <name>`, with `none` for either the session lacks (the orchestrator adds its role). A character that has shown no sign of activity for longer than the stall threshold wears a clock instead of its usual effect and its sprite dims, with its tooltip and accessible name reading `stalled since HH:MM` in local time; the look clears when the session records its next event, and a stalled worker's desk dims too. The QA wall screen runs its tests-running loop only while a task is being verified. Night follows the 20:00–07:00 local schedule with one-hour fades from 19:30 to 20:30 and 06:30 to 07:30; the room applies that night share through one scene colour matrix and night-sky windows, and uses one shared smooth radial texture for its lights. At night the main floor, the QA corner and the meeting room share one dark base (a night floor grade brings the two glass rooms' lighter floors to the main carpet's tone), so the lamps do the lighting: each ceiling lamp and floor lamp throws a warm pool on the floor. By day every light is off: no lamp halo, floor or glass pool and no monitor or QA screen glow, and each fades in with the evening night share to its night strength. Three room masks keep floor pools inside main (including the kitchen and lounge), the QA corner and the meeting room, while the small sconce halos stay on their back walls. Ceiling lamp halos and pools and the glass-room pools use smaller, lower-alpha profiles. A front-row monitor and each QA desk's screens are black (turned off) by day and night while nobody has arrived at their seat, and show their screen again once someone sits there in any state; the monitor backs on the back-row desks and the lead desk show no screen and are unchanged. A desk monitor's blue glow and lit overlay, and each QA desk's screen glow and lit screens, require the working or verifying agent to have arrived at the seat; the screen overlays show at 0.6 of the night share, so their rim reads as a soft edge. The lighting refreshes once a minute while the tab and Office view are visible. On a desktop the pointer turns to a hand over a character a click opens, and that character draws brighter; the highlight does not move or resize it or animate, holds still while you drag the room, and goes when the pointer leaves the room or the character does. Clicking a character opens that task in the same side pane the Board shows, sliding out over the room without navigating away; closing it returns focus to the character button that opened it, or to the room stage if its session has ended. The orchestrator has no task of its own, so clicking its character closes any open side pane, focuses the docked Chat column's composer and scrolls the thread to its latest message while the column is visible; otherwise it opens Chat, and the tooltip and accessible name say which action will happen. Open batch switches the task pane to that batch's panel in place and keeps the view on Office. With nothing running, the room is empty with a one-line note, shown only once a snapshot has arrived and named no sessions. On wide desktop screens, Chat docks to the right of the room once the room is at least 640 px wide and the measured content width is at least 380 px wider than it, and the dock stays mounted under the fixed task pane, which overlays Chat without changing the room width. When the daemon is offline, the room dims and its stage and dock fit below the warning banner without changing the online layout. The phone bar keeps five bottom tabs; Usage, Discussions and Evidence stay in the desktop Rail and Setup → General links to Usage, Discussions and Evidence on phones. `#office` opens the room directly, and the old `#needs` hash redirects there.

The office reads the same `/api/events` socket as the rest of the app, so it opens no second connection. A character walks in and out, the animation pauses while the tab is hidden, and it stands still when the system asks for reduced motion. Arrival changes the local pose only: a `walking_in` character is neutral at its desk until the feed reports `working`, which alone shows the typing effect. The room stays mounted while another view shows, so its characters and desks survive the switch: coming back shows them at their desks rather than walking in again, a session that ended while you were away walks out then and one that started walks in. When the socket is lost the room keeps its last-known characters, dimmed and standing still, with a note that activity is unavailable and reconnecting; that dimmed presentation stays until the snapshot the daemon sends on the next connect replaces the set, so the held set is never read as the current one in the gap right after a reconnect. Parts of the Office code are ported from [Claude-Office](https://github.com/W17ant/Claude-Office) under its MIT licence, kept in `packages/web/src/office/LICENSE.txt`; none of its art ships.

The room is drawn with PixiJS in layout 2: three desk pods of four worker seats, the back row facing the camera and the front row with its back to it, the orchestrator's own desk in the front middle of the work floor, clear of the i = 12 glass and the lounge rug, with a monstera at its front-left, so it reads as a workplace and the front floor is not empty, a glass-walled QA corner with two QA desks and a QA wall screen, a meeting room with a four-seat table (the glass partitions stand 2.3 units tall, about head height, with clear panes, so both rooms read through them), and a kitchen and lounge whose coffee machine, fridge and sofa are the standing errand spots, with the blocked spots by the left windows. A character on an errand or back-wall row spot stands, and does not type, even while its session works. There is no renderer setting: an earlier version's per-browser choice (`overseer.officeRenderer` in localStorage) is removed when the Office loads, so a stored `classic` or `pixi` changes nothing. Labels are drawn below each character's feet first. Its stage box keeps the 1680×1056 aspect and current measured size. On desktop (768 px and up), let s1 = max(1, round(stageWidthCss / 1680)) and t = min(s1, max(1, fit)), where fit is the largest CSS scale that keeps the question note, folders, whiteboard and whole meeting table 8 px inside the stage. The world uses the whole device-pixel scale k = max(1, floor(t × dpr)) device pixels per art pixel (CSS scale k / dpr); desktop never drops below one device pixel per art pixel and has no fractional fit fallback. Below 768 px, the phone band keeps its current formula, k = max(1, round(stageWidthCss / 1680 × dpr)) and CSS scale k / dpr, zooming out to fit the four objects when needed. The initial desktop view keeps the question note, folders, whiteboard and whole meeting table 8 px inside when they fit; among those views it shows the most floor, including the QA corner, and the least black outside the room. When they do not fit, it keeps the question note and folders in view first, then shows as much of the whiteboard as they allow; among views that preserve that priority, it shows the most floor and least black. Whatever does not fit is reached by dragging. Phone framing stays as it is: on each overflowing axis it starts with p(6, H / 2) at the box centre and moves the least distance needed to keep the note, folders, whiteboard and table in view as they fit. The view stays clamped to the world edges, and an axis whose world fits is centred as a whole. Resize preserves the world point at the box centre while that axis still overflows and the edges allow it, with the same shift for the room objects; a pan is the user's and is not shifted. The PixelLab art is under `packages/web/public/office/pixi/`: `characters.png` and `characters.json`, `room/layout2-day.png` and `room/layout2-night-windows.png`, furniture in `furniture/`, and glass segments in `glass/`. `characters/SOURCE.md`, `furniture/SOURCE.md`, and `room/SOURCE.md` record the sources and placements, including the glass segments. Use `.claude/skills/pixellab/SKILL.md` for generated or edited Office art, and record each PixelLab asset source in a neighboring sidecar. `.claude/skills/office-critic/SKILL.md` captures the room with `pnpm --filter @overseer/web run test:office-critic-capture`, grades it for lighting, layout, crispness, consistency and phone, and with `/office-critic fix` loops fix, capture and critique until no `must` or `should` finding is left and the score reaches the threshold. `assets.ts` loads each texture with nearest-neighbour sampling; a character with missing atlas keys uses `charCanvas` only for that character, and a missing furniture or glass texture keeps that piece’s Graphics fallback. Glyph-atlas bubbles sit above characters: `test`, `✎`, `z z` and `★`; `?`, `!` and `✓` badges take precedence. Stalled characters and their desks dim, failed characters tint grey and tilt, arrivals fade in over 400 ms, and departures fade near the door. Reconnecting holds the last room at half opacity with a note and frozen frames. The QA wall screen shows its idle chart, loops its tests-running frames while a task is being verified (holding the first frame under reduced motion, and holding the current frame on frozen frames, then resuming from it), and shows pass or fail for three seconds after a verification result, which is the room's verification mark; review-ready glows the In review folders green for three seconds, and merge sends 90 pieces of confetti across the room while characters hop in turn and face the board; a passing bead walks to the board and hops there. A review session at the meeting table reads an open manila folder lying in front of them, their hands on its pages, and turns a page every few seconds (each reader at its own moment); the In review folders lie along the table's middle, so both fit at once. Reduced motion removes walking, hops, confetti and page turns, and the room objects show only each change's end state. The night scene uses one shared smooth radial texture for dim, smaller room-masked pools and glows, all of which are off by day and fade in with the evening. The three room masks keep floor pools inside main (including the kitchen and lounge), the QA corner and the meeting room, and keep sconce halos on the main and QA corner back walls. The six ceiling lamps stay at their CEILING_LIGHTS anchors: four over the work floor and the lounge, one in the QA corner and one over the meeting table. Screen glows and their -lit overlays both require the working or verifying agent to have arrived, and the screen overlays show at 0.6 of the night share, and the pendant bulbs are drawn unlit by day. The lit parts of the furniture art (screens, lamps and the QA wall screen) skip the night colour matrix but keep their place in the depth order, so a character in front of a desk still covers its lit monitor. Rain is not shown because the live Office has no weather source.

## Chat

Each request that starts a batch shows an outcome chip under your message. It names the batch and its current state and updates with the Board. Selecting a chip for any batch status opens a side panel over Chat, or over the Office Chat dock, without changing the view or URL. The panel shows the batch details and visible tasks; selecting a task opens its pane there, with Back to batch returning to the list. A batch in review shows the shared review details and actions in this panel, and keeps Open in Review available. Closing the panel returns you to the same view, and switching views closes it. A request can show more than one chip. Follow-up messages that add work to an existing batch show its chip too: dispatching a worker, noting or updating one of its beads, or handing the batch over for review, rejecting, merging or abandoning it links that message to the batch as well.

Each of your messages is recorded as *seen* once the orchestrator session has been handed it — sent while a turn is running, it is handed over at once; one the daemon holds back stays unseen until a turn carries it. It is recorded as *answered* once the orchestrator replies or asks a question after seeing it; a message whose session ends without a reply stays seen, not answered.
The time under each new message shows **Waiting**, **Seen**, or **Answered** as that progress changes; older messages without tracking data show no status.

The thread loads its latest 100 messages; **Show earlier messages** prepends older pages without moving the visible message, and every socket update re-fetches the latest page and merges it into what is shown, so earlier pages you opened stay put. When you scroll up and new messages arrive, **Jump to latest** counts them and an **Unread** line marks the first arrival. Reaching the bottom within 24 px records the highest row as read and clears the button count, while the **Unread** line stays until you send a message or reload. Scrolling up again keeps the button hidden until another non-user, non-pending row arrives, and then it counts only rows since you last reached the bottom. When you come back from another view Chat opens at the latest message, with the **Unread** line above the first message that arrived while you were away. The thread is split into local days (**Today**, **Yesterday**, then a date), each row shows its local time on its first line or on hover, and consecutive replies from the same speaker within five minutes are grouped under one role label. The composer and repository selector work as follows: the line above the composer says where the message goes. With more than one repository registered you have to pick a target in this browser session before the first send — the selector shows "Pick a repository…" and names the last-used repository — and "all repos" is one of the choices. With no repository registered, Send is disabled and the line points at Setup. The labelled repository selector sits beside Send, including before the first choice when several repositories are registered. Enter sends, Shift+Enter adds a newline; the keyboard hint is hidden on touch devices. After you send, the composer stays disabled until the server acknowledges the message; the thread refresh continues in the background. During an outage or load error, the banner takes space from the conversation while the composer stays visible and the thread keeps its own scroll. On iPhone, Chat follows the visual viewport when the keyboard opens, keeping the composer above it; the bottom tab bar hides while you type, so it cannot cover the composer when Safari scrolls the page, and comes back when the keyboard closes. Returning from another app re-measures the visible screen, so a keyboard dismissed while away restores the composer and tab bar. The question card takes at most 40% of the visible screen, also with the keyboard open: a long question scrolls inside the card, keeps its line breaks, and multiple open questions appear one at a time with Previous and Next controls and a Question N of M count on a phone and on desktop, since several questions' answer boxes and buttons cannot all fit the card.

Typing `/` at the start of a draft or after whitespace opens the selected repository's command suggestions, matched by name or description; use Up/Down, Enter or Tab to choose one, or Escape to close the list.

Attach a screenshot with the paperclip button, paste it into the composer, or drag it onto the composer. You can attach up to four PNG, JPEG, WebP or GIF images, with an 8 MB limit per image; the orchestrator reads each attached image from the delivered file path. What you have typed and any attachments you have staged stay put when you visit another view and come back, and the text alone survives a page reload (kept per repository); sending clears both.

When the orchestrator calls `ask_user`, the question is pinned under the thread in a card that takes at most 40% of the visible screen, where a long question scrolls inside the card, keeps its line breaks, and has an answer box and a **Dismiss** link; multiple open questions appear one at a time with Previous and Next controls and a Question N of M count on a phone and on desktop, since the card cannot fit all of those controls. Answer it, or dismiss it to close it without an answer — the orchestrator is told not to wait. A composer draft records the open question IDs on its first keystroke, or when its first image is added if it has no text. Sending closes only those recorded questions that are still pending, so a question that arrives mid-draft keeps its answer box. Clearing the text and removing all images resets the snapshot; an older open page that sends no IDs keeps the previous close-all behavior. A send is acknowledged once its message and attachments are stored; delivery continues afterward. If delivery fails, the thread shows one system row saying the message was saved but not delivered, with the error. That row, and the not-logged-in or not-usable account line a refused send gets, carries a **Retry** button: it re-sends the stored message (its text, repository and images) in order with anything you send after it, without adding a new message. The button is disabled while the request is in flight and gone once the daemon accepts it, also after a reload; a retry that fails again adds a new row with its own Retry. Other Overseer notices have no Retry. If the daemon stops before an accepted retry finishes, startup requeues it ahead of new chat sends.

While a turn is in progress, the rail mascot's accessible label summarizes what the orchestrator is doing: which bead it is dispatching or which bd command it runs, never the full command or its output. Chat has no duplicate activity line.

Overseer's own notices appear as thin dashed rows. One written while no orchestrator session was live, or one that needs no action (an automatic re-dispatch after an exhausted account or a transient stream failure, a session resumed after its login token rolled over, a batch released from its hold, leftover processes stopped in a worktree, a review prompt reduced to fit the critic), is labelled "queued for the orchestrator's next turn" and travels at the start of the next turn; a notice that needs no action never starts a turn by itself, since every turn re-reads the whole session context.

**New session** (in the rail) ends the live orchestrator session after a confirmation. What is lost is the orchestrator's memory of the conversation: the next message starts a fresh session that is given a short preamble listing the repositories with their settings and every batch with its status, and is told to call `list_tasks` before acting. Batches, beads, worktrees and the chat thread on your screen are all unaffected. Any question still open is closed at that moment, since the session that asked it is gone. The same thing happens on its own after 30 minutes of inactivity (`OVERSEER_ORCHESTRATOR_IDLE_MIN`).

The rail shows the orchestrator's context use ("context 38%", the last request's tokens over the model's window; hover for the numbers). The pixel-art Me-1 mascot uses a full-body frame at 64 px and a head-and-shoulders frame at 32 px; low energy uses tired eyes on poses with that variant and slower frames, offline is greyed out, and reduced motion holds one frame. The mascot's accessible label announces its state, and on desktop an elapsed turn timer appears below it while a turn is in progress.

## Review

A list on the left under **Ready for you**, **Waiting**, **In progress** and **Finished** (the newest 20, collapsed by default), then any legacy per-bead items; and a pane on the right. Ready for you contains actionable review batches and matches the Review tab badge. Waiting contains held review batches; their muted rows carry a chip naming the batch they wait on, or its id when that batch is not on the board. Items assigned to the orchestrator appear under **Handled by orchestrator**. Empty groups stay hidden; the existing empty state remains when there are no batches or review tasks. The Review tab badge counts only work you can act on, includes the waiting count in its tooltip and accessible name when nonzero, and stays hidden when no work is ready.

The pane's header carries the title, branch → base, the verification state ("pass (n/m beads landed)", "failed (<bead ids>)", "verifying (<bead ids>)", "not run (no verify command configured)", "pending (no bead has landed yet)", or "nothing landed (n closed as won't do)") and the cost. Under it: the orchestrator's summary for this round, with the earlier rounds — every replaced summary and every rejection note — folded under "Earlier rounds"; the batch's beads with their outcome (landed, closed (won't do), abandoned, or their column); the actions; and the combined diff with a file list and per-file collapsibles.

Rejecting sends your note to the orchestrator and puts the batch back to work on the same branch — nothing is deleted and nothing is merged. The note you type is kept per batch for the browser session, so a trip to Chat does not lose it.

The rejection note has the same image attachment controls: use the button, paste, or drag and drop a screenshot. The limit is four PNG, JPEG, WebP or GIF images at 8 MB each, and the orchestrator reads the attached files when it receives the rejection notice.

A batch shown as **waiting** changes files that an older batch in review also changes; its Merge is disabled until that batch leaves review (see [What each action does](batch-flow.md#what-each-action-does)).

A **Finished** batch shows its merge commit (or the MR URL) or its abandon time, and no actions or diff.

Beads dispatched without a batch keep the v1 per-bead flow: they reach Review one at a time with their own Merge and Reject. This is kept for compatibility and is not what the orchestrator does by default.

## Evidence

Evidence lists folders in the configured data directory newest first, with each folder’s file count, total size and newest file time in local time. Cached summaries return immediately while their folders refresh in the background; updates appear on a subsequent load. Direct root files appear as Evidence root. Open a folder to browse its files; large folders load 100 files at a time, with **Load more files** for the next page. If a later page reports a different total or overlaps the rows already shown, the view reloads from the first page so additions or removals do not duplicate or skip files. The view shows image thumbnails, plays videos, opens HTML and text files or downloads other files; image links open the full-size file in a new tab. `#evidence` lists the folders and `#evidence/<folder>` opens a folder directly.

## Discussions

Discussions is experimental. Evals found three-model discussions produced 10 valid ideas on an open question versus 7, but blind judges ranked their answer last behind Claude plus one critic, at 1.66× the cost (evidence: `~/.overseer/evidence/discussions-eval/`).

A discussion puts one question to several agent CLIs at once and lets them read each other's answers. A request names the question, optionally a repository they may read, and up to three participants; the default is Claude, Codex and OpenCode, each on the standard tier's model for its harness, and a harness with no standard-tier model is refused by name rather than replaced. Every participant answers round 1 on its own, read-only: it may read and search the repository and the web, but never edit, commit, switch branches or push, and it runs in its own throwaway checkout that is removed when the discussion ends, so nothing it does can reach your repository; when a repository is chosen, every participant reads one base commit SHA resolved at discussion start (fetched from origin for merge-request repositories or the local base for local-merge repositories, with the resolver’s fetch fallback), and the synthesis uses that same SHA. The participant sessions stay alive between rounds, and each one's cost is recorded. From round 2 on, each participant is handed the others' latest answers verbatim, labelled by harness, and must say what it agrees with, what it disputes and why, then give its revised answer, ending with `Changed: yes` or `Changed: no`. The discussion stops after three rounds, or earlier when every participant says its answer did not change; a participant that fails is left out and its last answer is quoted as final. It then closes with a synthesis by a fresh Claude session: what they agree on, what they still disagree on, and a recommendation. A cost cap (default $5) ends a discussion that reaches it, keeping the answers so far; a synthesis that is the turn to cross it is dropped rather than stored. **Stop** ends a discussion at once and removes the checkouts.

**Discussions** is a rail entry on desktop; on a phone the tab bar stops at five tabs, so Setup → General links to the same page, and `#discussions` opens it from the address bar, even on an install with no repository yet. The form takes the question, an optional repository, the participants and the cost cap (default 5), and **Start** is disabled until the question is not empty, at least one participant is chosen and the cap is above 0. It also accepts up to four image attachments with the question, which participants see in their discussion. Under it the discussions are listed newest first with their status, the rounds so far ("round 2 of 3", marked "(in progress)" while that round still waits on a participant), their cost so far and their start time in local time. Selecting one opens the thread grouped by round (`#discussions/<id>`): every turn is labelled by its harness with the turn's cost, each participant's running total is shown against the cap, **Stop** is offered while it is running, and a completed discussion shows its synthesis with a **Send to chat** button that posts it to the orchestrator as a user message prefixed with the question. Long answers collapse behind **Show more**. The page updates live from the daemon's `discussion` socket ping.

## Usage

**Usage** reports what the sessions in a range cost and how many tokens they used. It is a rail entry on desktop; on a phone the tab bar stops at five tabs, so Setup → General has an **Open usage** link to the same view, and `#usage` opens it from the address bar.

Top to bottom: a range picker (7, 30 or 90 days, ending today, 30 by default), four summary cards (reported cost, estimated cost, tokens, sessions), the two known limits of these numbers, a stacked bar chart of cost per day by model — with a switch between reported cost, estimated cost and tokens — and breakdowns by model, account, harness and repository, each sortable by name, cost, estimate, tokens or sessions.

Reported and estimated dollars stay two separate figures and are never added together: a reported total is what the CLI billed, an estimate is that bucket's tokens priced from the models.dev catalog. Every estimated figure wears an **est.** marker whose tooltip says so. A bucket where no session reported a figure reads "unknown" rather than `$0.00`, and one where some did reads as a floor ("≥ $12.50") with the count of unpriced sessions in its tooltip; Codex reports no cost at all, so a Codex row shows its tokens and its estimate, never a bare dollar figure.

The two limits the page states next to its cards:

- An opencode or codex turn that was in progress when the daemon restarted contributes no token counts, so totals can read slightly low.
- Codex estimates are priced at the catalog's base context tier, because the codex stream carries no per-request context size: a codex session whose requests crossed ~272k tokens is estimated up to 2x low. The same caveat is behind the **est.** marker on every row that holds codex sessions, and on no other — Claude and OpenCode report their own per-response input, so their estimates use the real context tier.

On a phone the cards stack two by two, the chart scrolls sideways inside its card, and each table becomes a list, one block per row.
