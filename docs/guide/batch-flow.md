# Batch flow and lifecycle

## What Overseer does

Overseer is a local, single-user dashboard that drives coding-agent CLIs through one orchestrator. You talk to a Claude Code orchestrator session in a chat panel. Every request becomes a **batch**: one feature branch, one or more [beads](https://github.com/steveyegge/beads) tasks, and one review at the end. The orchestrator dispatches each bead to a headless worker session (Claude Code, Codex CLI or OpenCode) in its own git worktree branched off the batch branch. When a worker finishes, the daemon runs your verify command and merges that bead into the batch branch. Once every bead has landed or been closed, you review the batch once in the browser and merge it into the repository's base branch. The design is specified in [the v1 design spec](../superpowers/specs/2026-09-12-overseer-design.md) and [the batches spec](../superpowers/specs/2026-09-13-batches-speed-ui-design.md) (batches, board speed, orchestrator sessions, traces, the current UI).

## Plan gate

Instead of describing a batch straight away, tell the orchestrator to plan it out first — "let's plan it out" or similar. It calls `propose_plan` instead of creating a batch, and stops there: no branch, worktree or bead exists yet. A draft plan appears in the Office strip; its Plans row lists every plan of every status, newest first. Opening one lands on its own page at `#plan/<id>`, where step titles and dependencies edit directly, while plan titles and descriptions remain readable until you click them or their Edit control. The plan content scrolls above a normal-flow action footer, so long descriptions remain readable. Reorder with the move buttons (a move that would put a step above one it depends on is refused). Saves happen automatically as you edit. Back consumes the detail history entry and returns to the view that opened it; a cold `#plan/<id>` link falls back to Office, and approved or discarded plans remain reachable through the Plans row after you leave.

When it looks right, **Approve plan** turns it into a batch: one bead per step, in dependency order, with the same `blocked-by` relationships you set on the page, and the orchestrator is woken to dispatch them under the usual batch flow below. **Discard** throws the plan away — nothing else to clean up, since nothing else was created.

Below the plan list, **Programs** shows every open program: the batches of one multi-story request. The orchestrator opens one when you ask for three or more related stories or when one batch depends on another: it records each batch in a lane, who owns each piece of shared work, every decision you make about the program in your words and the merge order it follows, creates a dependent batch at once with its wait, and names the program in the review note. Each program lists its lanes with a card per batch (title, status, beads done out of total, and a `waits for <batch>` badge while a program wait is unreleased), the merge order as a numbered list with merged batches struck through, and its log of decisions (in your words), ownership and notes, newest first in local time. `spawn_worker` refuses a waiting batch and names its prerequisite and current status. When a prerequisite merges, the wait is stored as released and the daemon tells you that the batch can start; if the prerequisite is abandoned, the daemon asks what should happen next and leaves the wait in place. A program whose batches are all merged reads as done. Clicking a card opens the batch panel. The section refreshes on the daemon's board and chat events; with no open program it says so in one line.

## The batch flow

One request, one feature branch, one review.

- **Batch.** The orchestrator calls `create_batch` with a title. Overseer creates the branch (`feature/<slug of title>` unless the orchestrator passes a name) from the repository's base branch (in a `gitlab-mr` repository the freshly fetched `origin/<base>`, so the MR does not open already conflicting; in a `local-merge` repository the local base, since batches merge there and are never pushed, with a warning naming the count when `origin/<base>` has commits the local base lacks). When the user names another branch to stack on, only `gitlab-mr` repositories accept it: an open or review batch uses its local branch, and any other branch is fetched from `origin/<branch>`; the base is recorded on the new batch. Overseer checks the branch out in a worktree of its own under `~/.overseer/worktrees/<repo>/`. Every bead the orchestrator creates for that batch carries an `overseer:batch:<id>` label, so the batch counts a bead from the moment it exists, not from its first dispatch.
- **Workers.** Each dispatched bead gets a `bead/<id>` branch cut from the batch branch and its own worktree. A re-dispatch merges the batch branch as it is then into the bead's existing branch before the worker starts, so work a sibling landed since the branch was cut is in the new worker's tree; if that merge conflicts, no worker starts and the bead reopens naming the files, and the next re-dispatch starts the worker to rebase and resolve them. Two workers per repository by default (`worker_limit`, 1–16).
- **Worker reports.** For Figma parity or live captures, the task description lists `Parity widths: <comma list>` and, when locales matter, `Parity locales: <comma list>`. The worker reports each uploaded file first as `Evidence: <full https URL> - <caption>`; when the task says there is no upload target, each existing file outside the worktree is reported as `Evidence: <absolute path> - <caption>`. Then the worker reports every in-scope frame/width/locale as `Parity: <frame> | <width>px | <locale> | <score> | <sha>` measured after the last commit on final `HEAD`; scores may be a number, a percentage, or `<n> gaps, <number>`. A story task that names acceptance criteria ends its results block with an `AC | verdict | covering test or read-back` table, one row per criterion; verdicts are Covered, Not covered or Blocked with the reason for Blocked.
- **Integration.** When a worker ends with commits, the daemon runs the verify command in that worker's worktree. On pass it merges `bead/<id>` into the batch branch with `--no-ff`, closes the bead, removes the worktree and tells the orchestrator. On fail the bead reopens with the output in a note and the card comes back to Ready — you are not asked to review a failed bead.
- **Commits.** Workers are told to write [Conventional Commits](https://www.conventionalcommits.org/) (`<type>(<scope>): <subject>`) unless the repository's own commit rule says otherwise, and never to bypass hooks. The daemon's own merge commits follow the same form: `chore(<target branch>): merge <bead or batch id>`, with the title and `Source: <branch>` in the body. Hooks run on every merge, so a repository with commitlint or a `commit-msg` hook needs a setup command that installs their dependencies in the worktrees.
- **Notifications.** Setup → Notifications → **Enable on this device** subscribes that browser to push notifications: the orchestrator asked you a question, a batch is ready for review, a bead awaits your decision after its review rounds, and (by default, the **Also notify on every orchestrator reply** checkbox turns it off) every reply the orchestrator writes in Chat. A tap opens the matching view. Each device enables its own; the subscriptions live in the daemon's database with the VAPID key pair it generates once. Push needs a secure origin (https, or localhost), and on an iPhone the app must be added to the Home Screen and opened from there. **Send test notification** pushes to every subscribed device and lists the outcome per device (`ok`, `dropped (410)` when the push service reports the subscription dead and Overseer forgets it, or `failed (403: <the service's answer>)`); every failed send is also logged in `daemon.log` with the status code, the service's answer and the endpoint's host.
- **Review.** The batch stays open until every bead has landed or been closed. If the repository has a review command, the daemon runs it in the batch worktree at the current head, after setup when `setup_at` is null and before any push or MR; it records the command, head, exit code, duration, output tail and known test counts on the batch. A failure keeps the batch open and wakes the orchestrator with the result. The orchestrator quotes the recorded result in its review note. Without a review command, the current flow is unchanged. After a pass, the orchestrator hands the batch over with a summary; you see the combined diff (`git diff <base>...<branch>`) and decide. In `gitlab-mr` mode the request pushes the branch and opens a merge request with the summary as its description, targeted at the batch's recorded base branch. A re-request after a rejection runs the command again on a new head, but reuses a passing result already recorded for that head and command and runs a failed or timed-out one again; it updates the MR's title, description and target. If GitLab retargeted a stacked MR after its parent source branch was removed, Overseer finds it by source branch and targets it at the batch base again. Evidence a bead was asked for (screenshots, probe output) goes into the MR description or the review note, never into the repository. A repository whose **Batch approver** is `orchestrator` (Setup → Repositories) reaches the same review card and summary; the notice tells the orchestrator it may merge it without asking, while the verify, overlap and in-review gates are unchanged.

### What each action does

Every action below is acknowledged the moment you press it and runs in the background: the request returns a job id at once, the button reads the action in progress while the target's other action buttons are disabled until the action has ended (the 202 answer is not its end), the Board data carries a pending action for that batch or bead until the work ends (a badge on the card, the batch row, the Review list row and the Review header, so a reload keeps it), and the outcome arrives over the live connection when it does; the buttons come back and the badges go with the outcome, even while the Board data still shows the pending action because its next refresh hasn't arrived or failed. The outcome shows as a toast in the bottom corner: a success dismisses itself, and a failure stays until you dismiss it and carries the daemon's reason (a merge conflict, say). On phones, the message wraps beside a 44 px close target at the top-right, and a one-line toast stays compact. A second request for the same target while its action is still running is refused rather than starting another: that refusal names the running action in a toast and leaves the pending state in place until that action ends, while any other refusal restores the buttons and toasts why. In Review, Merge, Reject and Abandon close the pane at once with a line saying the action was accepted ("Merging batch … into main…"); the outcome replaces it once the action has ended, or the line goes when it fails, and a rejection note is kept until the rejection has succeeded, so a failed one can be sent again as it was.

Actions on a batch (the Review view). Merge and Abandon (and the legacy per-bead Merge, below) replace the action buttons with the question, Confirm and Cancel in the same place. The confirm takes focus and scrolls into view when needed. Cancel or Escape restores the buttons, rejection note and attachment; Reject still uses its note without a question.

- **Waiting on another batch** — when a batch reaches review and changes a file that an older batch still in review also changes, it is held: the list and the header read "waiting", the pane names that batch and the shared files, and Merge is disabled (Reject and Abandon stay). Merge the older batch first, or reject or abandon it; the held batch is released by itself, and the orchestrator is told which batch to merge first in both cases. In `gitlab-mr` mode the merge request is still opened.
- **Merge** — `local-merge`: merges the batch branch into the base branch in Overseer's persistent daemon-owned base worktree with a `chore(<base>): merge <batch id>` commit, then deletes the batch branch, its worktree and any remaining bead worktrees and branches. Your checkout is untouched when it is on another branch; when it is already on the base branch, Overseer merges there because Git permits that branch in only one worktree. The daemon base worktree must be clean. After recording the merge, Overseer runs `git push <remote> <base>` to the base branch's configured upstream or `origin`; with no configured remote it skips the push. A failure leaves the batch merged and posts one Chat notice with the first error line and `git push <remote> <base>` to run in the repo path. The next successful merge pushes all current base commits. A daemon stop or restart cancels a push that has not started, and the batch branch is not pushed in `local-merge` mode. If the merge conflicts, nothing is merged, the batch stays in review with the conflicting files recorded, and the orchestrator is told it stays in review until you reject it. `gitlab-mr`: the button reads **Mark merged** for manual recording. After the MR is merged on GitLab, the daemon watcher records it within about two minutes when the local branch head is equal to or contained in the MR head; it wakes the orchestrator once per MR merge when it finds local commits not in the MR head, and sends one wake notice if the merge path fails while recording it. For an opened MR head pipeline, in-progress statuses are ignored; failed pipelines wake with failed required-job details and a local-head SHA comparison, while successful pipelines with allowed failures and canceled pipelines each queue one quiet line. Terminal pipeline outcomes are stored per batch to prevent duplicate job reads and notices across restarts; a failed jobs read sends no notice and retries on the next poll.
- **After a merge, other batches in review with the same base are refreshed** — in both modes the merged batch's base branch is merged into each other batch in review that shares it (a `chore(<batch>): merge <base>` commit on its branch; in `gitlab-mr` mode Overseer uses the local branch when `<base>` is another open or in-review batch branch; otherwise it fetches and merges `origin/<base>`, then pushes the branch so the MR updates). If the fetched base does not contain the marked-merged batch head yet, Overseer retries for about 30 seconds and defers the refresh rather than merging a stale base while the source branch still exists. If GitLab removed the source branch after a squash or rebase merge, Overseer accepts the freshly fetched base after those retries, so even the last batch in review is refreshed without another bead or sibling merge. A clean refresh is verified again with the verify command: pass keeps it in review, fail sends it back to open with the output in its Earlier rounds and wakes the orchestrator. Without a verify command a notice says it was refreshed but not verified. A refresh that conflicts is aborted and leaves the branch untouched; the batch stays in review with the conflicting files recorded, and the orchestrator is told to reject it first if needed and add a merge bead. A batch whose worker is still running is normally refreshed just before that bead lands; after a refresh conflict, its recovery bead lands first and does not emit a duplicate conflict notice if it already contains the local parent branch for a stack or the queued merged head for another base. A stacked batch in review is also refreshed from its parent branch whenever the parent gains commits; an open stacked batch picks those commits up when its next bead worktree is cut. When a parent batch is marked merged, every open or review batch based on its branch moves to the parent's base and its MR is retargeted when present; because a squash merge leaves the parent's original commits on the stacked branch, refreshing relies on Git's merge and any conflict follows the same handling as any other refresh.
- **Reject** — takes a note (required). The batch goes back to open, the current summary and your note move to an "Earlier rounds" history, and the orchestrator is woken with the note. It adds beads to the same batch; the branch and everything on it stay.
- **Abandon** — asks in the pane first, naming the batch and branch. It stops any running workers, deletes the batch branch, the bead branches and all their worktrees, closes the batch's open beads and labels every bead of the batch `overseer:abandoned`. Nothing reaches the base branch. When a parent batch is abandoned, stacked batches stay on their existing base and the orchestrator asks whether to move each to the parent's base with `retarget_batch` or abandon it.

After a merge, an abandon or a rejection, the orchestrator gets a "Retrospective ready" notice if the batch had any signals (see Retrospectives below). Before a merge or abandon removes its worktrees, and before a bead worktree is removed after it lands or closes, Overseer runs the same scoped process cleanup used when a worker stops. A cleanup failure is logged and does not undo the landing, merge or abandon.

Actions on a bead (the Board's card pane). Which ones are offered is decided by the card's state, so a worker that has exited but whose bead has not settled yet offers nothing and reads "settling…".

- **Stop worker** — offered while the worker is running. If the worker had not committed, the bead reopens with a "Stopped by the user from the Board" note, the card goes back to Ready and the orchestrator is told not to re-dispatch it. If it had already committed, the commits stay on the branch and the bead goes on to verification as usual. Either way the stop is recorded in the bead's History, and it kills the CLI together with the processes that CLI started and left running (a dev server, a test daemon), so none of them outlives the stop.
- **Retry verification** — offered on a bead whose branch has commits and has not landed. It runs the verify command again on the existing worktree with no new worker. This is the way out when the command was wrong, not the work: fix it in Setup → Edit, then press Retry verification.
- **Re-dispatch** — starts a new worker on the same bead with the last session's harness. When a verification failed, its output travels in the new worker's instructions. This is the way out when the work was wrong.

If a Claude worker or critic reaches its account limit, Overseer stops it, holds that account until its reset time, and automatically re-dispatches the bead on another usable account; when nothing usable is left it stays Ready with an entry in the Needs strip on Office, except that a forced, tierless task whose accounts are all exhausted (its CLI itself not held) starts on that CLI's own login only without a repository model filter. Worker retries apply the current repository filter and wait with the refusal reason when no allowed candidate is usable; critics remain on global review routing.
- **Verification-only beads** — dispatch a bead that runs checks and commits nothing with `verify_only`. When one command decides pass or fail, also pass `verify_command`; a re-dispatch with `verify_only` keeps the stored command when no new `verify_command` is supplied. The daemon runs it in the bead worktree at session end and stores the command, head, exit code and parsed counts. This close applies when the bead's branch has no commits, only merge commits or an empty diff, so a re-dispatched bead whose branch carries earlier refresh merges closes the same way. A passing run closes as verified; a failing run reopens as `verify_incomplete` with its output tail, and includes a worker `Check:` PASS for the same command when present. Any worker `Check:` failure still reopens. Unless a stop wins, the daemon also evaluates an opted-in evidence report against the bead description, final message and worktree HEAD before either close. A gate failure reopens as `verify_incomplete` with every problem in the note and notice. If `verify_command` and the gate both fail, one reopen includes both reasons. Without `verify_command`, a passing set of `Check:` lines closes as worker-reported: the bead carries `overseer:worker-reported`, its close reason and Done card say "worker-reported", and the notice says it closed as worker-reported. Missing, failed, blocked, not-run or malformed checks keep their existing `verify_incomplete` reasons and reopen with the missing or offending result in the note and notice.
- **Close bead** — offered in the Ready, Blocked and verify-failed states for any bead that has not landed, including one the orchestrator created but never dispatched. It closes the bead in bd as won't do with an optional note for the orchestrator, and removes its branch and worktree. The batch stays open and counts the bead as closed, so it can still be reviewed once the rest is done; if it was the last unresolved bead, the orchestrator hands the batch over for review. Beads that were waiting on the closed one are named in the notice, and the orchestrator is told to ask you before dispatching them.
- **Retry close** — only on a card that reads landed but not closed: the work was merged into the batch branch and bd failed to record the close. The daemon also sweeps these on restart.

### When verification fails

The bead reopens, its card returns to Ready with a red left rule and a Failed state pill, and sorts to the top of its column. The pane shows the output tail, and the batch's Review header reads "failed (<bead ids>)" with a pointer to the Board. The orchestrator is woken and told which command failed on which branch.

You recover from the card: **Retry verification** if the command was wrong (fix it in Setup → Edit first), **Re-dispatch** if the work was wrong, **Close bead** if you no longer want the bead. The failure stays visible across a re-dispatch — it is the state of the branch the new worker starts on — and is only hidden while a new run is underway, when the pane heads the block "Previous verification".

A repository with no verify command configured is not a failure state: branches land unverified, and every surface says "not run (no verify command configured)" rather than "pass".

### When the setup command fails

The setup command runs in every new bead worktree before the worker starts, in the batch worktree when the batch is created, and again before a batch's first merge if it has not passed there yet. If it fails in a bead's worktree, no worker starts: the worktree is removed, the bead reopens with the output in a note, and Chat says which bead was not dispatched. If it fails in the batch worktree, the batch and its branch stay, and a bead whose branch cannot be merged there reopens with a note saying so; fix the command in Setup → Edit and press **Retry verification** on the card, which runs the setup and the merge again.

## Retrospectives

The daemon records what needed a human during a batch: rejections, reopens with their reason, re-dispatches with their instructions, beads closed as won't do, and chat messages of yours that read as corrections (a keyword match, so the orchestrator judges them). When a batch is merged, abandoned or rejected and there is at least one signal, the orchestrator gets a `Retrospective ready for batch <id>` notice and reads the record with the `batch_retrospective` tool (also `GET /api/batches/:id/retrospective`). The tool's result is compact by default so it fits a tool result: long signal text is cut and re-dispatches are grouped per bead, with `full: true` for the uncut record or `bead_id` for one bead's signals; the notice and the REST route always carry the full record. If a signal reveals a rule the prompts should carry, it opens a batch on the overseer repository titled `Lessons from <repo> <batch id>: <theme>` with one bead that appends a dated entry to `docs/lessons.md` and makes the matching prompt edit. You review that batch like any other; no prompt change is applied without it, and a lessons batch never gets a retrospective of its own. `docs/lessons.md` is the trace of every rule in the prompts that was added because a run went wrong.

The daemon also counts each day on its own clock. Once a night at 03:00 local it renders the last complete UTC day for every repository — worker sessions that ended without commits, re-dispatches and review rounds per bead, landings that kept open findings, beads closed as won't do, reported cost and cost per landing, and the disk held by orphan worktree folders git no longer lists — and writes it to `<dataDir>/reports/<date>.txt`, one file per day, so a run can be read back. It stays quiet unless something crosses a line: three or more sessions ended without commits in the day, a bead past its third re-dispatch or its review-round limit, or orphan worktree directories past a gigabyte. Then the orchestrator gets one notice naming the numbers and the beads, and nothing else. A night the daemon was down is skipped, not replayed in a burst the next morning, and a failure in the job is logged and never stops the daemon.

## How it works

- **Orchestrator.** One Claude Code session, started lazily on the first chat message, resumed by native session id across daemon restarts and resumed the same way when its account's token has rolled over (the process ends and the native session continues on the fresh token, so the conversation and open questions stay), and replaced by a fresh one after `OVERSEER_ORCHESTRATOR_IDLE_MIN` minutes of inactivity or a New session. It reaches the daemon through the MCP server at `/mcp` with thirty-two tools: `list_repos`, `list_tasks`, `bd`, `spawn_worker`, `message_worker`, `interrupt_worker`, `worker_status`, `worker_diff`, `request_merge`, `create_batch`, `list_batches`, `create_program`, `add_to_program`, `log_program_entry`, `set_merge_order`, `list_programs`, `request_batch_review`, `batch_retrospective`, `propose_plan`, `submit_review`, `accept_review`, `merge_batch`, `reject_batch`, `abandon_batch`, `retarget_batch`, `close_bead`, `retry_verification`, `start_server`, `server_logs`, `stop_server`, `list_servers`, `ask_user`. Program tools group batches into a multi-story request, record waits and notes, and set their merge order. `merge_batch`, `reject_batch`, `abandon_batch`, `close_bead` and `retry_verification` mirror the Review and Board buttons of the same name, for the orchestrator to act on the user's word in Chat instead of the user clicking them. Orchestrator and critic sessions now run without `--strict-mcp-config`, so a server in your configured scope now or later is visible to every such session with the credentials in its environment, alongside the `overseer` server; workers receive the `overseer` server too (for `start_server` and its siblings), on top of the repository's own `.mcp.json`. Claude workers and critics run with your context-mode plugin disabled (`enabledPlugins` in their `--settings`), since its per-session MCP server rescans every context-mode database once a minute and many of them at once saturate the disk; the orchestrator keeps it. Its prompt is `packages/daemon/prompts/orchestrator.md`; the workers' is `worker.md` beside it, the critic session that runs the review round below uses its own prompt, `critic.md`, and `docs/lessons.md` records why each incident-driven rule in them exists.
- **Worker CLI selection.** When adapter trouble or a long, silent check needs an explicit CLI, the orchestrator chooses one with usage headroom that fits the task and avoids the failing harness. It avoids OpenCode for long silence because that adapter ends the turn after 20 minutes; Claude is reserved for a Claude-only MCP tool such as Figma or a user rule when another CLI fits, and otherwise only when it is the sole fit, since automatic retries keep forced harnesses pinned.
- **Session-end rule.** When a worker ends: commits on the branch mean verify, then merge into the batch branch and close the bead (a bead outside a batch goes to Review instead). A failed verification or a merge conflict reopens the bead with a note, and so does a branch with no commits. A branch with no commits whose worker's final message hands the work to a background agent or promises a later result is a distinct outcome: the sentence that triggered it is recorded on the bead and re-dispatched at once on a harness this bead has not just run on, with instructions to do and commit the work in that session — a message that reports finished work with a check still running stays an ordinary no-commit reopen. So does a branch with real commits whose worktree still holds uncommitted work — a tracked file with a staged or unstaged edit, or a file never added: verification runs in that worktree and would pass on the uncommitted edit while the merge takes only the branch ref, so the bead reopens with the modified and untracked paths named in the note (a gitignored path is not work to lose, nor is what the repo's setup command left in the worktree when it was created, snapshotted on the worktree row so the subtraction still holds after a daemon restart). A notice that reports why a session failed names the account it ran on — "worker ended without commits on claude account Work: …" — or the bare harness name when the session ran on the CLI's own login, so an authentication error says which account to log in again in Setup. A branch that already had commits from an earlier run is verified even when this session added none. On daemon restart, a worker whose process is still alive is adopted and followed from its log, and the same rule runs when its turn ends. A worker that is gone reopens its bead with a "daemon restarted while the worker was running" note and the exit reason from the end of its log, rather than landing work it never finished. A harness that reports the end of a turn while its CLI lingers — Codex's `turn.completed`, OpenCode's `step_finish` with reason `stop` (intermediate steps carry `tool-calls` and do not count) — gets a five-second grace: the process tree is then killed and the turn ends normally, and once the CLI is gone, on its own or killed, anything still holding the session log is swept. Stopping a worker runs that same sweep once its CLI is gone, whatever the harness: the process tree first, then anything still holding the session log, each only when it started after the session, so what the worker started does not survive the stop. A stopped session is recorded as ended, never as failed: the kill makes the harness report the process death as an error, and the stop is marked before the signal goes out, so which of the two is seen first no longer decides what the Board and the notices say about a deliberate stop. A crash or restart skips that sweep, so the daemon also runs a reaper at startup and every `OVERSEER_REAP_MIN` minutes (default 5). It kills a process that names a worktree with no running session only when Overseer left it behind: on that periodic pass every live ancestor of that process must also name such a worktree, so an editor or shell you opened on a worktree path, whose parent is Explorer or a terminal, is never touched. At the moment a session ends the reaper runs once more, scoped to that session's worktree, without the live-ancestor guard. It still stops other processes that name the worktree in their command line or cwd, each with its process tree. A daemon descendant is a candidate only when its cwd or executable path is inside the ended worktree; text in its other arguments does not count. This keeps a server in the worktree eligible even when it remains below the CLI through the daemon, and the pass never touches another session's worktree, a primary checkout or the daemon itself. It logs each process it stops and posts a "Stopped N process(es) left running in <path>" notice, so a leaked server is visible rather than silent. A worker that leaves a dev server holding the CLI's stdio therefore cannot keep its session running with no ceiling, nor leave it running after it is stopped (2026-09-17). An OpenCode turn that prints nothing at all for 20 minutes (no line and no sub-agent activity, longer than opencode's 10-minute shell timeout cap) is ended the same way, with the silence and the last event it printed as the reason, since opencode 1.18.19 can hang on a `step_start` with no `step_finish` ever following. The same periodic pass also removes a leftover worktree folder git no longer lists once Overseer's own record says its work is done — its worktree row is closed or merged (or its batch is merged or abandoned), or it has sat there over a day with no row at all — and never a folder git still lists, one a running session sits in, or a path outside the worktrees directory.
- **Notices.** Overseer tells the orchestrator what happened in its own words in the chat thread. A notice that needs a decision — a reopened bead, a conflict, a landed or closed bead with nothing else running, a rejection — starts or resumes the session as a user message would. Purely informational ones are queued for the next turn, and the no-action kinds are queued even while a session is live, travelling as a "Since your last turn" block.
- **State.** beads owns the work (status, dependencies, `overseer:*` phase labels, the batch label); the daemon initialises it in each repository (`bd init --stealth` unless you opt into committing). SQLite owns the machinery (repos, batches, sessions, worktrees, events, chat). The daemon is the only writer of bead status and `overseer:*` labels.
- **Verification.** `verify_command` runs in the bead's worktree after the worker ends, through the shell, with a 20-minute timeout. A non-zero exit or a timeout is a failure. The repository row is read when the worker ends, so a command changed in Setup applies to the next verification, including the one for a worker running now.

## Servers a task needs

Some work needs something running: a dev server to screenshot, a preview to click through, a Playwright browser. A worker cannot keep such a process alive by itself — every CLI fails at it differently, and a process a worker starts in its own shell has stalled sessions for tens of minutes and left dev servers and browsers running for hours.

The daemon runs them instead. A worker asks for a server, gets an id back, reads its log to see when it is ready, and uses it. You do not have to do anything: the server is stopped when that worker's session ends, and one that survives a daemon restart is cleaned up at the next start. Its output is kept in `<data dir>/servers/`.
