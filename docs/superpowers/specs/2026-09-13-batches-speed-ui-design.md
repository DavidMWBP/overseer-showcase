# Feature branches, board speed, orchestrator sessions, traces, and the UI redesign

Date: 2026-09-13. Follows the v1 design in `2026-09-12-overseer-design.md`.

Sessions retain the cumulative input, output, cache-read, cache-write and reasoning token counts reported by each harness at turn end.

## Why

Feedback from the first real run (work item 9310 on acme-portal):

1. The board takes 12–30 s to load. Cause: `buildBoard` runs eleven serial `bd` calls (one `--version`, then per repo four `bd list --status X` plus one `bd ready`), each ~1 s on Windows, queued behind worker `bd` calls. `bd list` also defaults to a 50-row limit per call.
2. The chat composer gives the repo selector the flexible column and the textarea a fixed one.
3. Merge fails with "primary checkout has uncommitted changes" whenever the user has any local edit in the repo, even in unrelated files.
4. The user does not want to review every bead. All work for one request must land on one feature branch, reviewed once (as a GitLab MR when the repo uses `gitlab-mr`, in the Review view when it uses `local-merge`), and merged into the repo's base branch (`main` or `dev`).
5. There is no way to cancel work from the UI.
6. The orchestrator is one long-lived Claude session. After idle time the prompt cache is cold and every message re-reads the whole transcript.
7. Session traces exist in SQLite but are not exposed, and cost is not aggregated, so runs cannot be analysed.
8. The UI is unstyled and flat.

## Decisions

- **Every user request becomes a batch** with its own feature branch. Workers branch off the batch branch. Verified beads merge into the batch branch automatically. The user reviews the batch once. Beads without a batch keep the v1 per-bead flow (kept for compatibility, not the default).
- **Verification failure inside a batch reopens the bead** with the output in a note and notifies the orchestrator; the user is not involved.
- **Local merge no longer refuses a dirty checkout up front.** Git decides: a merge that would overwrite dirty files fails with git's own message, which the UI shows.
- **Orchestrator sessions expire after idle time** (default 30 minutes, `OVERSEER_ORCHESTRATOR_IDLE_MIN`). The next message starts a fresh session with a short handoff preamble listing every batch with its status (round 9: a preamble that listed a batch in review as "1/1 beads done" without a status read as merged to the fresh model). A "New session" button does the same on demand.
- **Chat stays focused on questions, decisions, actionable failures and completed requests.** The orchestrator searches and reads for itself first; when a search is too wide, a helper's full report reaches Chat, so the orchestrator caps it at about 100 words. It does not post progress recaps between tool calls, while the one-line note before a call expected to take over a minute remains.
- **Orchestrator and critic sessions start without `--strict-mcp-config`**, so the daemon's `overseer` server is combined with the user's configured MCP servers for the session scope; a server in that config now or later is visible to every such session together with any credentials in its environment. A critic on opencode or codex reaches the same `overseer` server through that CLI's own mechanism — an additional config file named by `OPENCODE_CONFIG` that the adapter writes per session, and a `-c mcp_servers.overseer.url` override on every codex turn — so it can end its review round with `submit_review` (`overseer_submit_review` on opencode) instead of losing the verdict. Both mechanisms add to the user's own configuration and write nothing in it. Workers receive no MCP config and already inherit the repository's `.mcp.json`.
- **Claude workers and critics run without the context-mode plugin.** Their `--settings` carries `"enabledPlugins": { "context-mode@context-mode": false }`, which overrides the user's own `enabledPlugins`, because each context-mode MCP server rescans every context-mode session database once a minute and one per headless session saturated the disk. Orchestrator and discussion sessions keep the user's plugins.
- **Traces and cost are exposed over REST**, and the daemon writes a JSON-lines log file.
- **Design direction (user choice): slate control room.** Dark slate ground, one hue per board column carried through cards, rail counts and chat notices; IBM Plex Sans for the interface, IBM Plex Mono only for identifiers (bead ids, branches, costs). The memorable element is the activity strip: live worker sessions as timelines with elapsed time and cost. The strip shows at most three workers, longest running first, with an "and N more running" line below when more are running (same rule on phone and desktop; desktop rows are one compact line each with a fixed-width bar and mono elapsed/cost columns, phone rows keep their two-line layout).

The existing `repos` table gains nullable `review_command`, edited in Setup → Repositories. `request_batch_review` runs it in the batch worktree after pending setup and before a GitLab push or MR creation. A non-zero exit stores a failed `review_check`, leaves the batch open and wakes the orchestrator with one notice naming the command, exit code and output tail; a pass continues the existing review flow. A recorded pass for the same head and command is not run again, while a changed head, a changed command, or a recorded failure or timeout gets a new run. Counts parse from Vitest's `Tests` summary or Playwright's final summary lines; unknown output keeps `counts` null. `list_batches` returns the record, and the Review header shows its command, status and counts.

`chat_batch_links (chat_id INTEGER, batch_id TEXT, created_at TEXT, PRIMARY KEY (chat_id, batch_id))` records every batch a message is acted on for: `create_batch`, a `batch_id` on `bd`/`spawn_worker`/`request_batch_review`/`reject_batch`/`merge_batch`/`retarget_batch`/`abandon_batch`, and `message_worker`/`interrupt_worker`/`close_bead`/`retry_verification`/`accept_review` plus a `bd note`/`update`/`dep add` write, whose batch comes from the bead's `overseer:batch:<id>` label; a bead with no batch records nothing, and the same pair twice is one row. Board batch rows carry `linked_chat_ids` (`BatchSummary`, sorted, `origin_chat_id` included) so Chat has one list to read.

`worktrees` gains `closed_at TEXT NULL`: set when the user closed the bead as won't do from the Board (Close bead); the bead is finished for its batch without having landed, and `BatchSummary.beads_closed` counts these apart from `beads_done`.

`worktrees` gains `batch_id TEXT NULL`. The schema helper adds missing columns with `ALTER TABLE ... ADD COLUMN` after `CREATE TABLE IF NOT EXISTS` (first migration mechanism; `PRAGMA table_info`), then runs `ADDED_INDEXES`: `CREATE INDEX IF NOT EXISTS` for `sessions(bead_id, started_at)` and `worktrees(batch_id)` (second mechanism; the `batch_id` index can only be created after the column loop added that column). The connection also sets `PRAGMA cache_size=-32768`, so the board's full scans do not spill the sessions table through SQLite's default 2 MB page cache.

A bead belongs to a batch from its creation, not from its first dispatch: the orchestrator creates beads through the MCP `bd` tool and passes the batch's `batch_id` with `bd create`; the daemon (the only writer of `overseer:*` labels) appends `--labels overseer:batch:<batch id>` to the command, after checking the batch exists in that repo and is open (`batch_id` with any other bd command is refused). The batch's beads are then the union of the worktree rows with its `batch_id` (dispatched at least once) and the beads carrying its label that were never dispatched; `beads_total`, `beads_closed` (a labelled, never-dispatched bead that is closed counts here), the card's `batch_id` (so its card sits under the batch on the Board and in the batch's bead list in Review), the "k/n beads done" of the landed and close notices, `request_batch_review` (refused while a labelled bead is still open) and Abandon (closes the labelled ones too) all read that union; `beads_done` and cost still come from the worktree rows only. Round 15: a bead the orchestrator had created for a batch and not dispatched yet was missing from the total, so the row read "1 closed of 1" beside a card of the batch still waiting in Ready, and that number is the one the orchestrator's review rule reads. `phaseOf` reads only the eight phase labels, so the batch label (same prefix) is never confused with a phase, and a phase change leaves it in place. The count in the landed and close notices runs after the merge or the close has happened, so its `bd list` is not allowed to fail them: a failing list is logged and the notice counts the dispatched beads only and says so ("k/n dispatched beads done; bd list failed, so beads never dispatched are not counted"), and nothing past the merge point of an integration throws back into the reopen handler (a failing `bd close` after the merge is logged and reported as "landed on <branch> but bd could not record it"; the row already carries `merged_at`, so the card reads `landed_unclosed` with a Retry close (`POST /api/tasks/:id/close-landed`: close in bd, phase `merged`, remove the worktree, the landed notice), the notice's hint tells the orchestrator so, and `recover()` sweeps every bead whose row says it landed on an open batch and that bd has not recorded as merged — open, or closed with its phase still `verifying`, since the landing is two bd calls (`bd close`, then the phase) and either can fail — and closes it, one `bd list` per repo (fix round 17 review: a failure of the second call left the bead closed with phase `verifying`, which the sweep skipped forever, so its worktree and branch stayed on disk and the landed notice never came) (fix round 16 review: the bead sat in Verifying with no action, Close bead refused it as busy and `request_batch_review` counted it open)) (fix round 15 review: one bd hiccup reopened a merged bead, and made a successful Close bead answer an error and skip its notice). `list_batches` degrades the same way, from the daemon's rows alone. A bead created for a batch is dispatched into it when `spawn_worker` names no batch, and refused for another batch ("was created for batch <id>; dispatch it there or create a new bead for <other>"), since the label stays and the bead would count in both. A labelled bead closed outside Overseer (a plain `bd close`, no phase label) has no card and is no member; a label naming a batch this database does not have (an earlier install whose data dir was reset, or a repo removed and registered again) is inert everywhere: its card sits under no batch, no count reads it, `spawn_worker` neither adopts it nor refuses on it, Close bead treats the bead as batchless, and the daemon logs the unknown id once (round 17). A never-dispatched bead labelled for a batch that is no longer open (merged or abandoned since) can still be closed from the Board (it was dispatchable nowhere and closable nowhere): the close notice says "its batch <id> is <status>" instead of "stays open" and wakes nobody (the status word is the one every other daemon line uses, so a batch in review reads "in review (awaiting the user's review, not merged)", not "review"; fix round 19 review NB-5), and the dispatch refusal for it names the batch's status and points to Close bead (fix round 16 review).

The program model groups batches from one multi-story request. `programs` stores the repo, title, `open|done` status, creation time and nullable source chat id. `program_batches` assigns a batch to one lane with a zero-based position, unique within that lane. `batch_waits` stores each batch's prerequisite and its durable release time; a new wait on an already merged prerequisite starts released. `program_entries` stores a `decision` verbatim, `ownership` or `note`, with its creation time and nullable source chat id. `merge_order` stores each program's ordered batch ids at zero-based positions; the store accepts only batches already linked to that program. `SCHEMA` creates these tables when opening an existing database. Orchestrator MCP tools expose `create_program(repo, title)`, `add_to_program(program_id, batch_id, lane, after_batch_id?)`, `log_program_entry(program_id, kind, text)`, `set_merge_order(program_id, batch_ids)` and `list_programs(repo, program_id?)`; waits connect only batches in the program repo and cannot create a cycle, and merge orders can name only batches in that program. The orchestrator prompt opens a program for a request of three or more related stories or any cross-batch dependency: it adds each batch to a lane, logs the owner of each piece of shared work as `ownership` and every user decision verbatim as a `decision`, sets the merge order and follows it, adds a dependent batch at once with `after_batch_id` and dispatches its beads on the release notice, and names the program in the review note.

### Git layout

- Batch branch is created in the primary repo: `git branch <branch> <base>`.
- The batch has its own worktree at `<worktreesDir>/<repo>/b<n>-<suffix>` (the batch id without the repo prefix; short on purpose: every checked-out file counts against the Windows 260-char path limit) checked out on the batch branch. All batch-side merges happen there, never in the user's checkout.
- Bead worktrees are created as today, but `-b bead/<id>` starts from the batch branch, and the worker prompt's `{{base}}` is the batch branch (so the conflict/rebase text is right).
- Integrating a bead: in the batch worktree, `git merge --no-ff bead/<id>` with a Conventional Commits message (`git/message.ts`), so a commitlint `commit-msg` hook in the managed repo accepts it: header `chore(<batch branch without feature/, lowercased, [a-z0-9-] only>): merge <id>` capped at 72 characters (the scope is truncated, never the id), blank line, then the full bead title and `Source: bead/<id>`. The message goes as one `-m` per paragraph; hooks run (no `--no-verify`). Landing a batch in `local-merge` mode uses the same shape with the base branch as scope, the batch id, its title and the review note. Conflicts → abort, record `conflict_files` on the bead worktree, reopen the bead, notify the orchestrator (same re-dispatch instructions as today).
- Batch diff for review: `git diff <base>...<branch>` in the primary repo (refs only, no checkout needed).
- Landing a batch, `local-merge`: `mergeLocal` uses Overseer's persistent base worktree when the primary checkout is on another branch, checks that worktree is clean, and detaches it after the merge so the user can check out the base branch later. When the primary checkout is already on base, it merges there because Git permits the branch in only one worktree. `gitlab-mr`: push the batch branch from the batch worktree, then update the MR the branch already has or find an open MR for the source branch and the batch's recorded base branch; create one targeting that base only when neither lookup finds one, and store `mr_url`. The batch's `mr_url` (kept across a rejection) names the MR and every update restores its target to the batch's current base. Without one, `glab mr list --source-branch` is asked for an open MR targeting the batch base first; for a stacked batch only, if that lookup misses, a source-only lookup finds an open MR that GitLab may have retargeted to the repository base after deleting the parent's source branch. That MR is retargeted to the batch base instead of creating a duplicate. A `409 Another open merge request already exists ... !<iid>` from create still falls back to `glab mr update <iid>`, so a re-request after a rejection never leaves the batch `open` with a stale description or target on GitLab. Title and description travel as `--title` and `--description-file <temp file>`, never as a shell argument: the note is markdown with pipes and backticks and can exceed the Windows command line.
- Cleanup after merge or abandon: remove batch worktree, delete batch branch, remove any remaining bead worktrees and branches. Removing a worktree also removes its `<worktreesDir>/<repo>/` folder while that folder is empty, so the per-repo folders do not outlive every batch (round 18: Remove repository says "Deleted: Overseer's worktrees for it" and empty folders were still there); that is the only place the rule lives, and Remove repository no longer rmdirs the folder itself (fix round 18 review). The `worktrees` rows stay: they keep the bead → batch link and the batch's bead count and cost, so a finished batch remains inspectable in Review ("Finished" section) and on the Board (collapsed "finished" group).

### Lifecycle

| event | v1 bead (no batch) | bead in a batch |
|---|---|---|
| worker ends, no new commits, branch has no commits ahead of its base | reopen, note, notify (wakes the orchestrator) | same |
| the same, or a branch with only merge commits or an empty diff (next row), but the worker was dispatched with `spawn_worker(verify_only: true)` | every one of the three nothing-to-land reasons takes this path, since a re-dispatched bead's branch carries the merge commits of earlier batch-branch refreshes (acme-portal-sample-046, 2026-09-26). With `verify_command`, the daemon runs the command in the bead worktree at session end and stores its command, HEAD, exit code and parsed counts. A re-dispatch with `verify_only: true` keeps the saved command when no new `verify_command` is supplied. Exit 0 closes with phase `verified`; a nonzero run reopens as `verify_incomplete`, quoting the output tail and any same-command worker `Check:` PASS. A worker `Check:` failure still reopens. Unless a stop wins, before either verify-only close the daemon checks an opted-in evidence report against the bead description, final message and worktree HEAD. A gate failure reopens as `verify_incomplete` with every problem in the note and notice; if `verify_command` and the gate both fail, one reopen includes both reasons. Without the command, at least one all-PASS `Check:` line closes with reason "worker-reported result, no commits", phase `worker-reported` (label `overseer:worker-reported`), the final message in the note, and a worker-reported notice and card state text. Matching is case-insensitive, and Markdown list markers or a bold `Check:` label are accepted. The separators around PASS may each be a hyphen-minus, en dash or em dash. The existing parser and the missing, FAIL, NOT RUN, BLOCKED or malformed `verify_incomplete` reasons are unchanged; the note and `[Overseer]` notice quote what was missing or did not pass. A no-final-message result without a command reopens as `verify_incomplete`; with a command, its run decides verification. A session with an exit reason follows the crash row below, and one lost during daemon recovery follows the lost-worker row | same close or reopen behavior; a verified close counts in `beads_closed`, adds the batch count to the notice and wakes the orchestrator unless another worker of the batch runs |
| worker ends, no new commits, branch already has commits ahead of its base | verify as if the worker had committed: the branch is what has to be verified, not this session (round 6: a re-dispatched worker that finds the earlier commit correct and adds nothing must not send the bead back to Ready with "no commits") | same, then integrate |
| Claude worker or critic emits `rate_limit_event` | stop that session, mark its account exhausted until Claude's reset (or five hours when none is supplied), reopen as a stop without a tier step-up or model-avoidance attempt, then immediately re-dispatch with the same tier, batch and instructions on a usable account; when none is usable, leave the bead Ready and post an entry in the Needs strip on Office | for a critic: bead keeps `in_progress`/`verifying`, no reopen signal emitted, review round retries on the next critic candidate; when none is usable, same as worker |
| a worker ends without commits with an exit reason (crash, not a clean end) | `classifyExit(reason, stderr)` (`lifecycle/crash.ts`) labels it `transient` (reason starts `event stream failed`), `harness_bug` (reason ends `exited with code 2` and the session's startup-only stderr, read only when it recorded no events, carries CLI usage text), or `task`; stored on `sessions.crash_class` and a `crash` batch signal. A first `transient` crash for the bead (its previous session was not transient) re-dispatches once, fresh (no resume), pinned to the same harness and model, notice "<bead> re-dispatched after a transient stream failure on <harness or harness account name> (<reason>)." and no wake; a `harness_bug` reopens as the "no commits" row above with a hint not to re-dispatch on that harness; any other case, or a second transient in a row, also falls through to that reopen | same |
| worker ends, branch has commits ahead of its base but none of them is real work | a verify-only session that did not crash takes the verify-only row above instead; otherwise reopen like "no commits", with the reason in the note and the notice: "… ended without new commits (only merge commits): …" when every commit ahead of the base is a merge (`git rev-list --no-merges <base>..HEAD` is empty), "… (empty diff): …" when `git diff --stat <base>...HEAD` is empty. "Has commits" means both hold: at least one non-merge commit not reachable from the base (the batch branch, or the repo base without a batch) and a non-empty diff against it (overseer-xen, 2026-09-14: a worker died right after `git merge main`, the merge commit counted as work, and the bead landed and closed as done with nothing in it) | same |
| worker still running when the daemon comes back (restart, crash, `tsx watch` reload) | adopted, no transition: the bead stays `in_progress`, the session `running`, and the rules above apply when its turn ends. `POST /api/daemon/restart` admits one restart (409 after that), starts one detached successor tagged with the old pid, closes every board websocket and any open MCP stream (Fastify also drops active keep-alive connections, not just idle ones) and the old Fastify server with a ten-second bound, and exits even if shutdown fails; the successor waits for that pid before opening the database or binding, then retries a busy port without a deadline and logs its pid on every failed bind. Under root `pnpm start`, the root process and Vite workspace script stay running when the daemon workspace script completes, so the same web server and proxy reconnect to the successor. The old daemon exits 0 on both paths, because a non-zero exit makes `pnpm -r --parallel start` stop the Vite sibling and the root process. A plain start (no restart-parent tag) that finds the port occupied asks `GET /api/daemon` on it: an Overseer daemon answers with its `data_dir` and `source_root`, and when both match this process the new daemon stops that one process (`taskkill /PID` without `/T`, `SIGTERM` elsewhere), logs its pid, and retries the bind until the port is free; its workers survive and are adopted. A daemon of another data dir or source checkout, or one that reports either field missing, is never stopped. Any other holder is left alone, and the start exits 1 with a line that names the holder's pid and process name (`netstat`/`tasklist` on Windows, `lsof` elsewhere). Workers are spawned detached (`spawnLines({ logFile })`: own process group, hidden window, unref'd, stdout to `<dataDir>/sessions/<session id>.log` and stderr to `.log.err`, only stdin a pipe; on Windows the detached process is `launcher.cjs`, which runs the worker with a hidden console that the worker's console children share, so none of them opens a window, and reports the worker's pid in `<log>.pid` for the session row; the worker dies with its launcher), so a daemon exit leaves them at EOF on stdin instead of with a broken stdout pipe, which is what killed them on every merge from Review while the daemon ran under `tsx watch`. The session row carries `pid` (from the spawn, before anything else), `pid_started_at`, `log_path`, `log_offset` (advanced as lines are consumed), `batch_id`, `cwd` and `harness`. `recover()` checks each running row's pid against its recorded start time (`Get-Process ... StartTime` on Windows, `ps -o lstart=` elsewhere), so a recycled pid is not adopted; a live worker with a log is followed from `log_offset` (`HarnessAdapter.adopt`), logged as "adopted worker <session> for <bead>", and ends when the harness's turn-end line arrives or the pid is gone (polled every second: claude reports a process gone without a result line as "claude exited without finishing its turn"). Stop worker and `interrupt_worker` kill an adopted session by pid (`taskkill /T` on Windows); `worker_status` reads the same fields. Orchestrator sessions are not adopted: a live one is killed as before and the next message resumes it by native session id | same |
| worker lost by a daemon crash (recovery), no new commits this session | reopen with the note "… ended without new commits: daemon restarted while the worker was running" (followed by "; the worker's log ends with: <reason>" when the log's last line is the harness's error line or stderr has a last line), session `failed`, notify (wakes), whatever the branch holds: the worker was interrupted, not finished, so an earlier commit on the branch is not verified and landed behind its back (round 7 carry-over NB-1); Retry verification and Re-dispatch stay available for it | same |
| worker ends, commits, verify pass | phase `review`, notify | merge into batch branch; `merged_at` on the worktree row (before bd is asked, so the daemon knows the bead landed whatever bd does next); close bead ("merged into <branch>"); phase `merged`; remove bead worktree; notify "<id> landed on <branch> (n/m beads done; verify command `<cmd>` passed)" or "…; not verified: no verify command configured" |
| worker ends with commits ahead of its base but its worktree still holds uncommitted work (a tracked file with a staged or unstaged edit, or a file never added) | reopen instead of verifying: `uncommittedWork` reads `git status --porcelain`, whose default output already omits ignored paths (so a gitignored evidence folder such as `.playwright-cli/` does not count) and which is run without `--untracked-files=no` (a never-added file is dropped at the merge exactly like a modified tracked file, overseer-gk52, 2026-09-17); the note names the paths grouped as modified and untracked and says they are not on `bead/<id>` and would be lost at the merge, the session is `failed`, and an `uncommitted_changes` reopen signal is recorded. | verify fail | phase `review` with fail (user may still merge) | reopen bead, note "Verification failed:\n<tail>", phase null, notify "<id> reopened: the verify command `<cmd>` failed on <bead branch>. | user Reject of a v1 bead | status `open`, phase `rejected`, note, notify "<id> rejected by the user: <note>…" (wakes; the Review acknowledgement "the orchestrator was notified" is true for v1 beads too since round 7) | n/a |

Program waits are dispatch gates: `spawn_worker` refuses a batch with any unreleased prerequisite wait and names the prerequisite and its current status. A successful local merge or a GitLab MR watcher merge stores the release on every wait for that prerequisite, then sends one wake notice per waiting batch: `[Overseer] Program <title>: batch <id> can start (<prerequisite> merged)`. Every transition above is one `bd update` (status, phase label and appended note together; the other `overseer:*` labels are removed blindly, which bd 1.2.2 accepts). A bd call costs about half a second; writes to one repo run alone and the board's `bd list` for that repo waits behind pending writes (reads run alongside each other, see Board speed); one call per transition is what keeps board builds under a second while workers move.

Notices (`notify`) carry a `wake` flag: a notice that needs a decision from the orchestrator (a reopened bead: no commits, failed verification, integration or merge conflict, failed integration or retry; a landed bead, or a bead closed as won't do by the user, when no other worker of the batch is still running; a rejected batch or v1 bead; a failed batch creation; a v1 bead entering review) starts or resumes the orchestrator when no session is live, as a user message would. Informational notices (stopped by the user, merged or abandoned by the user, re-dispatched by the user, a bead without a batch closed by the user, an MR URL, a question dismissed by the user, a repository removed by the user) are queued instead (see Orchestrator idle rule). A notice has two readers: its text is Overseer's log line in the thread, written about the user in the third person ("stopped by the user"), and carries no instruction to the model and no internal id; guidance for the orchestrator ("Do not re-dispatch it unless the user asks", "if the command is wrong, tell the user to fix it in Setup…") travels as a `hint` that is delivered with the notice, queued with it (`chat.hint` column, not served by `GET /api/chat`), and never shown (round 8: the rows read as orders to the model). A verification outcome in a notice reads "verify command `<cmd>` passed/failed" or "not verified: no verify command configured"; the earlier "verification pass (no verify command configured)" contradicted itself. A wake is a paid orchestrator turn: a boot that recovers K killed workers produces one session start and K sends, that is K turns, because recovery settles the workers one after another and nothing coalesces notices that arrive while a turn is running. That is the price of not stalling silently; coalescing mid-turn notices into one follow-up turn is a possible refinement, not done (it would delay every notice to the turn end and depends on `turn_end` never being missed).

Setup command (overseer-ldh). A repository has an optional `setup_command` (`repos.setup_command`, null by default, set in Setup alongside the verify and review commands, returned by `list_repos`). Before the daemon's setup command was added, it did not install dependencies in bead worktrees: those only had node_modules because workers ran the install themselves as part of their work, and a batch worktree, which no worker enters, had none, so a repo whose commit-msg hook runs `npx --no -- commitlint` failed every merge into the batch with "Not committing merge" and the bead was reopened as "integration failed". The daemon now runs the setup command through the same shell runner as the verify command (`runSetup`, same `$ <cmd>` + output + `exit <n>` format, same 20-minute cap) in every worktree it creates: the bead worktree at dispatch (only when the folder is new; a re-dispatch reuses the tree it has) and the batch worktree at `create_batch`. A batch records when the command last completed in its worktree (`batches.setup_at`); `integrate()` runs it before a merge when that is null (a batch created before the command was set, or one whose setup failed at creation) or when `ensureBranchWorktree` had to recreate the folder (the dispatch path clears `setup_at` in that case too). A failure never passes silently: at dispatch the bead stays open with the note "Setup failed in the bead's worktree, so no worker was started:\n<output>", the folder is removed so the next dispatch runs the command again, the wake notice reads "<id> was not dispatched: the setup command \`<cmd>\` failed in its worktree." and `spawn_worker` answers with an error; at `create_batch` the batch is created and its notice says the command failed in its worktree and runs again before the first merge; before a merge the bead is reopened with "Setup failed in the batch worktree of <batch>, so <bead branch> was not merged into <batch branch>:\n<output>" and the notice's hint points to Setup and Retry verification, which runs the setup and the merge again (the branch's own verification already passed and stays recorded). No package manager is detected and nothing is hardcoded: an empty command runs nothing. A merge that a hook rejects is reported as one: `mergeInto` recognises git's "Not committing merge" (and any stderr naming a hook) after aborting the half-done merge and throws "the repository's commit hook rejected the merge of <branch>: <hook output>", which the integration-failed note and notice carry verbatim. Changing the setup command in Setup is announced to the orchestrator like a verify-command change, without the running-workers clause: it applies to worktrees created from then on and to an open batch's worktree that has not had it yet.

Preflight probe (`lifecycle/probe.ts`). `Prober.probe(repoId)` is serialised per repo: it runs the setup command then the verify command in a throwaway detached worktree `<worktreesDir>/<repo id>/probe` at the base branch's head, removed after every run, and records a `preflight_runs` row (`pass|fail|timeout|error`, exit code, last 600 characters of output). A `fail` or `timeout` sets `repos.verify_suspect` to that run's id; `pass` clears it; `error` (the probe itself could not start) leaves it as it was; with no verify command configured, no run is recorded and the flag is cleared. On the transition to suspect, one Chat notice ("Dispatch to <repo> is paused: <refusal>.") with a hint, plus a web push. A probe is triggered by `POST /api/repos` with a verify command, by `PATCH /api/repos/:id` when the verify or setup command changed, and on demand by `POST /api/repos/:id/probe` (202); `GET /api/repos/:id/preflight` returns `{ runs (20, newest first), crashes (per harness and class) }` for Setup's repository row. The orchestrator prompt changes: create a batch first for every request (title from the request, e.g. the work item), pass `batch_id` to every `spawn_worker`, call `request_batch_review` when all beads are done or closed (`beads_done` + `beads_closed` = `beads_total`), and answer a rejection by adding beads to the same batch. Worker report formats for parity evidence and story acceptance criteria are documented in the [batch-flow guide](../../guide/batch-flow.md#the-batch-flow).

Before verification or critic planning, `settleWorker` calls `evaluateEvidence` for an opted-in code bead with committed work, passing the bead description, session final text, branch HEAD SHA and worktree path. Evidence lines accept HTTPS upload URLs or, when the task has no upload target, existing absolute file paths outside the worktree; each line includes a caption. No `Parity widths:` opt-in with no `Parity:` or `Evidence:` lines takes today's path. A first failure automatically re-dispatches the same worker using the first review-retry route; `worktrees.evidence_gate_failures` persists across automatic re-dispatch upserts and daemon restarts, resets on a passing gate or non-automatic dispatch, and the second consecutive failure parks the bead for a decision without advancing `review_round`.

The critic reads the change under review, not what the branch merged in. A branch that merged its base in is not reviewable against `<base>...HEAD`: the merge base is then the pre-merge tip, so the diff carries every change the merge brought with it (on 2026-09-21 a merge-resolution bead's diff was 1,344,560 characters against 230,221 for the same work, and codex refused the turn with `input_too_large`, which reached the user as a crashed critic with no reason). `reviewDiff` (`git/git.ts`) takes the newest merge commit since the base, when there is one, and diffs its second parent against HEAD; a branch with no merge commit since its base is diffed against `<base>...HEAD` exactly as before. The prompt names the refs it diffed. A prompt still above the harness's input limit (`inputLimit` in `lifecycle/prompt.ts`: codex's measured 1,048,576 characters, which claude and opencode carry too since they publish none; never raised by configuration) is not sent: `boundedCriticPrompt` reduces it in fixed steps until it fits, dropping the diff for `git diff --stat` over the same refs, then the earlier-round notes, the orchestrator's instructions and the worker's final message, then clipping the file list, and dropping the task description last of all: it carries the review criteria, and a critic without them cannot judge anything. No omission notice names a command the critic prompt forbids (a critic may not run `bd`); the notice for a dropped description asks the critic to report the missing criteria instead. Nothing the review needs for a verdict is cut: the task title and the `submit_review` instructions survive every step, so a reduced prompt still returns a verdict even after the criteria went. The critic is told which parts are missing, with the measured size, the limit and the instruction to read the change in its worktree file by file, and the round runs normally while the size, the limit, the refs and every omitted part are recorded as a bead note and one Chat notice.

A findings round with no `[must]` item (`landsWithFindings` in `lifecycle/reviewSeverity.ts`: every severity is `should`, case-insensitive; an unparseable severity counts as `must`, and a finding reporting that the critic could not read the change keeps the round from landing) lands the bead through the same path a pass takes, writes the findings to the bead's notes under `Review findings landed with (round N)` and appends them to the landing notice (the worktree row keeps both, `landed_note` and `landed_reviewed`, from the merge on, so a `landed_unclosed` bead's Retry close and the `recover()` sweep write that note and notice exactly once); only a round with a `[must]` finding re-dispatches or, at the limit, parks the bead. The configured `review_rounds` is a cap; within it the bead's dispatch tier plans its rounds (`reviewRoundLimit` and `reviewTierFor` in `lifecycle/reviewPlan.ts`, the tier read from the bead's last worker session, a null tier counting as standard): a chore bead gets one round, on `critic-chore` when that tier is configured, else `critic`; a standard bead gets round 1 on `critic-chore` (else `critic`) and round 2 on `critic` only when round 1 had a `[must]` finding or the diff is over 400 changed lines (`git diff --shortstat` insertions plus deletions over the review range, measured once when round 1 starts, stored in `worktrees.review_diff_lines` and written to the bead notes as `Review diff: N changed lines against <range>; L review rounds planned.`; the value survives the review's own worker re-dispatches, which restore it after `spawnWorker` rewrites the row, and is cleared by Retry verification and by a fresh dispatch, each of which starts a new review cycle); a large diff's clean or should-only round 1 does not land but starts round 2 directly (`reviewsAgain`), with no worker re-dispatch; a hard bead gets every round, all on `critic`. The critic prompt and every round notice name that planned limit (`round N of L`). A round past the first passes the previous critic's model in `previousModels`, so it prefers a different model. Critics and review retries keep global review routing, without the repository model filter; worker retries after findings apply the current filter and refuse when no allowed candidate is usable. Below that limit, findings re-dispatch a worker forced with a tier (`sessions.harness_forced`) on the same harness among that tier's candidates, with no step-up, refused rather than moved when none is usable, and a forced worker (`sessions.tier IS NULL`) with the same harness, recorded model and account (unless that harness hung or failed to start, in which case the worker loses its pin and the retry goes through the standard tier without it), while a tiered worker still goes through `resolveTier` with first-round continuation and later-round step-up excluding previously tried models. Every automatic re-dispatch also treats a harness as unusable for that task when its latest worker session there was stopped for inactivity or reopened as a harness bug, passing it to `resolveTier` alongside `unusableCandidates` and refusing with `no usable harness for tier …` when that leaves no candidate.

### API

- `GET /api/programs?repo=<id>` lists programs for one repo, newest first; omitting `repo` lists all programs. `GET /api/programs/:id` returns the program, lane-ordered batches with current batch status and bead counts, waits with their current released state, chronological entries and merge order. A program without batches returns empty collections.
- Evidence is read-only under `<dataDir>/evidence`, beside `overseer.db`: `GET /api/evidence` returns direct folder summaries newest first by recursive file time, count and size. A cold folder scan uses async filesystem operations; a cached summary or file page returns immediately while one coalesced async refresh runs for that folder, so changed files appear on a subsequent load after refresh. When files sit directly in the evidence directory, the list includes an `<evidence-root>` entry for those files (a missing or empty evidence directory returns `[]`). `GET /api/evidence/:folder` lists that folder's files recursively with relative paths, sizes, times and kinds; for `<evidence-root>` it lists only files directly in the evidence directory. Adding `offset` or `limit` returns `{ files, total, next_offset }`, with 100 files per page by default and a maximum of 500; with no paging query the route keeps its full-array response. The Evidence view requests the first page only after a folder opens and loads more pages on request; if a later page reports a different total or overlaps the rows already shown, it reloads from offset zero before appending so files added or removed between pages are not duplicated or skipped. `GET /api/evidence/:folder/*` serves a file with its content type. A satisfiable single byte range returns 206 with `Content-Range`; an unsatisfiable range returns 416 with `Content-Range: bytes */<size>`. HTML, plain text, Markdown and CSV responses include `charset=utf-8`. Symlinks are refused, resolved paths must stay inside the root, and file opens use `O_NOFOLLOW`. HTML and SVG use `Content-Security-Policy: sandbox allow-scripts`, other files download, and paths outside the root return 404. There are no write or delete routes. The Evidence view opens at `#evidence` and a folder at `#evidence/<folder>`; Evidence is a desktop Rail entry, while phones open it from Setup → General.
- `GET /api/repos/:id/commands` → `RepoCommand[]`, sorted by name: reads repo `.claude/commands/**/*.md` and `.claude/skills/*/SKILL.md`, plus the same folders under `~/.claude`. Commands use Claude Code names (nested path slashes become colons); skills use the frontmatter `name` or their folder name. Descriptions use the trimmed first line of valid frontmatter `description`; broken or missing frontmatter gives an empty description. Repo entries win name collisions with global entries, and skills win command collisions within one source. Missing folders contribute no entries, symlinks are skipped, unknown repos return 404, and each repo list is cached for 30 seconds.
- `GET /api/board` → `{ bd_ok, repos: [{ repo, batches: BatchSummary[], cards }] }`; `BoardCard` gains `batch_id` and `verify_failure` (the last 600 characters of the verify output when the bead's last verification failed and it has not landed; null otherwise, and a re-dispatch clears it), and `state` (`running` | `settling` | `verifying` | `review` | `verify_failed` | `blocked` | `idle` | `landed_unclosed` | `done`): one word the daemon computes in the board build from column, session and failure, and the only thing the web drives a card's actions from (round 11: the pane inferred the state from three fields and offered Retry verification / Re-dispatch to a worker that had exited but whose bead had not settled). `settling` is a Running column bead whose last session is not running; `verify_failed` is any non-running, non-verifying bead with a failed last verification (a v1 bead in review included); `blocked` is any Blocked column bead, whatever its last verification said (fix round 11 review: a blocked bead with a failed verification read `verify_failed` and was offered Re-dispatch); `idle` is Ready with nothing failed; `landed_unclosed` is a bead whose worktree row has `merged_at` and a batch while bd still has it open (bd failed after the merge): Retry close only. `BoardCard.session_id` is the bead's last session, so the web can match a `session_ended` notice to its card. The event socket carries `{ type: 'session_ended', session_id }` when a session's process exits, emitted before the `board` notice that follows; a board build waits behind bd for seconds, and the web flips the card to `settling` (and drops Stop) from the notice, keeping it so until a board that knows the session ended arrives, since a board requested before the exit can land after it (round 12: Stop stayed for six seconds after the worker had exited and "settling…" was never seen).
- `GET /api/batches/:id` → `{ batch, beads: BoardCard[], diff, cost, landed_verified }`; `batch.note` is the current summary and `batch.history` the earlier rounds. `diff` is null for a merged or abandoned batch and for a `gitlab-mr` batch once it has an MR (the MR shows the diff; computing it is the slow part of the route, and the Review view says "The diff is on the merge request." instead). On a phone the review sheet hides horizontal overflow and only the diff's own `pre` scrolls sideways. `BatchSummary` carries `beads_total`, `beads_done` (landed) and `beads_closed` (closed as won't do by the user), counted over the batch's worktree rows plus its labelled, never-dispatched beads (see Data); `list_batches` reports the same numbers from the same helper, the new-session preamble reports the closed count too, and the orchestrator is told a batch is complete when done + closed = total.
- `POST /api/batches/:id/merge`, `/reject {note}`, `/abandon` — `202 { job_id, action, target }` once the checks that need no git or bd work pass (the batch exists and is in review for merge/reject; not already merged or abandoned for abandon), with the lifecycle call then running as a background job (`src/api/jobs.ts`, in-memory, one job per target, gone on restart). A second request while that target's job runs is refused with 409 `{ error, job_id, action }`, naming the running action, instead of racing the first one (round 11); that check comes before the state checks, since a running reject has already moved the batch back to open and a running abandon has already marked it abandoned. The batch row carries `pending_action { job_id, action, started_at }` while the job runs, and the `action_result` socket message reports how it ended. Any 500 the REST layer answers is written to `daemon.log` (`rest: unhandled error` with method, url and stack), since Fastify's own logger is off. The three terminal batch actions also exclude each other per batch inside the lifecycle, so a Merge, Reject or Abandon started for a batch while another of the three runs for it is refused with `batch <id> is being merged|rejected|abandoned` naming the running action, whichever entry point — a REST job or the MCP tools `merge_batch`/`reject_batch`/`abandon_batch` — started the second one; a Merge that fails (a conflict) releases the guard, and Merge versus Merge behaves as before.
- `GET /api/batches/:id/retrospective` → `BatchRetrospective`: what went wrong or needed a human during the batch. The daemon records each signal in `batch_signals` as it happens (`rejection` from Reject in Review; `reopen` with a reason class `no_commits | uncommitted_changes | verify_failed | merge_conflict | hook_rejected | setup_failed | stopped` and the note; `redispatch` with the `instructions` given to `spawn_worker`; `closed` with the user's Close bead note) and, at read time, scans the user's chat messages between the batch's creation and its close for a fixed keyword list (`shouldn't`, `don't`, `why`, `still working`, `wrong`, `not what`, `instead`; plain substrings, no LLM call, false positives accepted) as `corrections`. Counts: beads total, reopens, re-dispatches, `signals`, worker cost (reported session costs of its beads) and wall clock from creation to close. The MCP `batch_retrospective(repo, batch_id, full?, bead_id?)` tool returns a compact form of the same record by default — rejection and correction text cut to 400 characters, other signal text to 300, each rejection and correction flagged `truncated` when cut, and re-dispatches grouped per bead with a count and the first 300 characters of each instruction — so a batch with 20 re-dispatches of long instructions no longer exceeds the orchestrator's tool-result limit; `full: true` returns the uncut record and `bead_id` one bead's uncut signals. The REST route, the notice and the retrospective reader `buildRetrospective` keep the full record. When a batch is merged, abandoned or rejected and the record has at least one signal, the orchestrator gets `[Overseer] Retrospective ready for batch <id> (<n> signals): …` — two lines, the second the counts by class — with a hint to call the tool; a batch whose title starts with `Lessons from` never gets the notice, so the retrospective loop does not feed on its own output. The orchestrator prompt has a matching Retrospective section: on the notice it calls the tool, drops one-offs and signals `docs/lessons.md` already covers (read from the overseer repo's primary checkout, the path `list_repos` reports; the record does not carry the file), and for what remains opens a `Lessons from <repo> <batch_id>: <theme>` batch on the overseer repo with one bead that appends the dated entries and makes the prompt edit, quoting the signals verbatim. The user reviews it like any batch; a prompt change is never applied without that review, and no lessons batch is opened for a lessons batch.
- `POST /api/tasks/:id/interrupt`, `/verify` (retry verification), `/redispatch` (`session_id` arrives in the job's `action_result` data), `/close {note?}` (Close bead, see the lifecycle table), `/merge`, `/reject {note}`, `/close-landed` and `/accept-review {note}`: like the batch actions above, each answers `202 { job_id, action, target }` once its cheap checks pass (the worktree exists, for a bead; a running worker, for Stop), then runs the lifecycle call as a background job, one per target; a refusal only git or bd can see is the job's `ok: false` result, and a validation failure is still the 4xx with the reason. The `/verify` job lasts until the verify run itself ends, not until it has started: it is `ok: false` with the reason when that run reopens the bead or the verify command fails. `GET /api/tasks/:id` diffs the worktree against the branch the bead was cut from (`worktree.base_branch`: the batch branch for a batch bead), so the diff is that bead's own work. It finds the bead's repo from its worktree row; with none (never dispatched) it asks the repo whose id prefixes the bead id first (bd's prefix is the repo id when Overseer initialised beads) and the other repos after, and answers 404 `task <id> not found in any repo` when none has it. `TaskDetail.blocked_by` names the open beads the bead waits on, read with one `bd blocked` and only for an open bead whose `dependency_count` is not 0 (`bd list` carries the count alone, and the pane counted where it could name; round 25 R25-4); a failing read leaves it empty rather than failing the detail. The store maps bd 1.2.2's exit-1 `no issue found matching "<id>"` to not-found like the older "not found" (round 15: the first repo's miss threw, the probe never reached the second repo, every never-dispatched bead of the second repo answered 500 and its pane stayed in its loading state for good).
- `ChatRow` gains `queued_at` (an Overseer notice written while no orchestrator session was live; cleared when a turn carries it), `superseded_at` (a question no answer is expected for), `seen_at` (set when the row was handed to an orchestrator session — sent directly, or carried as a queued row — and cleared again when the send threw) and `replied_at` (set on a user row the orchestrator answered with assistant text or an `ask_user` after seeing it; a row whose session ended without a reply stays seen). `POST /api/chat/dismiss {question_id}` sets `superseded_at` from the UI (404 for an unknown question). `GET /api/chat` returns an ascending-id `ChatPage` (default 100 rows; `before` pages backward and `since` returns a delta) so the Chat view does not reload its complete history on every chat event.
- `GET /api/sessions?bead_id=|repo=` → SessionRow[]; `GET /api/sessions/:id/events` → EventRow[] (`?after=<seq>` returns only the events newer than that sequence, so an open Trace fetches just the delta on each live update). The event socket's `{ type: 'event' }` message carries only `session_id` (an open Trace refetches its own session on it; payloads no longer stream to every tab). It also carries `{ type: 'action_result', job_id, action, target, ok, message, data }` when a background action ends: `data` is what the endpoint returned before the 202 (`{ session_id }` for a re-dispatch, `{ mr_url }` for a merge) and `message` the failure's reason.
- The event socket also carries one stateful message: `{ type: 'orchestrator_activity', activity: { state: 'thinking' | 'tool' | 'idle', tool, summary, started_at } }`. The orchestrator emits it when a turn starts (`thinking`), when a tool call starts (`tool`, with the tool name and a one-line summary: for `Bash`/`PowerShell` the call's `description` or the first 80 characters of the command, for the overseer MCP tools a fixed phrase such as "checking worker status for <bead>" / "listing batches" / "running bd <args[0]>", for anything else the tool name; never the full command and never tool output), when the result arrives (`thinking` again) and when the last pending turn ends or the session errors or exits (`idle`). `ws.ts` keeps the latest one and sends it to every socket that connects, so a refresh mid-turn shows the right line.
- The event socket carries the office view's feed too: `{ type: 'office', session: { session_id, role, harness, model, resolved_model, account_label, bead_id, bead_title, batch_id, repo_id, state, stalled_since } }`, one message per state change of a session, plus `{ type: 'office_snapshot', sessions: OfficeSession[] }`, sent once on every socket connect, including when the set is empty, so a view can tell "no sessions are running" from "the set is not loaded yet"; the snapshot replaces the set the web holds. The separate one-shot `office_milestone` message carries `{ type, kind, repo_id, batch_id, bead_id, at }`: `verify_passed` and `verify_failed` publish only after a configured verify command runs, `review_ready` marks handoff to the user, and `merged` marks a batch merging into its base. It is not replayed on connect. `state` is `walking_in` (started, nothing recorded yet), `working` (it recorded a tool call: typing at a desk), `verifying` (the bead's verify command is running between sessions, which alone runs the QA wall screen's tests-running loop), `reviewing` (a critic session: a reviewer walks over) or `leaving` (the session ended or its bead landed). The feed is derived in `src/office/office.ts` from the session events the daemon already emits (`session:started`, the `event` stream's `tool_call` and its `context` event, which re-sends the character once the harness reports the model it resolved, `session:ended`, and the lifecycle's `bead:verify` around a verify command); `ws.ts` sends the snapshot to every socket that connects, so an office view draws the running work at once. That set is reconciled against the sessions actually running when it is built, because recovery marks a lost session's row `ended` without the `session:ended` event: the character goes and an adopted one is drawn. Recovery's ended-write publishes `session:reaped` as well, so a socket already connected gets a `leaving` the reconcile cannot give it, and the reconcile covers the sockets that connect while recovery is still working through its list: a restart leaves no ghost either way. `bead_title` is recorded on the session row at dispatch, so naming a character costs no bd read. A stalled session is published too: the sweep hands `office.setStalled` the ids it currently finds stalled, and each named character carries `stalled_since`, an ISO time beside its `state`, until its next event or a later sweep that no longer finds it stalled clears it; the web draws that as the stalled look. A usage-limit pause still publishes nothing: the limit is held on the account until its reset, not on the bead.
- `GET /api/costs` → `{ repos: [{ repo_id, total, today }], batches: [{ batch_id, total }] }`.
- `GET /api/usage?from=&to=&group=` → `UsageResponse`: over an inclusive UTC calendar-day range (default the last 30 days ending today) it sums the sessions' `cost` as `reported_cost` and their `estimated_cost` as `estimated_cost` — separate fields, never added together — plus token counts by kind and a session count. `days` has one row per calendar day that has sessions (oldest first), `totals` covers the range, and `groups` carries a breakdown per requested dimension: `model` (the resolved model id when the CLI reported one), `account` (the account's label or, unlabelled, its name; null once the account is deleted while the session keeps its id), `harness`, `repo` (path as label) and `batch` (title as label), each sorted by spend, highest first (each session's reported cost where it has one, else its estimate, summed over the group — the same reported-wins-else-estimate rule `cost_source` applies per session, never a session's two figures summed together). Each sum covers only the sessions that carry its figure and is therefore a floor: `reported_unknown` counts the sessions with no reported cost and `estimated_unknown` those with no estimate, so a bucket that is entirely unpriced is distinguishable from one that genuinely cost $0. `group=model,repo` narrows which breakdowns are computed; omitted, all five. Every bucket also carries `codex_sessions`, the count of its sessions that ran on codex: a breakdown row names no harness, and that count is what lets the Usage view put the base-context-tier caveat on exactly the buckets it applies to. `days_by_model` repeats the same sums split by day and model (oldest day first, empty unless `model` is requested), which is what a per-day bar stacked by model is drawn from. Every bucket is one grouped SQL query, so a 5,000-session range costs a scan per bucket rather than loading every row.
- `POST /api/orchestrator/reset` → ends the live session; next message starts fresh.
- MCP: `create_batch(repo, title, branch?)` (a `gitlab-mr` repo cuts the branch from `origin/<base>` after `git fetch origin <base>`, falling back to the last fetched ref and then the local base with a warning, because a stale local base opened MR 8398 already conflicting; a `local-merge` repo cuts it from the local `<base>`, because its batches merge there and are never pushed, so origin falls behind (74 commits on 2026-09-22, when a batch cut from origin conflicted with main); it fetches anyway and returns a warning naming the count when `origin/<base>` has commits the local base lacks, merging nothing (when the fetch fails the warning says so first, and a count taken from the last fetched ref is named as that ref's, which may be behind the remote; plan approval appends the warning to its batch-created notice); a repo without origin uses the local base), `bd(repo, args, batch_id?)` (with `batch_id`, a `create` is labelled for the batch; see Data; a write command returns only the bead id(s), status and title — its labels on `create`, the two ids and dependency type on `dep add`/`dep remove` — and `dep list` returns id, title and status per dependency, so the description and notes are never handed back to be re-read, while a read command including `show` returns the full output), `spawn_worker(..., batch_id?)`, `request_batch_review(repo, batch_id, note)`, `list_batches(repo, batch_id?)` (a default row omits `history` and `note`, the long free text that grows with every rejection and overflowed the orchestrator's tool-result limit; `batch_id` returns that one row with both, so a previous summary can be read before it is rewritten), `batch_retrospective(repo, batch_id, full?, bead_id?)` (compact by default; see the REST entry above). Every `bd` command that is not a read (`show`, `list`, `ready`, `blocked`, `stats`, `search`, `export`, `version`) emits a `board` notice when it succeeds, so a bead the orchestrator creates reaches the Board whether or not it dispatches one; the other writing tools emit it through the lifecycle or the session manager, the reading ones emit nothing, and `ask_user` emits `chat` alone. Round 22 R22-1: a turn that only created beads refreshed nothing, so the batch row read 0 of n for minutes and `#board/<the new bead>` answered "no registered repository has that bead any more" about a bead the daemon was serving in the same second.

When an explicit CLI is needed for an adapter failure or a long, silent check, the orchestrator chooses a different CLI with usage headroom that fits the work. It avoids the failing harness for an adapter issue and OpenCode for silence: Codex waits for `turn.completed` or process exit, while OpenCode ends a silent turn after 20 minutes. Claude is used only when it is the sole fit or the user or a Claude-only MCP tool such as Figma requires it, because automatic retries keep a forced harness pinned.

## Board speed

- The web allows one board request at a time. Socket updates during it coalesce into one trailing request; any fresh trigger makes that request fresh. The current response applies before the trailing request starts, including when the current request fails. Responses are ordered by request start and an answer is ignored only if a newer answer already applied. Every applied answer still passes its request mark to `boardLoaded` and the board through `settle`; the 400 ms `REFRESH_NOTE_MS` note remains continuous across a trailing request.
- `Beads.list` runs one `bd list --all -n 0 --json` per repo (also removes the 50-row cap); the last result is reused for up to `LIST_TTL_MS` (2 s) while neither `last-touched` nor `interactions.jsonl` in the repo's `.beads` changed, and every write (and every `bd init`) clears it.
- `buildBoard` builds repos with `Promise.all`. Inside a repo `Beads` runs reads (`list`, `show`, `ready`) alongside each other and writes alone, each after every earlier call: the board's `list` waits only behind writes (one per transition, about half a second), not behind the orchestrator's `list_tasks` or `show` calls. Round 5 measured the remaining 1.0–1.85 s builds and every one was a repo whose `list` had queued behind the orchestrator's tool calls or a lifecycle write, not the idle repo's own cost (`bd list` is 0.48 s on that machine whichever repo runs). `list_tasks` skips `bd ready` like the board does when no open bead has a dependency. `list` and `ready` are two reads half a second apart: a dispatch between them leaves the bead open in the first and in_progress (so not ready) in the second, and its card flashed through Blocked for a second (round 14); a bead with a running session in the daemon's own table is shown running whatever bd read.
- The slow-build warning logs `{ ms, per_repo: { <repo id>: ms } }`.
- `Beads.available()` caches a positive answer for 60 s.
- `GET /api/board` coalesces concurrent builds into one in-flight promise.
- The web Board keeps the previous board while refetching and debounces refetches by 300 ms; the board shimmers in the shape of its columns only before the first response. Every block that waits on its own fetch shimmers in the shape of what arrives rather than standing as one line of text or, worse, as an answer it does not have yet: the board (a repo section of six columns of cards), the card pane (History, the last assistant text and the verification output), Trace (four collapsed event rows), the Office needs-you strip (a Plans-shaped row — icon, title, one sub line, drawn as spans since the library paints a button as one solid box — plus as many item-shaped rows as the strip showed the last time it loaded in this browser, kept in localStorage as `overseer.officeStripRows`, default 1 and 0 allowed, capped as the arrived strip is and followed by the `+N more` row's shape when the stored count is over the cap; each placeholder row is border-box like the arrived button rows, keeps their card border and background and draws its title bar as long as its text, clipped to the line; `pnpm --filter @overseer/web test:office-strip-layout` holds the API, measures each placeholder row against its arrived row at 390x844 dpr 3, 768x1024, 1280x800 and 1920x1080 with 0, 1, 3 and 7 items (7 is over both caps, so the `+N more` row is compared too) and fails on a left, right, width, height or top difference over 2 px (all land at 0 px), and checks that the object buttons and count row show no digit while loading; an empty settled list has no strip) and the Office counts (until the data a count needs has arrived the room draws no question note, no folder and a bare whiteboard, the object buttons read `questions loading` / `columns loading` and each phone count row button shimmers where its number goes; 0 once that fetch has failed; Questions waits on the chat page, and In review and the whiteboard columns on the board alone, so a failed or slow plans, chat or repositories fetch neither drops In review to a false 0 nor keeps it shimmering after the board has answered), the Plans list (two rows, in place of "No plans yet.") a plan's own page (the head, the title field, two steps and the action footer) and, in Setup, Prerequisites (one row per tool in the daemon's own list, then the data dir), the daemon's running-since line and the repository table (two rows, the count a working install settles at), and in Review the list (two sections of one row each, In progress and Beads in review, since a batch sits in one section at a time and Finished is collapsed; ## Daemon restart

`GET /api/daemon` reports the daemon pid, start time, running commit, source head, whether a restart is needed, whether a restart is in progress, and any last restart failure. Setup can send `POST /api/daemon/restart`; it receives 202 immediately, and a second request while the restart runs receives 409. Before spawning a successor, the daemon compares a startup hash of the root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `packages/*/package.json`; if any differ, or the startup hash was unavailable and the current inputs can be read, it runs `pnpm install --frozen-lockfile` in the checkout with a five-minute bound. A startup hash read failure does not stop the daemon. If current restart inputs cannot be read, the restart fails with the reason and keeps the old daemon online. A failed install or a successor that exits or misses the startup gate also leaves the old daemon online. The status endpoint carries the reason and at most 20 lines of install or successor output; Setup displays them, hides an older failure while a new restart is in progress, the orchestrator receives one wake notice, and a later successful restart clears the failure. Once the successor has loaded and reached its parent gate, the old daemon closes and Setup polls until the replacement returns on the same port. A restart ends the orchestrator session, but detached workers survive and `recover()` adopts them from their saved logs. The daemon retries port hand-over while the old process exits, and the web reconnects without a reload. A watcher (`pnpm dev`) never takes an occupied port: it exits after naming its holder, leaving the long-running daemon untouched.

### Accounts

An OpenCode account holds a provider key, and a tier candidate can point at that account; Setup determines which tier uses DeepSeek. An OpenCode candidate with no account runs on the CLI's own login, so tier resolution (every worker, forced and critic pick) skips it as unusable, with the reason in any refusal, when that login holds no key for the model's provider: the provider's key variable is unset in the daemon's environment and `opencode auth login` stored no entry for it in `auth.json` (`opencodeOwnLoginReaches`; a provider Overseer knows no key variable for is not checked). opencode 1.18.19 given no key exits 1 on its first request with only an `UnknownError` "Unexpected server error" line and an empty stderr; four chore critics were lost that way on 2026-09-28. A repository model filter restricts the global worker tier candidates by harness, model and account before routing and price sorting; it is not a separate tier table. Each non-empty list is an allow-list, empty lists leave that field unrestricted, and an account allow-list excludes machine login. All worker retries use the current filter, including review-findings and exhausted-account retries. A forced harness outside the filter is refused. If no allowed candidate is usable, dispatch is refused with the reason and the task waits; a filtered repository never uses the degraded CLI-default or machine-login fallback. Critics and their retries keep the global review tiers and are not filtered. A forced harness (`harness` without `tier`) takes the first usable candidate of that CLI in the `standard`, `chore`, then `hard` tier, with its model, effort and account, and records them on a session whose tier stays null, so a forced `claude` worker runs on a configured Claude OAuth account and reaches the plugin MCP servers (Figma) that Claude Code suppresses for the machine login's claude.ai connectors; a candidate whose account has no authorization yet, or whose stored token can no longer be refreshed, is skipped rather than failed on, and without a repository model filter, with no such candidate the dispatch keeps a retry's pinned model (else the CLI's default) and any still-usable recorded account, falling back to the CLI's login otherwise, a degraded session, and the daemon logs a warning. A harness passed together with a `tier` forces that CLI within that tier: it resolves only among that tier's candidates of the harness, in configured order and under the same usage, exhaustion, `previousModels`, `needs_server` and held-harness rules, with no step-up, and when none is usable the dispatch is refused with `no usable <harness> candidate in tier <tier>` (plus the reasons) instead of moving to another harness or tier. The session records the tier and `harness_forced = 1`, so every retry of it (transient crash, rate or usage limit, review round, deferred work, the Board's Re-dispatch, and after a daemon restart and re-adoption) keeps the harness and the tier, and is refused the same way when that tier has no usable candidate of the harness left.

PixelLab is a user-scope HTTP MCP server in `~/.claude.json`, which Claude workers load, so a task that needs it is dispatched to `claude`.

OpenCode cannot keep a server, daemon or browser running: its shell tool reaps a backgrounded process with the tool call's host and blocks for good on a detached one (measured in `docs/server-start-in-a-worker-shell.md`, after four workers stalled on it in one evening). `spawn_worker(needs_server: true)` states that a task starts such a process — a dev server, a daemon, a browser, including evidence and screenshot capture. The flag turns every harness in `NO_SERVER_HARNESSES` (`routing/tiers.ts`, today OpenCode alone, and the single place to add or clear one) into an `unusableHarnesses` entry for that dispatch, so a tier skips its candidates; when that leaves no candidate, the dispatch is refused as "no usable harness for tier <tier>: \<reason\>". A forced harness is no exception: `harness` set without a `tier` to one that cannot hold a server is refused with the same reason, naming the harness, instead of started; `harness` passed together with a `tier` stays a preference the tier may overrule, so it routes as usual. The flag is stored on the session row (`sessions.needs_server`, `ADDED_COLUMNS`) and `needsServerFor(beadId)` re-applies it to every later dispatch of the bead — the review round, the rate-limit pickup, the crash retry and the Board's Re-dispatch — since no orchestrator is in the loop to set it there. The orchestrator prompt tells the orchestrator to set the flag for such work and to relay either refusal to the user.

|---|---|
| name, harness, kind, provider | A named Claude (OAuth with setup-token fallback, or API key), Codex (device login), or OpenCode API-key credential set. OpenCode requires its provider, for example `deepseek`. |

`accountEnv` injects `CLAUDE_CODE_OAUTH_TOKEN` for Claude OAuth or setup tokens, `ANTHROPIC_API_KEY` for Claude API keys, the provider-specific variable for OpenCode API keys (`DEEPSEEK_API_KEY` for `deepseek`), and an isolated `CODEX_HOME` for Codex. Setup starts Codex device login and polls its link and code; the user can open the link anywhere, enter the code and approve, or cancel. Claude login generates a PKCE verifier and state, returns the Claude approval URL, accepts the pasted `code#state`, exchanges it for access and refresh tokens, and stores those tokens in private account columns that no API response exposes. The same field accepts the full token from `claude setup-token` as a fallback. Before a worker or orchestrator starts, an OAuth access token expiring within two hours is refreshed and persisted, and the session records that expiry so a resume can tell whether the account has since refreshed it; a failed refresh never mutates the stored credentials, and only the start is refused as logged out with the refresh error in the notice, so Setup's Verify can retry and heal the account. A live orchestrator session is ended and the same native session resumed when its recorded expiry no longer matches the account's, or is inside that window, so it picks up the refresh with its context and open questions intact (only when no turn is running, since ending the process would kill that turn; a delivery during one joins it, and a 401 on it takes the recovery below); a turn the CLI rejects on its token (`auth_failed`, or a `turn_end` with `authFailed`) writes no chat row, ends the process, refreshes the account and resumes the same native session, re-sending each delivery that failed once in order, and the not-logged-in line appears only when the refresh is rejected or the resumed session is rejected again. API keys are entered while adding the account; an OpenCode key is pasted directly, has no login flow, and can be replaced with its provider in the existing account row without any API response exposing it. Verify runs the selected harness with that account and records success or its error. Model tier candidates may select only logged-in accounts with the candidate's harness; the Claude orchestrator may select only Claude accounts; null remains the machine login.

An optional account label distinguishes otherwise similarly named accounts. Setup shows it as a tag, Models includes it in account options, and a Board card exposes the selected account in the agent pill hover text and its detail pane.

Setup polls `GET /api/accounts/:id/usage` every 60 seconds for each Claude OAuth account. The daemon caches upstream usage for 180 seconds and dedupes in-flight calls, so the shorter client poll only reads locally and picks up a refreshed value within about a minute of cache expiry. When a session on an account ends, the daemon drops that account's usage cache so its next gate decision fetches fresh values. A compact line shows session, weekly and per-model percentages with local reset times and a fetched-at staleness marker. A failed refresh keeps the last good values and adds its error; an empty response shows no line.

On a bead's first dispatch (no previous models) a `chore` or `standard` tier takes, among its usable candidates remaining after the repository model filter, the one with the lowest models.dev input price (`resolveTier` with `prices`); an unpriced model sorts after every priced one, ties keep configured order, and without a loaded catalog (no cached copy read and no fetch finished yet, `PriceCatalog.loaded()`) the configured order applies and the log says no price catalog is loaded. `hard`, `critic`, `critic-chore`, re-dispatches and a forced harness keep configured order. The daemon logs the pick and its price.

At every account-backed session start—a worker's first or automatic dispatch (including exhausted-account retries and auth resumes), a critic's review round, a discussion participant or synthesis, or a fresh or auth-failure-resumed orchestrator session—the gate checks a Claude OAuth account's five-hour session bucket, seven-day all-models bucket and matching model bucket against `max(OVERSEER_USAGE_THRESHOLD / 2, OVERSEER_USAGE_THRESHOLD - running sessions on the account * OVERSEER_USAGE_RESERVE_PER_SESSION)`. For a new start it counts all other running session rows for that account, including workers, critics, discussion sessions and orchestrator sessions; for a resume it excludes the session being resumed. `OVERSEER_USAGE_THRESHOLD` defaults to 95 and `OVERSEER_USAGE_RESERVE_PER_SESSION` defaults to 2 percentage points; a blank, negative or non-finite value falls back to 2, while 0 is valid. A refusal names the configured threshold, reserve, running-session count and effective threshold. The gate only blocks new starts and auth resumes; it never stops an already-running session. Model matching uses the exact ID first and then the shared hyphenated model family. A candidate is also skipped while its account has a future `exhausted_until` handoff timestamp, or, with no account, while its harness has a future entry in the `harness_limits` setting; a codex session that ends after a usage-limit `error`/`turn.failed` sets one of the two to the reset its message names (read as local time, which is how codex formats it; one hour when unreadable), a forced-harness dispatch is refused the same way, and one Chat notice names the harness, the reset in UTC and the session. The same session is then re-dispatched through the exhausted-account path: a worker starts afresh on the next usable candidate of its tier — a forced, tierless worker on the next usable candidate of its own CLI, so it keeps that harness and the account it needs — a critic resumes its current review round on the next critic candidate without reopening the bead or spending a round, and one Chat notice names the harness, its reset and the new candidate; when no candidate survives the bead stays Ready and the notice names the harness and its reset instead — except the exhausted-account case of a forced, tierless worker, whose own accounts are exhausted while its CLI is not held and which, only without a repository model filter, instead starts on that CLI's own login in the forced-harness route's degraded fallback, tier and account null, with a warning; a forced worker whose whole CLI is held still waits. A session stopped on purpose, or one whose batch was abandoned or merged meanwhile, is left to its own settle instead of being re-dispatched. If every candidate is skipped, the bead remains Ready, the dispatch reports every account reason, and Chat posts one deduplicated `no usable account for tier` notice for that bead. A session that ends on a rejected login (the structured `auth_failed` event or a `turn_end` with `authFailed`; the CLI's own login is read from the exit text) is resumed on the account's refreshed environment first — the same native session (a claude worker's or critic's native id is recorded at spawn, so a first turn with no `turn_end` resumes too), or the same review round re-run on whichever usable critic candidate the tier picks again — and only a rejected refresh, or a resumed session rejected again (one resume, marked on the row as `sessions.auth_resumed` so it holds across a restart), parks the account at `AUTH_HOLD_UNTIL` (far future, not a reset). A worker or critic auth resume blocked by the usage gate is not started and reopens its task without parking the refreshed account; an orchestrator auth resume stays on its account and leaves the failed delivery retryable when the gate refuses it. When the session's recorded token expiry still equals the account's, the stored token is the rejected one and the refresh is forced past the two-hour margin; a stop from the user or the orchestrator is applied first and a stopped worker is never resumed, so it is skipped until the user logs it in or verifies it again (`clearAuthHold`); those sessions record `crash_class='auth'`, and one notice names the account and asks for the re-login. ## Stall detection

A worker that loops, waits on a prompt, or re-reads the same files looks exactly like a working one: the pid is alive and
its start time matches, which is all `recover()` ever checked. `src/lifecycle/stall.ts` adds the missing signal. Every
harness event already lands in `events` with a `ts`, so a session's last sign of life is one indexed read
(`events.lastTs`); a session that has recorded no events at all falls back to its `started_at`.

`sweepStalls` runs every `SWEEP_MS` (60s) over `sessions.running()`, restricted to the `worker` and `critic` roles — the
orchestrator is idle between the user's messages by design and would report constantly. A session is quiet only when
neither its log nor its worktree has changed: once the log has been silent for longer than `OVERSEER_STALL_MIN` (default
15 minutes; `0` starts no sweep at all), the sweep reads the newest modification time among the worktree's changed files
(`git status --porcelain`, so ignored paths such as `node_modules` and `dist` never count), at most once per
`WORKTREE_CHECK_MS` (5 minutes) per session. A worktree changed within the threshold keeps the session unreported, since
an opencode sub-agent can edit files long before its `task` call shows up in the log (a DeepSeek worker was stopped after
16 silent minutes on 2026-09-17 with ten files edited). A session quiet on both gets one queued notice:

```
[Overseer] ov-1 has shown no sign of activity for 16 minutes; its worker (codex gpt-5.6-terra) last said: "Running the test suite."; its worktree has not changed for 20 minutes
```

When the worktree changed after the last log event but is itself past the threshold, the tail reads `; quiet log for 40
minutes, but the worktree changed 17 minutes ago; a sub-agent may be working`. A clean or unreadable worktree adds no
tail.

with the hint *Call worker_status for the bead. If it is genuinely stuck, interrupt_worker with the reason; if it is
waiting on something slow, leave it. Do not re-dispatch without asking the user.* For an opencode session the hint
adds that the adapter ends a turn that prints nothing for `TURN_SILENCE_MS` (20 minutes) after its last event and after
every running tool call's own timeout by itself, so the session can be left until then rather than interrupted: the
15-minute stall threshold comes first.

The daemon reports and never acts: interrupting a worker that was legitimately running a slow test is worse than the
silence, and deciding is what the orchestrator is for. Dedupe is a session-id → last-activity mark (the last event timestamp, plus the worktree time when that is newer) map held in the
sweep's closure, so one silent stretch is reported once while a session that wakes up and stalls again is reported again;
entries for sessions that are no longer running are dropped each pass. The map is memory only — a daemon restart re-arms
the detection, which is the wanted behaviour. `startStallSweep` returns a stop function (null at threshold 0) and unrefs
its timer, so it is never the reason the process stays alive; `index.ts` starts it after `recover()`, so an adopted worker
is running before its silence is measured, and stops it in the `onClose` hook.

Each pass also hands the office feed the ids of every session it finds stalled (`onStalled`, the empty set included, so a
cleared mark is published too). `office.setStalled` gives a named character not yet marked a `stalled_since`, clears the mark
on a character the pass does not name, and publishes only a change, so a repeated pass over one silence is silent. The web
draws a marked character with a clock effect in place of its usual one and a dimmed sprite, and its tooltip and accessible
name read `stalled since HH:MM`; the mark clears on the session's next event or on the next pass that does not name it, and
returns the character to the pose it already had. A marked session is still swept and reported like any other; the mark is a
second reader of the same signal, not a replacement for the Chat notice.

## Idle end after a turn end

A worker that already reported its final result but is left running (an orchestrator message queued mid-turn keeps the
session open past that turn end, on the chance of another message) pays for the idle time until the stall sweep notices
it 15 minutes in — the session cost that time for nothing and the bead waited (acme-portal-sample-039, 2026-09-22: a complete
final report sat idle for 15 minutes before the stall notice ended it). `src/lifecycle/idle-end.ts` closes that gap:
`sweepIdleEnds` runs on the same `SWEEP_MS` interval as the stall sweep, over `sessions.running()` restricted to the
`worker` role, and ends a session whose latest event is a `turn_end` and whose last `assistant_text` is non-empty once
that turn end is older than `OVERSEER_IDLE_END_MIN` (default 3 minutes; `0` starts no sweep). Ending it calls
`SessionManager.end`, the same clean-end path a session takes on its own when nothing keeps it open, so the settle rule
sees an ordinary end: the final message is the result and commits are verified as usual, exactly as if the queued
message had never arrived. Because the sweep always reads the session's *current* latest event rather than a timestamp
it captured earlier, any later event (a further message, a tool call) reopens the window on its own — the sweep simply
no longer sees a `turn_end` as the latest event until another one lands. A session with no final message, or one that
never reached a turn end at all, is left to the stall sweep untouched.

## Orphan reaper

Stopping a worker sweeps its process tree, but a daemon crash or restart skips that sweep, and on 2026-09-17 four
processes were still running hours later under worktrees whose tasks had merged. Later that night five more dev servers,
each with its `esbuild.exe` child, outlived the sessions that started them (cleanly, by silence, by interrupt) and were
stopped by hand; every one had been reparented, so the session-end sweep could not reach it. `src/lifecycle/reap.ts`
closes both gaps.
`reapOrphans` reads the process table once through `processRows` in `util/procs.ts` (the same listing `descendantPids`
walks, extended with each command line) and kills, with `killProcess`, every process whose command line, or on Linux
working directory, names a worktree `<dataDir>/worktrees/<repo>/<name>` that no running session uses. It logs the pid,
the worktree and the command line for each. It never kills a process that also names a protected worktree (the cwd of a
running session, a repo's `base` worktree, or any worktree inside or around a primary checkout or the daemon's own source
root). It also spares the daemon, its ancestors and its descendants, so a setup, verify or probe command and a worker
being started are left alone. It kills only what Overseer left behind: a candidate is reaped only when every live
ancestor (a parent that exists, started before it and is not pid 1) is itself a candidate, so an orphaned tree whose root
lost its parent in the crash is reaped, while an editor or shell the user opened on a worktree path, whose chain leads to
Explorer or a terminal that names no worktree, is never touched. An orphaned tree with an intermediate that names no
worktree (a bare `cmd.exe`) is spared too; that miss is the safe side. `startReaper` runs the first pass at startup, after `recover()`, since a crash leaves
the most behind then and an adopted worker's session is running by that point. It runs again every `OVERSEER_REAP_MIN`
minutes (default 5; `0` starts no reaper) and never overlaps a pass still running. Its timer is unref'd, and
`index.ts` stops it in the `onClose` hook.
`reapEndedSession` runs on every `session:ended`, whatever ended the session — a clean end, a silence timeout, an
interrupt, a crash — and is that same pass scoped to the worktree the session ran in. Only candidates there are considered, and the live-ancestor guard is not consulted. The daemon and its ancestors stay safe. A daemon descendant is a candidate only when its cwd or executable path is inside the ended worktree; text in its other arguments does not count. A server in that worktree remains eligible even when it stays below the CLI through the daemon, and
the ended session is the authority that the worktree is disposable. A process in another live session's worktree, a
protected path or a `base` worktree is still never touched. It stops each process with its tree, logs the pid, worktree
and command line, and posts one Chat notice naming them when it stops anything, so a leak is visible rather than silent.
A finished lifecycle path — a bead that lands or is closed, a standalone `merge()`, or a batch that merges or is
abandoned — runs that same scoped pass on the worktree before removing it, and a failure there is logged and never
escapes the landing, merge or abandon.
Known limit: a process that outlives its session with its parent chain still leading to this daemon is a descendant and
is spared by the periodic pass; the session-end pass stops it when its cwd or executable path is inside the ended worktree, and the periodic pass covers a daemon
crash once that chain has broken.

### Leftover worktree folders

Every periodic pass also runs `reapLeftoverFolders`: a `<worktreesDir>/<repo>/<name>` folder git no longer lists is removed when the daemon's own record says its work is done — the worktree row is closed or merged, or its batch is merged or abandoned — and a folder that matches no row is removed only once it has sat there more than a day. The folder list reuses `deregisteredWorktrees` (the same detection the day report's orphan-bytes count reads), a folder a running session sits in is skipped, and any path that resolves outside the worktrees directory is refused and logged. Each removal goes through `removeWorktreeRetry`, and the folder's size is logged so a reclaimed leak is visible; the periodic pass's other work (killing processes) is unchanged.

## Nightly report

A retrospective reads one batch; nothing counted a day. `src/report/dayReport.ts` derives one UTC day's counters for a repo
from the stored record — worker sessions whose bead reopened as `no_commits`, re-dispatches and critic rounds per bead,
landings that kept open findings, closes as won't do, reported cost and cost per landing, and the bytes held by worktree
folders git no longer lists — and renders them as plain text. Signal extraction reuses `lifecycle/retrospective.ts` and the
cost sum reuses the usage reader, so there is one reader of each. `src/report/nightly.ts` runs it once a night for every
repo over the last complete UTC day.
`startNightlyReport` schedules the next local `NIGHTLY_HOUR` (03:00) and only ever moves forward, so it runs nothing at
startup: a night the daemon was down is skipped, not replayed in a burst the next morning. At the hour it writes
`<dataDir>/reports/<date>.txt` (one file per day, so a run can be read back) and reuses `orchestrator.systemMessage` to
notify only when a threshold trips. The thresholds are the report's `REDISPATCH_THRESHOLD` (a bead past three
re-dispatches) and `REVIEW_ROUND_THRESHOLD` (a bead past two review rounds), plus `NO_COMMIT_THRESHOLD` (three or more
sessions ended without commits) and `ORPHAN_BYTES_THRESHOLD` (orphan worktree directories past 1 GiB). A notice names the
numbers and the beads and says nothing else; a failing run is logged and rescheduled, never thrown at the daemon. The timer
is unref'd and `index.ts` stops it in the `onClose` hook. `nightly.test.ts` covers the scheduled run, a quiet night, each
threshold and a skipped missed night with fake timers. The same clock runs `startRetention` (`report/retention.ts`): a session that ended more than `OVERSEER_RETENTION_DAYS` (14 by default, and a blank, zero, negative or non-numeric value falls back to it) ago loses its events and its stdio log, while its row, cost and token counts stay; a running session and one with no `ended_at` are never touched, a stored `log_path` is used only when it resolves inside the sessions dir (otherwise `<sessionsDir>/<id>.log`), and the freed pages return with an incremental vacuum, one full `VACUUM` the first time to switch `auto_vacuum` to incremental, its duration logged.

## Orchestrator idle rule

`Orchestrator` records `lastActivityAt` on every delivered message and every `assistant_text` event. In `deliver`, if a live session exists and `now - lastActivityAt > idleMs`, end it first. When starting a session, resume only if the previous session's `ended_at` (or last activity) is within `idleMs`; otherwise start without `resumeId` and prepend a preamble, which ends with the daemon's own offset from UTC ("The dashboard shows local time, which is UTC+02:00."): tool output and bd JSON are UTC, the dashboard renders local time, and a time quoted straight from a tool was two hours off what the user was reading (round 19). A resumed session records the model it is already running (the id its harness resolved when it last ran, else the one its row recorded, else the setting) without passing a model to the CLI, which cannot change a live thread; a fresh session records the configured model. The orchestrator prompt carries the matching rule: convert to that offset before quoting a time, or say "UTC". Every stamp the UI renders comes from the viewer's own locale, in the shape its place needs: a Trace event shows the time alone (the stream is one session), a batch that was merged or abandoned shows date and time (the decision may be days old), and the orchestrator's prose is its own sentence. Round 21 noted the three shapes; they are deliberate, and forcing one would override the viewer's locale to no one's gain.

```
[Overseer] New orchestrator session (the previous one expired after inactivity or was reset). State lives in beads and the board, not in this chat. Repositories: <id> (base <branch>, merge mode <mode>, verify command `<cmd>` | no verify command configured); ... Batches (a batch in review is awaiting the user's review and is not merged, whatever its beads-done count): <id> "<title>" on <branch>: open | in review (awaiting the user's review, not merged), <n>/<m> beads done; ...; finished: <id> "<title>" on <branch>: merged | abandoned, <n>/<m> beads done; and <k> more (list_batches has them). Call list_tasks before acting.
```

Every batch carries its status; the newest five finished ones are named and older ones counted. `list_batches` returns the same phrase as `status_label` next to `status`, and the prompt says a batch is merged only when `list_batches` says `merged` or a merged notice arrived (round 9: after New session the orchestrator told the user a batch in review was "already merged").

`POST /api/orchestrator/reset` ends the live session and marks it so the next message starts fresh. The Chat view gets a "New session" button and the rail shows the session's age.

`GET /api/status` reports the orchestrator as `idle` (with the last activity time) after a reset and in a daemon that has not started a session yet, a restart included: the previous row is `ended` by design in both cases, and the next message starts or resumes a session. `ended` and `failed` are reported only for a session this daemon started. It also reports `busy`: true while any delivery is still without its `turn_end` (a count, not a flag: a notice delivered mid-turn pipelines a second turn, and the first `turn_end` must not read as "waiting" while the second runs; a send that throws rolls the count back; the session's end clears it). The rail mascot shows its thinking pose while busy and its idle pose for a live session between turns; its accessible label announces that state without visible status text. Round 7 found "running" read as "it is doing something" through minutes of silence, and round 15 found "waiting" read as waiting on the user while no question was open.

Notices without a live session (round 6). `systemMessage` delivers a notice to the live session at once. Without one, a notice flagged `wake` (see Lifecycle) starts or resumes the orchestrator through the same `deliver` path as a user message, so a rejection or a reopened bead after a daemon restart is acted on without the user typing (the daemon therefore runs crash recovery after it listens: the orchestrator's MCP server is the daemon itself; the port being bound is not the daemon serving, though — `registerReadyGate` in `src/app.ts` holds every request, websocket upgrade and MCP call until `lifecycle.recover()` and `servers.recover()` have returned, and answers `/api/health` 503 in the meantime, so no board, socket snapshot or tool call reports a session recovery is about to end; the notice that starts the orchestrator spawns its CLI and returns without awaiting the turn, so the tool calls that turn makes wait for the gate without stalling recovery, and only `GET /api/daemon` is exempt, because the port-takeover handshake reads it); every other notice is stored with `queued_at` and the Chat view labels it "queued for the orchestrator's next turn". A notice kind the orchestrator prompt says needs no action (`isQuietNotice` in `src/orchestrator/quietNotices.ts`: an `… re-dispatched: … exhausted until …, now on …` re-dispatch, a re-dispatch after a transient stream failure, `Batch <id> no longer waits`, `Stopped N process(es) left running in …`, and a review round prompt that did not fit the critic's harness) is queued even while a session is live, is written to its bead's notes when the caller names the bead (`beadId`, the session-end process cleanup passing the ended session's bead), and never starts a turn, since every turn re-reads the session's whole context; a `wake` notice is never quiet. `deliver` prepends the queued notices to the next turn: the quiet ones as `[Overseer] Since your last turn: - …`, then the rest as one block (`[Overseer] Notices while no orchestrator session was live: - …`) and clears `queued_at` only once that turn was sent or started (a start that throws leaves the notices queued). The UI text "the orchestrator was notified" is therefore true for the actions that say it (rejection of a batch or a v1 bead).

Superseded questions (round 6). A question is pinned with an answer box until it is answered, superseded or dismissed. Superseded: `sendUser` records the draft's open-question snapshot against its stored message id. A successful delivery closes only questions from that snapshot that remain open; a refusal or thrown delivery clears the snapshot without closing its questions. If `turn_end`, session end or auth recovery wins the completion race, it settles only snapshots attached to the deliveries it ended, so an earlier turn cannot close a later queued send's questions. Questions in a closed snapshot get `superseded_at`: the user moved on in the composer and the delivery told the orchestrator the question is closed, so it is no longer waiting. New session does the same to every question still open, at the moment of the reset: the orchestrator that asked them is gone, so an answer would reach one that never saw the question (round 22 R22-2: the ended session's question stayed pinned with its answer box and its rail count, describing a state that had moved on since); the supersede is written before the notice row of the new session, so each question keeps its place above the notice that closed it (round 23 R23-2). Round 9: closing at turn end kept the card and the rail count on screen for ~25 s after the reply that answered the question. Answers to other questions do not set a cutoff (two questions in one turn stay pinned while they are answered one by one), and neither do notice-driven turns (a landed bead does not close an unrelated question). A superseded question sits in the thread where it was closed (see the thread order below) with a muted "No longer waiting for an answer" line and no answer box; it is not counted in the rail; the user can still reply through the composer. Dismiss on the pinned card sets `superseded_at` directly for a question the orchestrator has not moved past in that sense (a notice-driven turn, a question answered by an action on the Board) and sends an informational notice ("Question \"…\" dismissed by the user without an answer.", with the question id and "do not wait for an answer" as a hint to the model only), so the orchestrator's "Waiting on your answer" does not stand as the thread's last word next to a closed question (round 7). Superseding sends no notice and costs no turn: the user's message itself carries it. Question ids are Overseer's own bookkeeping and appear in deliveries only: the prompt tells the orchestrator never to put a question's number in anything the user reads, since no surface shows one (round 22 nit: "Still waiting on the filename (question #938)" referred to a number the UI has never printed). The prompt asks for the same exactness with ids: bead and batch ids are written as the tools return them, never shortened, since the user matches them against the Board (round 23 nit: one sentence said "overseer-7hg" for `overseer-copy-7hg` while every tool call and every rendered id was right). When `sendUser` finds questions still open, the delivery (not the stored row) is prefixed with "[Overseer] The user replied in the composer rather than in the answer box of question #n (\"…\"). If this message answers it, take it as the answer; either way the question is closed and no separate answer will come, so do not report it as waiting." Round 8 found the orchestrator repeating "waiting on your answer" for four turns after the UI had closed the question.

- Events already recorded per session are exposed (see API). The Board detail pane's Trace button opens the last session's events under the pane, one row per event (time, kind, a one-line summary: the assistant text, the tool name and input, the changed path, the turn cost, the pid, the error) with the raw event JSON behind a disclosure, and a "raw JSON" link to the endpoint (round 11: Trace opened a raw JSON array in a new tab with no way back). Summaries render like every other worker text (an inline code span becomes `<code>`), the list follows a running session: the daemon emits `board` only at lifecycle boundaries, so the app shell counts the session's own `event` notices, at most one bump a second per session, and an open Trace of a live session refetches on that count and on board changes (once more when it ends), keeping the rows it has until the new ones land; a response for a session no longer shown is dropped (fix round 12 review: a live trace never refreshed during a run). A codex session that resumes a thread (a continuation re-dispatch) records the thread's counters at resume and prices only the delta above them, so its row does not bill the earlier session's turns; its token columns store that delta as well, so summing a bead's session counters counts the thread once, not once per continuation. Codex's `gpt-5.6-*` models also carry a higher per-request price tier (the catalog's `context_over_200k`); the codex estimate deliberately does not apply it, because codex's stream reports no request's own context, so a codex session whose individual requests crossed ~272k tokens is estimated low by up to 2x. opencode does report one usage per model response, so its estimate is accumulated response by response, each billed at the context tier each response's own input selects exactly as opencode does (the matching `tiers` entry with the largest `size`, else `context_over_200k` when `inputTokens > 200000`, else base). Claude's cache-write tokens split into a 1-hour and a 5-minute TTL slice (`cache_creation.ephemeral_1h_input_tokens`); the 1h slice is billed at 2x the input rate and the rest of the cache-write tokens at the catalog's 5-minute rate. The catalog is fetched once from `https://models.dev/api.json`, cached at `<dataDir>/models.dev.json` and refreshed daily, falling back to the cached copy when the fetch fails. `cost`, the totals and the floor labels above stay the reported figures; the estimate and its source are recorded on the session row, `GET /api/usage` sums both figures over a range, and `views/Usage.tsx` is where the user reads them.

## Plan gate

Design: `2026-09-16-plan-gate-design.md`. When the user asks to plan work out, the orchestrator calls `propose_plan` instead of
`create_batch` and ends its turn. A plan (`plans` table, `src/plans/plans.ts`) is a draft that touches no git or bd state: steps
carry a title, a description and `dependsOn` indexes, validated by `planProblem` in `packages/shared/src/plan.ts`. It appears
in the Office needs-you strip and opens at `#plan/<id>` (`views/Plan.tsx`). The strip's top Plans row shows the draft count
only, and opens `views/PlanList.tsx`: every plan the daemon has (`GET /api/plans/all`, newest first), each row naming its title,
status and step count. Below it, `views/Programs.tsx` lists the open programs (`GET /api/programs`, then `GET /api/programs/:id` for each `open` one): lanes in API order with one card per batch (title, status, beads done of total, a `waits for <prerequisite title>` chip per unreleased wait) that opens the batch panel, the merge order as a numbered list with `merged` batches struck through, and the entries newest first in local time with the text verbatim. A program whose batches are all merged is labelled done even while its row is still `open`. It refetches when a `board` or `chat` socket message arrives, never on a timer. Opening a plan from the list or a per-plan Office strip row pushes a detail history entry; page Back consumes it and
returns to the view that opened it, while a cold `#plan/<id>` link falls back to Office. This is the route that keeps
a draft, approved or discarded plan reachable, not the hash link alone. Draft titles and descriptions display as readable prose until clicked or their Edit control is used; their editor saves on blur. Step titles edit directly. The plan content is its own scrolling region above a normal-flow action footer, so neither long prose nor the footer obscures another step. Every save carries the revision
it was loaded at; a stale one answers 409 and the page keeps the user's text. `POST /api/plans/:id/approve` calls
`createBatch` without an alternate base (plan approval uses the repository's configured base), then creates one bead per step in `planOrder` (every dependency first) with the batch label and `blocked-by`
dependencies, stores `approved` with the batch id, and wakes the orchestrator with the bead ids. A bd failure part-way calls
`rollbackBatch`, which closes the beads made so far and removes the worktree, branch and row without abandon's notices, and
the plan stays a draft. Discarding changes only the plan's status. The web writes plan drafts; this is the one exception to
the daemon being the only writer of what the web shows, and it ends at approval. See `2026-09-16-plan-gate-design.md`'s "Known
limits" for what a daemon crash mid-approval or a title clash with an open batch leaves behind.

## Discussions

Discussions is experimental. Evals found three-model discussions produced 10 valid ideas on an open question versus 7, but blind judges ranked their answer last behind Claude plus one critic, at 1.66× the cost (evidence: `~/.overseer/evidence/discussions-eval/`).

A discussion is a question put to several agent CLIs at once, each answering on its own and then reading the others. The
participants default to Claude, Codex and OpenCode, each on the standard tier's model for its own harness
(`standardCandidate` in `src/routing/tiers.ts`); a harness with no standard-tier candidate is refused by name rather than
replaced. A participant session is a `sessions` row with role `discussion`, linked to its discussion through the
`sessions.discussion_id` column (the closing synthesis session carries `discussion_kind = 'synthesis'` so a round never
confuses it with a participant), and is started `keepAlive` so it survives between rounds instead of re-reading its
context. Data is three tables (`src/db/schema.ts`): `discussions` (id, question, repo_id, status `running|done|stopped|failed`,
stop_reason, cost_cap default 5.00, created_at, ended_at, synthesis, synthesis_cost, attachments TEXT), `discussion_turns` (discussion_id, round, harness,
session_id, text, cost, created_at), one turn per participant per round, and `discussion_participants` (discussion_id, harness,
session_id, status, cost), the harness/status/cost snapshot written before a repository removal deletes the participant session
rows, so an ended discussion keeps its participants and their final cost. The runner is `src/discussions/discussions.ts`,
wired in `index.ts`.

The sessions are read-only by prompt and by isolation. `prompts/discussion.md` forbids editing, committing, switching
branches and pushing, and each participant runs in its own throwaway checkout: a `git worktree add --detach` of the chosen
repository at one commit SHA resolved before any participant starts under `worktrees/<repo>/disc-<id>/<harness>`. The same
resolver used for new batches selects the fetched origin base for `gitlab-mr` repositories and the local base for
`local-merge`; a failed fetch uses its existing last-fetched-origin or local-base fallback. The synthesis worktree uses that
same SHA even if origin advances during the discussion. With no repository, each session gets an empty directory under
`<dataDir>/discussions/<id>/<harness>`. The cwd is asserted never to be, or sit inside, the
repository's primary checkout, and every worktree is removed when the discussion stops or a restart fails it, so nothing a
participant writes can reach the repository. After each cwd is made, stored question images are copied into its
`.discussion-attachments/<index>-<name>` directory for every participant and synthesis, including the no-repository temp
directory, so each harness can read the file from its own cwd.

`POST /api/discussions` validates the question, the one-to-three non-duplicate participants, the repository and an optional
cost cap (`cost_cap`, default `DEFAULT_COST_CAP`; a non-positive one is refused), and up to four optional PNG, JPEG, WebP or
GIF images as raw base64, with an 8 MB decoded limit per image. The runner first resolves each participant's standard-tier
model and account and the shared base commit, then stores the images under `discussion-<id>` with `storeAttachments` and
writes their name, MIME type, size and path to `discussions.attachments`. It starts them in parallel with the round-1
prompt. A turn end records the round-1 answer as a turn. A turn that ends after an `error` event (a codex or opencode CLI that exits nonzero emits
the error, then the turn end) or with no answer text records no turn: that participant's session is ended and marked
`failed` with the reason, and the others go on. Every start settles before any teardown (`Promise.allSettled`), and a Stop
waits for starts still running, so a late start cannot leave a session or a checkout behind; the cleanup removes every
checkout under `disc-<id>`, not only those a session row names. Removing a repository stops its running discussions first
(`repository removed`), snapshots every discussion of that repository into `discussion_participants`, and only then deletes its
session rows: a detail whose session rows the removal deleted keeps each participant's harness, final status and cost from the
snapshot, falling back to its recorded turns. Every discussion session end emits the `discussion` socket ping, so the open page
refetches a participant the manager marked `failed` on its own (an exit after an `error` with no `turn_end`) too.
`GET /api/discussions` lists them with image name, MIME type and size (never the stored file path), a turn count, cost,
`rounds` (the highest round with a recorded turn) and `round_in_progress` (that round still waits on a participant that has
not failed). `GET /api/discussions/:id` returns the thread, the same path-free image metadata, the per-participant cost
(`cost ?? estimated_cost ?? 0`, summed) and the status. `GET /api/discussions/:id/attachments/:index` serves the image
with its stored MIME type and returns 404 for an unknown discussion or index. The stop route
`POST /api/discussions/:id/stop` ends every participant, removes the worktrees and marks it `stopped`. A `discussion`
socket ping tells the web to refetch. Discussion sessions stay out of the idle-end and stall sweeps, the board and the
office. A daemon that starts with a discussion still running marks it `failed` with `daemon restarted`: the participant
processes are already gone and the round cannot be reconstructed.

Round 1 answers on its own. With images attached, the round-1 and synthesis prompts list one
`[attached image: <absolute cwd path>]` line per image and tell the model to open each image with its file or image tool
before answering and refer to what it shows. Later rounds do not repeat those paths because the `keepAlive` session already
holds round 1, and no-attachment prompts render exactly as they did before. After every participant of a round has answered
or failed, the next round's prompt
(`prompts/discussion.md`) is sent to each still-live participant (`sessions.send`): the other participants' latest answers
verbatim and labelled by harness, then, in order, what the participant agrees with, what it disputes and why, and its
revised answer, ending with one line `Changed: yes` or `Changed: no`. A round is settled once every participant that has
not failed has a turn in it. The discussion stops after three rounds, or earlier after a round in which every live
participant's final non-empty line is `Changed: no`; a missing or malformed line counts as `yes`, so the discussion goes on rather than
ending on a line the prompt could not obtain. A participant that fails — a turn that ended after an `error`, with no
answer, or a session that ended without answering the round — is left out of later rounds and its last answer is still
quoted, marked as its final answer; a participant session ending on its own is noticed a macrotask later, so a `turn_end`
already buffered on the stream is still recorded as its answer first. When a round prompt would exceed the receiving
harness's `inputLimit` (`lifecycle/prompt.ts`), every quoted answer is cut from the middle with a
`[...N characters omitted...]` marker until the prompt fits.

Closing is a synthesis written by a fresh claude session on the standard tier's claude candidate, in the same kind of
throwaway cwd and under the same read-only rules, from `prompts/discussion-synthesis.md`: the question and every
participant's final answer, then what they agree on, what they still disagree on with each side's reason, and a
recommendation. It is stored in `discussions.synthesis` and its cost (`cost ?? estimated_cost ?? 0`) in
`discussions.synthesis_cost`, so the total survives the repository removal that deletes the session; the status becomes
`done` and every participant and synthesis session and worktree is ended. A discussion whose only participants have all
failed is `failed` with no synthesis.

A cost cap per discussion (default `DEFAULT_COST_CAP`, $5) is checked after every turn end against the total
(`discussionCost`), which already includes the synthesis's cost — its live session while it runs, or its stored
`synthesis_cost` once the session row is gone. Reaching it ends every session, sets the status `stopped` with the
stop_reason `cost cap $X reached after round N`, and keeps every turn so far. No synthesis starts after a cap stop, on
purpose: the cap exists to bound the spend, and the synthesis is the one step that can be skipped while still returning
the answers the rounds produced. The synthesis's own turn end is checked too: a synthesis that crosses the cap is not
stored, so the status stays `stopped` with no synthesis. A user's Stop while a round is running ends the discussion at
once, with no further round and no synthesis, and a Stop that lands while a synthesis is being settled stays the final
word rather than the continuation writing `done` over it. The rounds, the stop rule, the synthesis and the cap are decided
in memory (`src/discussions/discussions.ts`), while the persisted rows and the isolation described above are unchanged.

The web page is `views/Discussions.tsx`: `#discussions` holds the form (question, up to four optional question images,
an optional repository, the three participants and the cost cap, all defaulting to the values above) and the list of
discussions, newest first. Each row shows its status, rounds so far (`round N of 3`, with `(in progress)` from
`round_in_progress`), cost so far and start time in local time. `#discussions/<id>` is the thread grouped by round, each turn
labelled by harness with its cost, the total and per-participant cost against the cap, **Stop** while it runs, and the
synthesis card when the discussion is done — its **Send to chat** button posts the synthesis to the orchestrator as a user
message prefixed with the question, and is disabled without one. Long answers collapse behind **Show more**. A `discussion`
socket ping refetches the list and any open thread, and the page is a desktop rail entry that Setup → General links to on
phones, like Usage; Office is its own first phone tab. Participants see the attached images with the question, and the thread renders linked
thumbnails from the discussion attachment route. Unlike the Board, Chat and Review, `#discussions` and `#discussions/<id>`
are exempt from the no-repository redirect to Setup, since a discussion may run with no repository.

## Usage view

`views/Usage.tsx` renders `GET /api/usage`: a range picker (7/30/90 days ending today, 30 default), four summary cards, the two
known limits of these numbers, one stacked bar chart per day by model (`components/UsageChart.tsx`, hand-drawn SVG — the web
carries no charting dependency) with a switch between reported cost, estimated cost and tokens, and sortable breakdowns by model,
account, harness and repository. The pure parts — the range arithmetic, the cost wording, the sort and the stacking — are in
`lib/usage.ts`. The two cost sums stay apart exactly as the daemon keeps them: an entirely unpriced bucket reads "unknown" rather
than `$0.00` and a partly priced one is a floor with its count in the tooltip, so nothing on the page adds a reported figure to an
estimate. Every estimate wears an `est.` marker; on a bucket whose `codex_sessions` is above zero its tooltip also carries the
base-context-tier caveat (a codex session over ~272k tokens per request is estimated up to 2x low), and the page states that
caveat and the restart token gap as two lines beside the cards. Series colours are `--chart-1..6`, each keeping the hue of the status token it comes from (within 20 degrees)
and re-stepped until every pair — not only adjacent ones, since a stacked bar can put any two together — clears the categorical
checks: worst pair deltaE 17.9 normal, 9.4 protan and tritan, and 3:1 contrast against both the dark surface and white; a seventh model folds into "Other" rather than taking a generated hue, and the legend names every series, so identity
is never colour alone. Placement: a rail entry on desktop, hidden in the phone layout because the tab bar was measured full at five tabs
(the Board label wraps at 390 px), with Setup → General carrying an "Open usage" link as the phone's way in and `#usage` as the

## Needs-you strip on Office

Everything blocked on the user appears in a strip above the Office room: a bead awaiting a decision, a batch in review, an
unanswered `ask_user` question, a draft plan, or a repository with a suspect verify command. `lib/needsYou.ts` gathers the items
from board, chat, plans and repo data the shell already holds — no fetch of its own. Office is the default view and first phone
tab. The Plans entry on Office stays above the Needs-you strip, shows the draft count, and opens the list of every plan status,
newest first. When the settled item list is empty, the item strip is not rendered and only the Plans entry remains.

The strip shows at most 3 item rows in the phone layout (read from the shared `usePhoneLayout`) and 6
otherwise, in the order below; the Plans entry is not counted. With more items than that, one button row after the list reads
`+N more`, N being the number hidden; activating it shows every item and turns it into Show fewer at the end of the list, which
returns to the capped list. It is the same button in both states, so focus stays on it. While capped, N follows the items as
they arrive and leave; while expanded, the list stays expanded; once the count is at the cap or below, the control is gone. The
expanded state is not persisted: a reload, or leaving Office (the strip stays mounted and collapses while hidden), shows the
capped list. The review's scene with 12 questions and 12 batches in review had the strip take the top two-thirds of a 1440x900
screen, the room shrink to 303x190 and the Chat composer cut off; at 390x844 the room started at y = 1525.

`needsUser` (a failed verification or `awaiting_decision`) is shared with `Board.tsx`, so the Board's "sort it to the top of its
column" and the strip read one definition. A card in the done column is excluded, and so is a batch with `waiting_on`: that one
waits on an overlapping batch ahead of it, not on the user. Items are ordered by what the wait costs — plan, repo, question,
decision, batch, failed — and keep their source order within a kind, since the board carries no timestamp for a card. An open
unanswered, non-superseded question that names a bead id as a whole token suppresses that bead's decision or failed item:
answering the question resolves that choice, and once it is answered or superseded the card appears again if it still needs the
user.

A row's headline is the readable title (the question, the bead's title, the batch's title) and its second line carries the repo,
the id and the state; a list is scanned by what things are, not by their ids. **Every line is clipped, never wrapped**
(`min-width: 0` on the grid child, then `overflow: hidden; text-overflow: ellipsis; white-space: nowrap`). A real batch title —
"Lessons from overseer overseer-b33-e4d5: a fallback that degrades the user's stated flow is a decision for the user, not a review
finding to implement" — pushed the first banner attempt past the viewport at 390 px; the earlier harness used short fixtures and
proved nothing. Clipping is structural, and the check uses that title with five items at 390 and 1280 px.

Decision and failed bead rows open their TaskPane over Office, so the user can act without leaving the room. A batch opens its review drawer over Office, where the shared summary and earlier rounds, approver note, waiting and conflict banners, merge-request link, Merge or Mark merged, Reject with a required note and attachments, and Abandon are available; Open in Review opens Review,
a question row selects that question and focuses its answer in the docked Chat, or opens Chat with the question selected and focused when the dock is absent; a plan opens its page, and a repo opens Setup → Repositories. The Plans entry on Office opens `PlanList`,
including approved and discarded plans that do not appear as draft item rows. A plan opened from the Needs-you strip on Office
returns to Office on Back; a plan opened from its list returns to that list.

The browser tab keeps using the full `needsYouItems` count: it draws a favicon badge and changes the title to `(n) Overseer`; where
canvas is unavailable, it changes the title only. Office has no separate Needs tab or badge.

Review has its own badge; a batch in review showed nothing on the Review tab before it was added. `RailCounts.review` is the number
of `batch` items in `needsYouItems`, so it counts exactly the batches ready for the user: in review, not `waiting_on`, in a repo
whose effective batch approver is the user. `RailCounts.reviewWaiting` counts the review batches with `waiting_on`. The visible
badge shows only the ready count; with waiting batches, its tooltip and accessible name read "1 ready for review, 1 waiting", and
with none waiting they read only "1 ready for review". With zero ready batches there is no visible badge, even when waiting batches
remain. In the Review list, **Ready for you** uses the badge's actionable-batch rule. **Waiting** contains review batches with

from the board. Review batches without `waiting_on` whose effective approver is the orchestrator stay visible under **Handled by
orchestrator**. Empty groups are hidden; the existing empty state remains when there are no batches or review tasks. After a blocker
is merged, the next board refresh clears `waiting_on` and releases a user-approved batch to **Ready for you**.
The favicon and title remain the full item count.

In the phone layout each tab's count badge overlaps the top-right corner of its label like an app-icon badge: the badge and warning dot
sit inside the label span, positioned absolutely, so neither shifts nor widens the label; the badge's right edge is 6 px past the
label and the Board's failed dot sits below it at the label's bottom-right. The five phone tabs are Office, Board, Chat, Review and
Setup. In the desktop layout the badge stays at the row's right end.

The initial Chat page contains the latest 100 rows. **Show earlier messages** fetches the preceding page and preserves the visible top row; a chat socket event (and a send or an answer) fetches the latest page again and merges it by id into the loaded rows, so answered, superseded and queued changes on the rows that live there are reflected while loaded earlier pages stay; `has_more` and `oldest_id` change only when an earlier page loads. Every page also carries every open question and every queued notice, however old (deduplicated by id, ascending), so the Office strip, Chat rail count, favicon badge and Chat pin never lose a question to pagination; `has_more` and `oldest_id` describe the window only. The daemon's `since` parameter is not used by the web. A thread pinned to the bottom follows new rows. When scrolled up, new rows from others show a Jump to latest button with a count capped at 99+ and an Unread divider above the first arrival (a day separator, when that arrival also opens a local day, sits above the divider); only non-user, non-pending arrivals since the thread last reached the bottom count toward the button, while loading earlier rows, the user's own rows and pending questions do not count. The divider remains anchored at its first arrival after reading; sending clears it and a reload recalculates it. The thread is at the bottom when `scrollHeight - clientHeight - scrollTop` is at most 24 px, one test shared by the pin, the button and the read position, because an iPhone touch scroll stops 2 to 3 px short. Reaching the bottom (by scrolling, Jump to latest or an auto-scroll) hides the button, clears its count and records the highest row as read at once, not only when Chat is left; sending also clears the divider. Jump to latest and every scroll to the bottom set the thread's own `scrollTop` to its `scrollHeight`, again on the next animation frame, instead of `scrollIntoView`, which can move the page or the visual viewport on iOS. Chat keeps the last read row across view changes; a return from another view, like a full load, opens at the bottom whatever arrived, with the Unread divider above the first row that arrived while away and no Jump to latest button. On iOS, a visual viewport shorter than the layout viewport at scale 1 sizes Chat from its height and offset to keep the composer above the keyboard, including when the viewport is panned. While that state is on (the `chat-visual-viewport` class on `.chat`, which the phone shell reads through `.app:has(.chat-visual-viewport)`), the fixed bottom tab bar is hidden and `main` drops its bottom padding for it, so nothing fixed covers the composer when Safari pans the page, and the question card uses 6 px padding and 4 px gaps so the pager, a one-line question, the answer box and the buttons fit its cap; both return when the keyboard closes. The thread retains bottom pinning. Chrome's layout resize, desktop and pinch zoom keep the normal height.

User message status: Chat shows Waiting, Seen, or Answered beside the time from `queued_at`, `seen_at`, and `replied_at`. A null row newer than the first seen user row is Waiting; an older null row has no status. The existing chat refresh updates the label. Assistant and system rows have no message status. A continuation user row floats the stamp at the right of its first text line, so only that line is shortened and a row without a status reserves no space; the group-start row keeps You, time, and status on its role line.

### Chat image attachments

The Chat composer and the Review rejection note for both a batch and a v1 bead accept images from the attach button, clipboard paste, or drag-and-drop. The picker accepts PNG, JPEG, WebP and GIF files, up to four files at 8 MB each; the daemon stores them under `<orchestratorDir>/attachments/`, keeps their metadata in the chat row, and serves each one from `GET /api/chat/:id/attachments/:index`. Chat messages and rejection notices deliver one `[attached image: <absolute path>]` line per file to the orchestrator, whose prompt tells it to read the files with the Read tool. In the phone layout, the composer and Review attach buttons and pending-image remove buttons have 44 px touch targets, and attached message images use `max-width: 100%`.

- Daemon-owned servers: a worker that needs a long-lived process (a dev server, a preview, a Playwright run) asks the daemon for it instead of starting it in its shell, through four MCP tools — `start_server` (command, optional cwd and name; returns a `server_id`), `server_logs` (tail, to confirm the ready line or read a stack trace), `stop_server` and `list_servers`. No harness can hold such a process itself: opencode's shell tool is synchronous and upstream closed the background-process request as not planned, codex's command policy refuses `Start-Process ... -PassThru` on Windows, and a claude worker is denied `run_in_background` by the daemon's own hook because a headless session exits when the model yields. The process is a child of the daemon, not of the worker, with its output on a file in `<data dir>/servers/`, so it holds none of the session's stdio and cannot keep a turn open the way the codex worker of overseer-41x did for 75 minutes. `stop` runs the same `sweepProcessTree` the harness adapters use, so the server's own children go with it. Every server a session started is stopped when that session ends, and `servers.recover()` at startup kills any that outlived a restart, since an adopted worker can no longer stop what it started. Rows live in the `servers` table (`id`, `session_id`, `repo_id`, `bead_id`, `name`, `command`, `cwd`, `pid`, `pid_started_at`, `log_path`, `status`, `started_at`, `stopped_at`).
- Per-session MCP URLs: `registerMcp` serves the tools at `/mcp/<session id>` as well as `/mcp`, and `SessionManager.start` appends the session row id to every MCP server URL it hands a harness. A tool call needs a caller identity — `start_server` must know whose session it is starting a process for — and no harness lets the daemon set a request header, while every harness already takes a per-session MCP config. Bare `/mcp` keeps working for a caller with no identity; a server tool called there answers "this tool is available to a worker session only". Workers are given the `overseer` MCP server for the first time here; previously only orchestrator and critic sessions received one.
